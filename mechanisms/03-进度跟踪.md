# 机制详解：进度跟踪 (Progress Tracking)

> **对应失效**：⑤ 状态丢失 (State Loss)
> **核心贡献**：每完成一个子任务里程碑，立即将进度持久化到本地文件。关键里程碑打 git commit。
> Session 重启时自动读取进度文件，从断点续传。
> **所属支柱**：状态流（主要）、输入流（恢复上下文）

---

## 一、为什么需要进度跟踪？

### 1.1 Agent 是脆弱的——不是会不会 crash，而是何时 crash

```
Agent 进程可能因以下原因终止：
  ┌─────────────────────────────────────────┐
  │ 用户行为                                 │
  │  · 关闭终端/IDE                          │
  │  · 按 Ctrl+C                             │
  │  · 电脑休眠/关机                         │
  ├─────────────────────────────────────────┤
  │ 系统行为                                 │
  │  · OOM Killer 杀死进程                   │
  │  · 系统重启（Windows Update 强制重启）     │
  │  · 云函数达到最大执行时间（15 min）        │
  ├─────────────────────────────────────────┤
  │ API 行为                                 │
  │  · 持续 429 限流 → 异常退出               │
  │  · 账单余额不足 → API 返回 402 → 退出     │
  │  · 服务端故障 → 无法恢复的错误             │
  ├─────────────────────────────────────────┤
  │ 代码问题                                 │
  │  · Agent 自己的代码有 bug → crash         │
  │  · 工具调用触发未预期的异常               │
  │  · 死锁或无限等待                         │
  └─────────────────────────────────────────┘
```

**没有进度跟踪** → crash 后一切归零。一个完成了 90% 的 45 分钟任务，从零开始重做。

**有进度跟踪** → crash 后读取 progress.json，从第 8/10 步子任务继续。损失最多 5 分钟。

### 1.2 进度跟踪解决的核心矛盾

> **Agent 运行时间越长，crash 概率越高，crash 损失也越大。**
> 
> 进度跟踪打破了这个恶性循环——让 crash 损失被限制在最后一个毫秒级操作内。

### 2.2 进度状态机

```
pending ──→ in_progress ──→ completed
                │               
                └──→ failed ──→ (retry) → in_progress
                      │
                      └──→ skipped (用户决定跳过)
                      └──→ blocked (等待人工操作)
```

```python
class SubtaskStatus(Enum):
    PENDING = "pending"          # 还没开始
    IN_PROGRESS = "in_progress"  # 正在执行
    COMPLETED = "completed"      # 完成并通过验证
    FAILED = "failed"            # 失败（已达最大重试次数）
    SKIPPED = "skipped"          # 用户决定跳过
    BLOCKED = "blocked"          # 被阻塞（依赖未满足/等待人工）

# 状态转换规则
ALLOWED_TRANSITIONS = {
    PENDING: [IN_PROGRESS, SKIPPED],
    IN_PROGRESS: [COMPLETED, FAILED, BLOCKED],
    FAILED: [IN_PROGRESS, SKIPPED],  # 重试或跳过
    BLOCKED: [IN_PROGRESS, SKIPPED],  # 解除阻塞后继续或跳过
    COMPLETED: [],  # 终态
    SKIPPED: [],    # 终态
}
```

## 三、写入策略

### 3.1 写入时机

```python
class ProgressWriter:
    """
    进度自动写入的触发条件
    """
    
    def on_subtask_status_change(self, subtask, old_status, new_status):
        """任何子任务状态变更 → 立即写入"""
        self.save()
    
    def on_iteration_complete(self, iteration_number):
        """每轮四相循环结束 → 写入"""
        self.save()
    
    def on_signal(self, signum):
        """收到 SIGTERM/SIGINT → 紧急写入 + 标记 interrupted"""
        self.progress.status = "interrupted"
        self.progress.interrupted_at = datetime.utcnow()
        self.save()
        # 注意：这里的时间窗口很窄，必须快速完成
        # 所以只写入关键信息，不做复杂计算
    
    def periodic_save(self):
        """每 30 秒兜底写入一次"""
        if self.last_save_time + timedelta(seconds=30) < datetime.utcnow():
            self.save()
```

### 3.2 原子写入（防止写入中途 crash）

```python
import os
import json
import tempfile

def atomic_write(filepath, data):
    """
    原子写入：先写临时文件，再 rename
    确保不会出现写到一半 crash 导致文件损坏的情况
    """
    dirpath = os.path.dirname(filepath)
    
    # 1. 在同一目录下创建临时文件（确保在同一文件系统，rename 才是原子的）
    with tempfile.NamedTemporaryFile(
        mode='w',
        dir=dirpath,
        suffix='.tmp',
        delete=False
    ) as tmp:
        json.dump(data, tmp, indent=2, default=str)
        tmp.flush()
        os.fsync(tmp.fileno())  # 确保写入磁盘
    
    # 2. 原子 rename（在 Unix 上这是原子操作）
    os.replace(tmp.name, filepath)
    # 注意：Windows 上 os.replace 也是原子的（要求同文件系统）
```

```python
        # 仍然可以恢复，因为 Agent 的操作是幂等的
        # 但需要提醒用户可能存在冲突
    
    # 查找第一个未完成的子任务
    next_subtask = find_next_pending(progress_data["subtasks"])
    
    if next_subtask is None:
        print("✅ 所有子任务已完成！")

    print(f"   上次更新: {last_update.strftime('%Y-%m-%d %H:%M UTC')}")
    
    if progress_data.get("statistics", {}).get("total_tokens_used"):

    return Progress.from_dict(progress_data)
```

### 4.2 恢复后的上下文重建

```python
def rebuild_context_on_resume(progress: Progress) -> dict:
    """
    从进度文件重建 Agent 的工作上下文
    Agent 醒来后需要知道:
    1. 任务是什么
    2. 做到哪了
    3. 前面做了什么（不影响后续决策的摘要）
    4. 当前卡在哪（如果是重试）
    """
    
    context = {
        "task": progress.task_description,
        "progress_summary": (
            f"已完成 {progress.completed_count}/{progress.total_count} 个子任务。"
        ),
        "completed_work": [],   # 已完成的子任务摘要
        "current_subtask": {},  # 当前正在做的子任务
        "blockers": []          # 遇到的阻塞问题
    }
    
    for subtask in progress.subtasks:
        if subtask.status == "completed":
            context["completed_work"].append({
                "id": subtask.id,
                "description": subtask.description,
                "key_output": subtask.output_summary
            })
        elif subtask.status == "in_progress":
            context["current_subtask"] = {
                "id": subtask.id,
                "description": subtask.description,
                "attempts_so_far": subtask.attempts,
                "last_error": subtask.last_error,
                "last_verification_output": subtask.last_verification_output
            }
        elif subtask.status == "failed":
            context["blockers"].append({
                "id": subtask.id,
                "description": subtask.description,
                "failure_reason": subtask.last_error
            })
    
    return context
```

## 五、Git 集成：里程碑式 Commit

### 5.1 什么时候打 Commit

```python
MILESTONE_COMMIT_CONDITIONS = [
    # 1. 重要子任务完成
    lambda st: st.phase == "act" and st.status == "completed",
    
    # 2. 阶段性里程碑（如 "所有重命名完成"）
    lambda st: st.is_milestone and st.status == "completed",
    
    # 3. 用户手动触发
    lambda st: st.user_requested_checkpoint,
    
    # 4. 完成了 N 个累积的修改后
    lambda progress: progress.modifications_since_last_commit >= 5,
]
```

### 5.2 Commit 消息规范

```python
def generate_commit_message(subtask):
    """
    Agent 的 commit 消息应该包含:
    - 子任务 ID：方便追溯
    - 符号：✅ 表示自动操作，🔧 表示修复
    - 子任务描述：人类可读
    """
    prefix = "✅" if subtask.status == "completed" else "🔧"
    return (
        f"{prefix} [{subtask.id}] {subtask.description}\n\n"
        f"Verification: {subtask.verification.result}\n"
        f"Task: {subtask.progress.task_id}\n"
        f"Agent session: {subtask.progress.session_id}"
    )
```

### 6.2 跨 Session 的一致性

```python
def validate_consistency(progress):
    """
    恢复前验证进度文件与实际环境的一致性
    """
    warnings = []
    
    # 1. 检查 Git 分支
    current_branch = run("git branch --show-current").strip()
    recorded_branch = progress.context_snapshot.get("git_branch")
    if current_branch != recorded_branch:
        warnings.append(f"Git 分支从 {recorded_branch} 变为 {current_branch}")
    
    # 2. 检查关键文件是否存在
    for subtask in progress.subtasks:
        if subtask.status == "in_progress":
            for artifact in subtask.artifacts:
                if not os.path.exists(artifact):
                    warnings.append(f"产物 {artifact} 可能被移动或删除")
    
    # 3. 检查是否有未提交的修改（可能在 crash 期间被其他进程修改）
    dirty = run("git status --porcelain").strip()
    if dirty:
        warnings.append("工作区有未提交的修改，可能与 Agent 进度冲突")
    
    return warnings
```

## 八、总结

进度跟踪是 Harness 的**保险系统**。它不能防止 crash，但它确保 crash 的成本可控。

核心设计原则：
1. **每次状态变更立即落盘**（不是"有空了再写"）
2. **原子写入**（写一半 crash 也不能损坏文件）
3. **足够的元数据**（不仅记录"做到哪了"，还记录"当时的环境是什么样"）
4. **Git 作为双重保险**（文件 + git history 两条线保护进度）
