# 机制详解：子代理分治 (Subagent Delegation)

> **对应失效**：② Context 溢出 (Context Overflow) —— 隔离维度的解决
> **核心贡献**：把特定子任务委托给拥有独立 context 的子 Agent。子 Agent 在自己的 messages 列表中工作，完成后只把最终结果摘要返回给主 Agent。主 Agent 的 context 完全不受子任务中间过程的污染。
> **所属支柱**：输入流（隔离视野）、控制流（分治管控）、状态流（独立生命周期）

---

## 一、为什么需要子代理？

### 1.1 Context 隔离的必要性

主 Agent 的 context 是**有限且共享**的资源。每个工具的每次调用、每轮交互的中间结果都会占用这个共享空间。当多个子任务在主 context 中交叉执行时：

```
主 Agent 的 messages (不用子代理):
  [system prompt] ................... 2K
  [分析子任务 A] ........... 15 轮 .... 45K
  [分析子任务 B] ........... 20 轮 .... 60K
  [分析子任务 C] ........... 12 轮 .... 36K
  [执行子任务 D] ........... 18 轮 .... 54K
  ──────────────────────────────────────
  总计: ~197K tokens → 爆炸！

主 Agent 的 messages (用子代理):
  [system prompt] ................... 2K
  [规划: 将 A,B,C 委托给子代理] ........ 2K
  [子代理 A 结果摘要] ................ 0.5K
  [子代理 B 结果摘要] ................ 0.5K
  [子代理 C 结果摘要] ................ 0.5K
  [基于汇总结果的决策] ................ 3K
  ──────────────────────────────────────
  总计: ~8.5K tokens → 充裕

节省了 ~188.5K tokens (95.7%)！
```

**子代理分治的"分治"**：不是让一个 Agent 做所有事，而是把一个复杂任务拆成多个独立子任务，每个子任务由一个独立的子 Agent 在自己的隔离 context 中完成。

### 1.2 子代理的独立特性

```
每个子代理：
  - 拥有独立的 messages 列表（context 隔离）
  - 拥有独立的工具集（权限隔离）
  - 拥有独立的迭代上限（资源隔离）
  - 独立崩溃不影响主 Agent（故障隔离）
  - 可以并行执行（性能隔离）
```

## 二、子代理的设计

### 2.1 子代理结构

```python
@dataclass
class Subagent:
    """一个拥有独立上下文的、专注于单一任务的小型 Agent"""
    
    # === 身份 ===
    name: str                    # 名称，如 "test-runner", "csv-analyzer"
    role: str                    # 角色描述
    
    # === 独立性 ===
    messages: list               # 独立的 messages 列表
    tools: list[str]             # 独立的工具子集（最小权限原则）
    max_iterations: int = 15     # 独立的最大迭代次数
    
    # === 接口 ===
    input_schema: dict           # 接收的输入格式
    output_schema: dict          # 返回的输出格式
    
    # === 生命周期 ===
    timeout_seconds: int = 300   # 独立的超时限制
    token_budget: int = 50000    # 独立的 token 预算
    
    # === 状态 ===
    status: str = "idle"         # idle / running / completed / failed / timeout
    result: SubagentResult = None


@dataclass
class SubagentResult:
    """子代理返回的结果（精简的、结构化的）"""
    success: bool
    summary: str                 # 产出的摘要（不是全部细节！）
    artifacts: list[str]         # 产出的文件路径
    key_findings: list[str]      # 关键发现
    errors: list[str]            # 遇到的错误（如果有）
    metrics: dict                # 执行的指标
    # metrics 包含:
    #   iterations: 实际迭代次数
    #   tokens_consumed: 消耗的 token 数
    #   duration_seconds: 执行时间
    #   tools_called: 调用了哪些工具
```

### 2.2 子代理的 System Prompt 设计

子代理的 system prompt 与主 Agent 不同：

```python
SUBAGENT_SYSTEM_PROMPT = """
你是 {name}，一个专门负责 {role} 的 AI 子代理。

## 你的工作方式
- 你接收的是一个具体的、明确的任务
- 你在自己的独立上下文中工作，你的中间过程不会被主 Agent 看到
- 你只需要返回最终结果，不需要解释你的中间推理过程
- 你只有 {max_iterations} 次迭代机会完成这个任务

## 你可以使用的工具
{available_tools}

## 你必须返回的格式
完成或失败后，你必须以以下 JSON 格式返回结果：
```json
{{
    "success": true/false,
    "summary": "对完成工作的简洁摘要（不超过 200 字）",
    "artifacts": ["生成/修改的文件路径列表"],
    "key_findings": ["关键发现的列表"],
    "errors": ["如果失败，列出错误"]
}}
```

## 重要规则
1. 只专注于分配给你的这一个任务，不要做其他事
2. 如果遇到无法处理的错误，标记 success=false 并返回
3. 不要猜测——如果不确定，用工具去验证
4. 你的响应要简洁——你在消耗主 Agent 的预算
"""
```

## 三、主 Agent 如何调度子代理

### 3.1 子代理调用 = 高级函数调用

从主 Agent 的视角，调用子代理就像调用一个**异步的高级函数**：

```
主 Agent 视角:
  输入: 子代理名称 + 任务描述 + 上下文数据
  输出: SubagentResult (成功/失败 + 摘要 + 产物)
  
关键: 主 Agent 完全不用关心中间过程！
```

### 3.2 三种调用模式

```python
class SubagentInvocation:
    
    @staticmethod
    async def fire_and_forget(name, task, context):
        """
        模式 1: Fire-and-Forget
        委托一个子代理去执行任务，主 Agent 继续做其他事
        
        适用场景:
          - 独立任务，主 Agent 不依赖其结果做下一步决策
          - 如 "运行全量测试"、"生成代码覆盖率报告"
        """
        subagent = Subagent(name=name, ...)
        # 启动后立即返回，不等待
        task_future = run_in_background(subagent.execute, task, context)
        return task_future  # 主 Agent 可以稍后检查
    
    @staticmethod
    async def request_response(name, task, context):
        """
        模式 2: Request-Response
        委托子代理执行任务，等待结果后基于结果继续
        
        适用场景:
          - 有依赖关系，主 Agent 需要子代理的结果来决定下一步
          - 如 "分析这个 CSV 的结构" → 基于分析结果决定清洗策略
        """
        subagent = Subagent(name=name, ...)
        result = await subagent.execute(task, context)
        return result
    
    @staticmethod
    async def map_reduce(name_template, tasks, context):
        """
        模式 3: Map-Reduce
        启动多个子代理并行执行同类任务，汇总结果
        
        适用场景:
          - 批量操作，如 "分析 10 个模块各自的测试覆盖率"
          - "并行检查 5 个微服务的健康状态"
        """
        subagents = []
        for i, task in enumerate(tasks):
            name = name_template.format(i=i)
            subagents.append(Subagent(name=name, ...))
        
        # 并行启动
        futures = [
            subagent.execute(task, context)
            for subagent, task in zip(subagents, tasks)
        ]
        
        # 等待全部完成
        results = await asyncio.gather(*futures)
        
        # 汇总
        return SubagentResult(
            success=all(r.success for r in results),
            summary=f"{sum(1 for r in results if r.success)}/{len(results)} 子任务成功",
            artifacts=sum([r.artifacts for r in results], []),
            key_findings=sum([r.key_findings for r in results], []),
            errors=sum([r.errors for r in results], []),
            metrics={"subagent_count": len(subagents)}
        )
```

## 四、子代理的生命周期管理

### 4.1 超时与资源控制

```python
class SubagentTimeout(Exception):
    pass

class SubagentTokenExhausted(Exception):
    pass

def execute_subagent_with_guard(subagent, task, context):
    """
    子代理执行的生命周期管理
    """
    
    # 创建独立的 token 计数器
    token_counter = TokenCounter(budget=subagent.token_budget)
    
    # 设置超时
    start_time = time.time()
    
    try:
        for iteration in range(subagent.max_iterations):
            # 检查超时
            if time.time() - start_time > subagent.timeout_seconds:
                raise SubagentTimeout(
                    f"子代理 {subagent.name} 超时 "
                    f"({subagent.timeout_seconds}s)"
                )
            
            # 检查 token 预算
            if token_counter.remaining <= 0:
                raise SubagentTokenExhausted(
                    f"子代理 {subagent.name} token 预算耗尽"
                )
            
            # 正常执行一步
            response = llm.chat(subagent.messages, subagent.tools)
            token_counter.add(response.usage)
            
            # ... 工具调用处理 ...
            
            # 检查是否完成
            if task_completed(response):
                result = extract_result(response)
                result.metrics = {
                    "iterations": iteration + 1,
                    "tokens_consumed": token_counter.used,
                    "duration_seconds": time.time() - start_time,
                    "tools_called": token_counter.tools_used
                }
                return result
        
        # 达到最大迭代次数
        return SubagentResult(
            success=False,
            summary=f"子代理达到最大迭代次数 ({subagent.max_iterations})",
            errors=["MAX_ITERATIONS_REACHED"]
        )
    
    except SubagentTimeout:
        return SubagentResult(
            success=False,
            summary=f"子代理超时 ({subagent.timeout_seconds}s)",
            errors=["TIMEOUT"]
        )
    
    except SubagentTokenExhausted:
        return SubagentResult(
            success=False,
            summary=f"子代理 token 预算耗尽 ({subagent.token_budget})",
            errors=["TOKEN_EXHAUSTED"]
        )
    
    except Exception as e:
        # 真正的崩溃——子代理内部出现了意外错误
        # 崩溃被隔离在这里，不影响主 Agent
        return SubagentResult(
            success=False,
            summary=f"子代理异常终止: {str(e)[:200]}",
            errors=[f"CRASH: {type(e).__name__}"]
        )
```

### 4.2 崩溃隔离

```
子代理崩溃 ≠ 主 Agent 崩溃

子代理的执行在隔离的上下文中：
  - 子代理的 messages 独立 → 不会污染主 context
  - 子代理的异常被捕获 → 不会传播到主 Agent
  - 主 Agent 只需处理 SubagentResult (success=False)

主 Agent 的恢复选项：
  1. 重新委托同一个子代理（retry）
  2. 换一个策略的替代子代理（fallback）
  3. 主 Agent 自己完成这个子任务（degrade）
  4. 报告用户（escalate）
```

## 五、子代理的设计原则

### 5.1 最小权限原则

```python
# ✅ 正确：只给完成任务所需的最小工具集
test_runner = Subagent(
    name="test-runner",
    tools=["bash", "read"],  # 只能运行命令和读文件
    # 不能: 写文件、编辑代码、网络请求
)

# ❌ 错误：给了多余的工具
test_runner = Subagent(
    name="test-runner",
    tools=["bash", "read", "write", "edit", "webfetch", "delete"],
    # ↑ 为什么 test runner 需要编辑代码和删除文件？
)
```

### 5.2 单一职责原则

```
每个子代理只做一件事：
  ✅ test-runner  → 运行测试 + 报告结果
  ✅ code-fixer   → 根据测试失败信息修复代码
  ✅ csv-analyzer → 分析 CSV 文件结构 + 返回字段信息
  ✅ doc-writer   → 基于代码生成文档

  ❌ do-everything → 分析 + 修复 + 测试 + 文档 ← 这是主 Agent 的工作
```

### 5.3 输入明确原则

```python
# ✅ 好的子代理委托：输入明确、具体
await subagent.execute(
    task="运行 tests/services/test_user_service.py 中的所有测试",
    context={
        "test_file": "tests/services/test_user_service.py",
        "python_version": "3.12",
        "required_env_vars": ["DATABASE_URL=postgresql://test:test@localhost:5432/test"]
    }
)

# ❌ 坏的子代理委托：输入模糊
await subagent.execute(
    task="运行一下测试看看有什么问题",
    context={}
)
```

### 5.4 输出结构化原则

```python
# ✅ 好的子代理输出：结构化、可解析
{
    "success": true,
    "summary": "全量测试通过: 247/247",
    "artifacts": ["test-results.xml"],
    "key_findings": ["覆盖率: 87%"],
    "errors": []
}

# ❌ 坏的子代理输出：自由文本
"""
好的，我运行了测试，结果还不错，
247 个通过，有一些覆盖率数据...
哦对了测试结果保存在 test-results.xml 里...
"""
# ↑ 主 Agent 需要再次解析这个自由文本 → 又消费一轮 tokens！
```

## 六、子代理代理树

```
                    ┌──────────────┐
                    │  主 Agent     │
                    │  (协调者)      │
                    └──┬───┬───┬──┘
                       │   │   │
          ┌────────────┼───┼───┼────────────┐
          │            │   │   │            │
          ▼            ▼   ▼   ▼            ▼
    ┌──────────┐ ┌──────┐ ┌──────┐ ┌───────────┐
    │analyzer  │ │tester│ │fixer │ │doc-writer │
    │(分析模块) │ │(测试) │ │(修复)│ │(文档生成)  │
    └──────────┘ └──────┘ └──┬───┘ └───────────┘
                             │
                             ▼
                      ┌──────────┐
                      │lint-fixer│
                      │(lint修复)│
                      └──────────┘
```

代理树的深度一般不超过 2 层（主 → 子 → 孙），过深会导致：
- 协调开销超过实际工作
- 错误在多级传递中被稀释
- 调试极其困难

## 七、子代理 vs 函数调用的区别

```
                  子代理                    普通函数调用
────────────────────────────────────────────────────
决策能力           有自己的 LLM 可以独立决策     固定逻辑，不能自主判断
Context            有独立的 messages 列表         无状态
任务粒度           复杂子任务                      单个工具操作
恢复能力           可以在内部处理异常后继续        失败就是失败，返回错误
成本              消耗 tokens + 时间              基本免费（除了 API 调用本身）
适用场景           需要多步推理的复杂子任务         简单的单步操作
```

**经验法则**：
- 子任务需要 ≥ 5 轮 LLM 交互 → 考虑子代理
- 子任务只需要 1-2 个工具调用 → 不需要子代理，主 Agent 自己做

---

## 八、总结

子代理分治是 Context 溢出的**隔离解**。它通过将复杂任务拆解到独立的子 Agent 中，实现了：

1. **Context 隔离**：子任务中间过程不污染主 Agent 视野
2. **故障隔离**：子代理崩溃不影响主 Agent
3. **资源隔离**：独立的 token 预算和超时
4. **并行可能**：同 parallel_group 的子任务可并行执行

子代理分治 + 任务拆解 = 从"一个 Agent 扛所有事"变成"一支 Agent 团队协作"。
