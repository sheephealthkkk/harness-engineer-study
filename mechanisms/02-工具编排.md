# 机制详解：工具编排 (Tool Orchestration)

> **对应失效**：④ Tool 错误吞并 (Tool Error Swallowing)、⑥ 缺权限闸 (Missing Permission Gate)
> **核心贡献**：所有工具调用包裹在结构化 Schema 中，失败返回结构化错误信息而非空字符串；前置权限检查。
> **所属支柱**：控制流（主要）、输入流（返回内容）

---

## 一、为什么需要工具编排？

### 1.1 工具调用是最容易出错的环节

Agent 的工具调用发生在系统边界——与外部世界交互的地方。这意味着它面对的是**不可控的真实环境**：

```
工具调用可能因为以下任何原因失败：
  - 网络: 超时、DNS 解析失败、连接被拒绝
  - 文件系统: 权限不足、文件不存在、磁盘满
  - 操作系统: 进程被 kill、信号中断、资源耗尽
  - 被调用服务: API 限流 (429)、服务端错误 (500)、认证失败 (401)
  - 参数: 类型错误、范围错误、格式错误
  - 环境: 环境变量缺失、依赖未安装、版本不兼容
```

Naive Agent 用一个 `except: return ""` 掩盖了所有这些情况。

### 1.2 工具编排的四个目标

```
1. 永不吃掉错误 —— Agent 总能知道调用成功了还是失败了
2. 分类错误类型 —— 不同错误类型 → 不同恢复策略
3. 提供救援提示 —— 告诉 Agent "接下来可以试试什么"
4. 前置权限检查 —— 危险操作在执行前就拦截
```

## 二、工具调用的生命周期

```
┌─────────────────────────────────────────────────────┐
│  1. 工具调用请求 (LLM 产出 tool_call)                │
│     ↓                                                │
│  2. 前置检查 (权限闸)                                 │
│     ├── 被禁止 → 返回 PERMISSION_DENIED              │
│     ├── 需审批 → 暂停，等待用户确认                   │
│     └── 允许 → 继续                                  │
│     ↓                                                │
│  3. 参数校验与预处理                                  │
│     ├── 校验失败 → 返回 INVALID_ARGUMENTS            │
│     └── 通过 → 继续                                  │
│     ↓                                                │
│  4. 执行工具                                         │
│     ├── 超时 → 返回 TIMEOUT + 重试建议               │
│     ├── 异常 → 返回 UNKNOWN_ERROR + traceback        │
│     └── 成功 → 返回结果 + 元数据                      │
│     ↓                                                │
│  5. 后处理 (截断、格式化)                             │
│     └── 结果太大 → 截断 + 标记 TRUNCATED             │
│     ↓                                                │
│  6. 返回 ToolResult (统一格式)                        │
└─────────────────────────────────────────────────────┘
```

## 三、ToolResult：结构化的工具返回

### 3.1 Schema 设计

```python
from dataclasses import dataclass, field
from typing import Any, Optional
from enum import Enum

class ErrorType(Enum):
    """标准化的错误分类"""
    TIMEOUT = "timeout"              # 执行超时
    PERMISSION_DENIED = "perm"       # 权限被系统或用户拒绝
    USER_DENIED = "user_denied"      # 用户拒绝了审批请求
    INVALID_ARGUMENTS = "bad_args"   # 参数格式/类型错误
    NOT_FOUND = "not_found"          # 目标资源不存在（文件、API等）
    RATE_LIMITED = "rate_limited"    # 被调用服务限流
    AUTH_FAILED = "auth_failed"      # 认证/授权失败
    EXECUTION_FAILED = "exec_fail"   # 执行过程中失败（如编译错误）
    UNKNOWN = "unknown"              # 未分类的错误

@dataclass
class ToolResult:
    """统一的工具调用返回结构"""
    
    # === 成功/失败标识 ===
    success: bool
    # → Agent 第一眼看到的字段
    # → 决定后续策略：正常继续 vs 分析错误 vs 换方案
    
    # === 成功时的数据 ===
    data: Any = None
    # → 工具的实际产出
    
    # === 失败时的信息 ===
    error_type: Optional[str] = None
    # → 错误分类，对应 ErrorType
    # → Agent 据此选择恢复策略：
    #   TIMEOUT → 重试（可能分段）
    #   PERMISSION_DENIED → 报告用户或换路径
    #   NOT_FOUND → 检查路径是否正确
    #   RATE_LIMITED → 等待后重试
    #   INVALID_ARGUMENTS → 修正参数后重试
    
    error_message: Optional[str] = None
    # → 人类可读的错误描述
    # → "文件 /path/to/file 不存在（当前目录:/home/user/project）"
    # → 注意：提供上下文（当前目录、用户权限等）帮助 Agent 诊断
    
    error_traceback: Optional[str] = None
    # → 技术细节，截断到 500 字符
    # → 给 Agent 足够信息分析根本原因
    
    # === 救援提示 ===
    suggestion: Optional[str] = None
    # → 给 Agent 的"接下来试试这个"建议
    # → "请使用 --force 参数或先获取文件所有权"
    # → 注意：suggestion 是基于错误类型的经验规则，不是 LLM 生成的
    
    # === 元数据 ===
    metadata: dict = field(default_factory=dict)
    # → 包含：
    #   duration_ms: 执行耗时
    #   tokens_produced: 结果 token 数
    #   truncated: 结果是否被截断
    #   original_size: 截断前的大小
    #   retry_count: 这是第几次重试
    #   tool_version: 工具的版本号
```

### 3.2 各种场景的返回示例

```python
# === 场景 1: 成功 ===
ToolResult(
    success=True,
    data="class UserService:\n    def get_username(self):\n        ...",
    metadata={"duration_ms": 120, "tokens_produced": 45}
)

# === 场景 2: 文件不存在 ===
ToolResult(
    success=False,
    error_type="not_found",
    error_message="文件 src/services/UserService.java 不存在",
    suggestion="当前工作目录为 /home/user/project。请检查路径是否正确，"
               "或使用 Glob('**/UserService*') 搜索文件位置。",
    metadata={"duration_ms": 5}
)

# === 场景 3: 命令执行超时 ===
ToolResult(
    success=False,
    error_type="timeout",
    error_message="命令 'npm install' 执行超时（>60s）",
    suggestion="可能是网络问题或依赖过多。请尝试:"
               "1) 检查网络连接"
               "2) 使用 --prefer-offline 参数"
               "3) 单独安装问题依赖",
    metadata={"duration_ms": 60000, "retry_count": 1}
)

# === 场景 4: 用户拒绝审批 ===
ToolResult(
    success=False,
    error_type="user_denied",
    error_message="用户拒绝了 'git push --force origin main' 操作",
    suggestion="force push 被拒绝是正常的保护行为。请使用非 force 的 push 方式，"
               "或先与用户沟通为什么需要 force push。",
    metadata={"duration_ms": 15000}  # 用户思考了 15 秒
)

# === 场景 5: API 限流 ===
ToolResult(
    success=False,
    error_type="rate_limited",
    error_message="API 返回 429 Too Many Requests",
    suggestion="请等待 30 秒后重试。如果持续限流，请减少请求频率。",
    metadata={"duration_ms": 200, "retry_after_seconds": 30}
)

# === 场景 6: 结果截断 ===
ToolResult(
    success=True,
    data="[前 5000 字符] ... [截断]",
    error_type=None,
    suggestion=None,
    metadata={
        "duration_ms": 50, 
        "truncated": True, 
        "original_size": 50000,
        "truncated_to": 5000
    }
)
```

## 四、错误分类与恢复策略映射

```
错误类型 → Agent 恢复策略


TIMEOUT
  → 第 1 次: 等 5 秒 → 重试
  → 第 2 次: 减少数据量，分段执行
  → 第 3 次: 报告用户，建议替代方案

PERMISSION_DENIED / USER_DENIED
  → 不可重试
  → 探寻替代方案（换个目录、换个方式）
  → 如果无可替代 → 报告用户解决权限问题

NOT_FOUND
  → 检查路径/名称拼写
  → 搜索文件位置 (Glob)
  → 确认资源是否真的应该存在

RATE_LIMITED
  → 等待重试（指数退避: 1s → 2s → 4s → 8s）
  → 减少请求并行度
  → 合并请求减少总次数

INVALID_ARGUMENTS
  → 检查参数的格式、类型、范围
  → 查看工具的 schema 要求
  → 修正后重试

EXECUTION_FAILED
  → 分析失败原因（从 output 中提取）
  → 修正代码/命令
  → 重试

UNKNOWN
  → 尝试一次重试（有时候是瞬时故障）
  → 如果仍然失败 → 报告用户 + 提供完整 traceback
```

## 五、与权限闸的集成

### 5.1 权限分级

```python
class PermissionLevel(Enum):
    """操作的危险级别"""
    SAFE = 1       # 只读操作，无副作用
    MODIFY = 2     # 修改文件，可通过 git revert
    NETWORK = 3    # 网络请求，可能泄露数据
    DESTRUCTIVE = 4  # 不可逆操作（删除、force push）
    SYSTEM = 5     # 修改系统配置

class PermissionGate:
    """工具编排的前置权限检查"""
    
    # 操作 → 权限级别 映射
    PERMISSIONS = {
        "read": PermissionLevel.SAFE,
        "glob": PermissionLevel.SAFE,
        "grep": PermissionLevel.SAFE,
        "edit": PermissionLevel.MODIFY,
        "write": PermissionLevel.MODIFY,
        "bash_git_status": PermissionLevel.SAFE,
        "bash_git_diff": PermissionLevel.SAFE,
        "bash_git_commit": PermissionLevel.MODIFY,
        "bash_git_push": PermissionLevel.DESTRUCTIVE,
        "bash_general": PermissionLevel.MODIFY,  # 普通 shell 命令
        "bash_destructive": PermissionLevel.DESTRUCTIVE,  # rm, chmod 等
        "webfetch": PermissionLevel.NETWORK,
        "delete_file": PermissionLevel.DESTRUCTIVE,
    }
    
    # 权限级别 → 处理方式
    POLICIES = {
        PermissionLevel.SAFE: "auto",           # 自动执行
        PermissionLevel.MODIFY: "auto_or_ask",  # 可配置
        PermissionLevel.NETWORK: "ask",         # 每次询问
        PermissionLevel.DESTRUCTIVE: "ask",     # 每次询问（需要明确确认）
        PermissionLevel.SYSTEM: "deny",         # 默认禁止
    }
    
    def check(self, tool_name: str, args: dict) -> PermissionResult:
        level = self.PERMISSIONS.get(tool_name, PermissionLevel.MODIFY)
        policy = self.POLICIES[level]
        
        if policy == "auto":
            return PermissionResult(allowed=True)
        
        if policy == "deny":
            return PermissionResult(
                allowed=False,
                reason=f"操作 {tool_name} 被策略禁止 (level={level})"
            )
        
        if policy == "auto_or_ask":
            if user_has_preapproved(tool_name, args):
                return PermissionResult(allowed=True)
            else:
                return PermissionResult(
                    allowed=False,
                    requires_approval=True,
                    prompt=f"Agent 想要执行: {tool_name}({args})"
                           f"\n危险级别: {level.name}"
                           f"\n是否允许?"
                )
        
        if policy == "ask":
            return PermissionResult(
                allowed=False,
                requires_approval=True,
                prompt=f"⚠️ 危险操作 (级别:{level.name}): "
                       f"{tool_name}({args})\n确认执行?"
            )
```

### 5.2 用户审批的交互模式

```
审批粒度选项：
  1. 每次审批 (Once): 只允许这一次调用
  2. 会话审批 (Session): 这个 session 内同类操作自动允许
  3. 模式审批 (Pattern): 匹配特定模式的操作允许（如 "编辑 tests/ 目录下的文件"）
  4. 项目审批 (Project): 通过 CLAUDE.md 配置，永久允许/禁止特定操作
```

## 六、工具 Schema 设计原则

### 6.1 好的工具 Schema

```python
# ✅ 好的 Schema：清晰、具体、有约束

{
    "name": "search_code",
    "description": "在代码库中搜索匹配正则表达式的代码行。"
                   "用于查找函数定义、变量引用、错误信息等。"
                   "注意：这会在所有文件中搜索，结果可能很多。",
    "parameters": {
        "type": "object",
        "properties": {
            "pattern": {
                "type": "string",
                "description": "正则表达式模式。示例: 'def get_user', 'import.*from'"
            },
            "path": {
                "type": "string",
                "description": "搜索的目录路径。默认: 项目根目录。"
                               "指定子目录可以缩小范围提高速度。"
            },
            "file_types": {
                "type": "string",
                "description": "限定文件类型，用逗号分隔。示例: '.py,.js'。留空则搜索所有文件。"
            },
            "max_results": {
                "type": "integer",
                "default": 50,
                "minimum": 1,
                "maximum": 200,
                "description": "最大返回结果数。默认 50，最多 200。超过此数的结果会被截断。"
            }
        },
        "required": ["pattern"]
    }
}
```

### 6.2 坏的工具 Schema

```python
# ❌ 坏的 Schema：模糊、无约束、缺少关键信息

{
    "name": "run",
    "description": "Run something",  # ← 太模糊
    "parameters": {
        "type": "object",
        "properties": {
            "cmd": {
                "type": "string"      # ← 没有描述、没有示例、没有约束
            }
        },
        "required": ["cmd"]
    }
}
```

### 6.3 Schema 设计清单

```
✅ description 要说清楚工具能做什么、不能做什么
✅ 每个参数有清晰的描述和示例
✅ 尽量使用 enum 约束参数值，减少 LLM 犯错空间
✅ 设置合理的 minimum/maximum 约束
✅ 标注默认值
✅ 在 description 中提示注意事项（"结果可能很多"、"只搜索 index 过的文件"）
```

## 七、与其他机制的协作

| 协作机制 | 协作关系 |
|---------|---------|
| **权限闸** | 工具编排在执行前调用权限闸 |
| **验证循环** | 工具编排保证"调用不崩溃"（工程层），验证循环保证"结果正确"（任务层） |
| **四相循环** | 四相循环的 ACT 阶段通过工具编排执行所有工具调用 |
| **上下文工程** | 工具编排返回的 metadata.tokens_produced 被上下文工程用来追踪 token 消耗 |

## 八、总结

工具编排是 Agent 与外部世界交互的**安全接口**。它的核心原则：

1. **永不吃掉错误**：成功和失败都返回结构化的完整信息
2. **分类错误 → 分类恢复**：不同错误类型对应不同的自动恢复策略
3. **永远给 Agent 一条出路**：suggestion 字段让 Agent 不必在黑暗中摸索
4. **前置权限检查**：在炸弹引爆前就拆除引信
