## 1. 问题定义：Tool 错误吞并与缺权限闸的根源

### 1.1 什么是 Tool 错误吞并

**Tool 错误吞并（Tool Error Swallowing）** 是指 Agent 调用外部工具时，工具执行过程中发生的异常（超时、权限不足、网络中断、返回数据异常等）被不透明地吞掉——Agent 收到的不是一个结构化的错误描述，而是一个空字符串、一个 `null`、或一条含糊的"出了点问题"——导致 Agent 基于错误信息做出错误决策，进而进入**幻觉螺旋（Hallucination Spiral）**。

Naive 做法的典型代码：

```python
try:
    result = execute_tool(name, args)
except Exception:
    result = ""  # ← 错误被吞并。Agent 不知道发生了什么。
```

这一行 `result = ""` 是整个失效链的起点。考虑以下因果链：

```
工具调用超时
  → Agent 收到: ""（空字符串）
  → Agent 推断: "操作成功了，只是没有输出"
  → Agent 继续基于"操作已成功"的错误假设工作
  → 后续操作依赖于一个不存在的中间产物
  → 更多工具调用失败
  → 更多错误被吞并
  → Agent 陷入幻觉螺旋：它"相信"自己正在取得进展，实际上每一步都在累积错误
```

**关键洞察**：问题不在于工具会失败——工具失败是分布式系统的常态。问题在于**失败信息未能以 Agent 可理解、可行动的方式传递给它**。当 Agent 无法区分"成功但无输出"和"失败"时，它的推理基础就是不可靠的。

### 1.2 什么是缺权限闸

**缺权限闸（Missing Permission Gate）** 是指 Agent 在执行工具时，缺少一个统一的、分层的、前置的权限检查机制。危险操作（如删除文件、发送邮件、执行 shell 命令、force push）可以在没有任何拦截的情况下被执行。

这本质上是**控制流（Control Flow）设计的缺失**——Agent 的行为边界没有被明确地定义和强制。没有权限闸的 Agent 就像一个拥有 root 权限但不受监管的脚本：它可能因为一个错误决策造成不可逆的破坏。

### 1.3 两类失效的共同根源

Tool 错误吞并和缺权限闸共享同一个结构性问题：**Agent 推理层和工具执行层之间缺少一个可靠的中间层**。

```
Naive 架构:
  Agent (LLM) ────直接调用────> 外部工具
                  ↑
            没有任何中间层
            - 无错误结构化
            - 无权限检查
            - 无超时控制
            - 无重试策略
            - 无可观测性

Harness 架构:
  Agent (LLM) ──> 工具编排层 ──> 外部工具
                  ├── 参数校验 (JSON Schema)
                  ├── 权限前置检查 (Permission Gate)
                  ├── 超时控制 (Timeout Controller)
                  ├── 重试策略 (Retry Policy)
                  ├── 熔断保护 (Circuit Breaker)
                  ├── 结果格式化 (ToolResult Schema)
                  └── 可观测性 (Tracing + Metrics)
```

工具编排层的核心设计原则是：**它是 Agent 与外部世界之间的唯一通道**。没有旁路，没有直接调用。每一次工具交互都经过编排层的完整处理管线。这保证了：

1. **错误不再被吞并**——每个工具调用都返回结构化的 `ToolResult`，包含 `success`、`error_type`、`error_message`、`suggestion`
2. **权限不再有漏网之鱼**——每次调用前都经过统一的权限闸检查
3. **所有调用可审计**——每次调用都有 trace_id、结构化日志、耗时、重试次数

## 2. 架构定位：Agent 与外部世界的唯一受控通道

### 2.1 工具调用的生命周期

工具编排不是简单地"调用工具"。它是一个完整的**工具调用生命周期管理系统**，涵盖七个阶段：

```
  1. 发现 (Discover)     → 从注册表中按语义匹配候选工具
  2. 绑定 (Bind)         → 将 LLM 输出的参数名映射到工具的实际参数
  3. 校验 (Validate)     → JSON Schema 校验参数合法性；权限前置检查
  4. 调度 (Schedule)     → 根据 DAG 依赖关系确定执行顺序和并发度
  5. 执行 (Execute)      → 实际调用工具（本地函数 / HTTP API / 子代理）
  6. 恢复 (Recover)      → 超时重试、降级切换、熔断保护
  7. 聚合 (Aggregate)    → 结果裁剪、格式化、合并，注入回 Agent 上下文
```

**一句话定义**：工具编排是 Agent 的"API Gateway + 消息队列 + 断路器"的组合体——在 Agent 推理层和外部世界之间建立了**唯一、受控、可观测的通道**。

### 2.2 在四相循环中的位置

工具编排是四相循环中 Phase 3（执行编排）的执行引擎。它的职责边界是精确的：

```
四相循环                        工具编排的参与
────────                      ──────────────
Phase 1: 感知装配             无直接参与（工具注册表的元数据影响上下文裁剪）
Phase 2: 规划决策             工具注册表提供候选工具列表 + 参数 Schema
                              → LLM 据此生成 ExecutionPlan (DAG)
Phase 3: 执行编排  ←────────  ★ 工具编排的核心发生地
                              → 接收 ExecutionPlan，按 DAG 调度执行
                              → 每次调用经过：校验→权限→执行→重试→聚合
Phase 4: 验证修正             工具编排返回的 ToolResult 是 Phase 4 的验证输入
                              → 结构化错误信息使验证环能精准诊断
```

**关键设计原则**：工具编排不参与"决定调用什么工具"（Phase 2 的职责），也不参与"判断工具结果是否正确"（Phase 4 的职责）。它只负责**可靠地执行已经决定好的调用**。这种职责分离是 Harness 系统可维护性的基础——每个模块可以独立演进和测试。

### 2.3 为什么需要独立的编排层

将工具调用的横切关注点（错误处理、重试、超时、权限、日志）从 Agent 推理逻辑中分离出来，不是一个架构审美偏好，而是一个**工程必要性**问题。

| 维度 | 硬编码调用 (`execute_tool(name, args)`) | 声明式编排引擎 |
|------|:---:|:---:|
| **可扩展性** | 新增工具 = 修改 Agent 代码 | 注册即可，编排器自动发现 |
| **可观测性** | 无统一 trace，日志散落各处 | 统一 trace_id，每次调用的入参/出参/耗时/错误全量记录 |
| **并行能力** | 需手写 `asyncio.gather`，易出错 | 声明式 DAG → 编排器自动计算最大并行度 |
| **容错能力** | 每个工具调用处手写 try/except/retry | 编排器统一重试策略、熔断、降级 |
| **权限管控** | 散落在各处，容易遗漏 | 编排器统一前置检查，无死角 |
| **单测友好** | Mock 散落在 Agent 代码各处 | 编排器可独立测试（注入 Mock ToolRegistry） |

**量化对比**（内部基准，100 个多工具调用任务）：

- 硬编码方式：平均代码量 **340 行**（工具调用逻辑散落在 Agent 循环中），bug 密度 **1.8/KLOC**
- 编排引擎方式：平均代码量 **85 行**（只定义工具 + 注册），bug 密度 **0.3/KLOC**

**大厂实践参考**：

| 产品 / 平台 | 编排方式 | 核心特点 |
|------------|---------|---------|
| **OpenAI Assistant API** | Function Calling + `parallel_tool_calls` | 单一 `run` 内多条 tool_calls 自动并行；并发上限由 API 层控制 |
| **LangGraph ToolNode** | `ToolNode` + 条件边 | 工具调用映射为图的节点，并行执行靠 `Send` API 分发 |
| **字节 Coze 插件编排** | 可视化 DAG + 插件市场 | 串行/并行/条件分支可在画布上拖拽编排；每个插件自带 parameter schema 和错误映射 |
| **Anthropic Claude Code** | `tool_use` + 结构化 `ToolResult` | 每次工具调用必须返回带 `is_error` 标记的结果；失败时携带 `suggestion` 字段指导 Agent 恢复 |
| **Temporal / Argo Workflows** | 持久化编排 (Durable Execution) | 编排状态持久化到数据库；编排器 crash 后可精确恢复未完成的工具调用——是生产级 Harness 的理想底层 |

## 3. 核心概念与抽象

### 3.1 工具定义 (Tool)

工具是 Harness 系统中的一等公民。一个完整的工具定义不仅描述"这个工具做什么"，还声明了它的**执行策略、安全约束、资源限制和降级路径**。这些元数据是编排器做出调度决策的基础。

```python
from dataclasses import dataclass, field
from typing import Any, Callable, Optional, Literal
from enum import Enum


class ToolCategory(Enum):
    """工具分类——影响编排器的调度策略"""
    READ = "read"           # 只读（可高度并行，无需权限审批）
    WRITE = "write"         # 写入文件/数据库（需版本控制检查）
    NETWORK = "network"     # 网络请求（需超时控制 + 速率限制）
    COMPUTE = "compute"     # 计算密集型（需资源隔离）
    SUBAGENT = "subagent"   # 子代理调用（递归编排）


class RiskLevel(Enum):
    """风险等级——影响权限闸行为"""
    SAFE = 1                # 自动执行（如 read_file）
    MODIFY = 2              # 可逆修改（如 edit_file，可通过 git revert）
    SENSITIVE = 3           # 敏感操作（如发送邮件、网络请求）
    DESTRUCTIVE = 4         # 不可逆操作（如 rm、DROP TABLE）


@dataclass
class Tool:
    """工具的完整定义"""

    # ── 身份与元数据 ──
    name: str                               # 唯一标识
    description: str                        # 人类可读 + LLM 可理解的描述
    category: ToolCategory

    # ── 接口定义 ──
    parameters_schema: dict                 # JSON Schema (Draft 2020-12)
    executor: Callable[..., Any]            # 实际执行函数
    executor_type: Literal["local", "http", "subagent"] = "local"

    # ── 执行策略 ──
    timeout_ms: int = 30_000                # 单次调用超时（默认 30s）
    max_retries: int = 2                    # 最大重试次数（含首次 = 最多 3 次）
    retry_strategy: str = "exponential_backoff"
    retryable_errors: tuple[type, ...] = (TimeoutError, ConnectionError)
    base_delay_ms: int = 1000
    max_delay_ms: int = 32_000

    # ── 安全与权限 ──
    risk_level: RiskLevel = RiskLevel.SAFE
    requires_approval: bool = False
    approval_prompt_template: Optional[str] = None

    # ── 资源控制 ──
    rate_limit: Optional["RateLimit"] = None
    max_concurrent_calls: int = 5
    max_output_tokens: int = 50_000

    # ── 幂等性 ──
    idempotent: bool = False
    idempotency_key_param: Optional[str] = None

    # ── 降级链 ──
    fallback_tool: Optional[str] = None
    fallback_args_mapping: Optional[dict] = None

    # ── 版本与生命周期 ──
    version: str = "1.0.0"
    deprecated: bool = False
```

**设计要点**：

- `category` 不只是分类标签——它直接决定超时默认值、并发策略和权限闸行为。例如 `NETWORK` 类工具自动应用 30s 超时和速率限制。
- `retryable_errors` 显式声明哪些异常可重试。`ValueError`（参数错误）不可重试——重试不会改变结果。`TimeoutError` 可重试——网络抖动是暂时的。
- `idempotent` / `idempotency_key_param` 是生产级工具定义中常被忽视的关键字段。没有它，编排器在超时重试时无法判断是否会导致副作用重复。
- `fallback_tool` 定义了工具的降级路径，使编排器在主工具不可用时能自动切换备用方案，而非简单失败。

### 3.2 工具结果 (ToolResult)

`ToolResult` 是工具编排层与 Agent 推理层之间的**接口契约**。它的设计决定了 Agent 能否正确理解工具调用的结果。

```python
@dataclass
class ToolResult:
    success: bool                    # 成功/失败——Agent 的第一眼判断
    data: Any = None                 # 成功时的数据载荷
    error_type: str = ""             # 失败时的错误分类：TIMEOUT | PERMISSION_DENIED | VALIDATION_ERROR | ...
    error_message: str = ""          # 人类可读的错误描述
    error_traceback: str = ""        # 技术细节（截断版）
    suggestion: str = ""             # 给 Agent 的恢复建议："你接下来应该怎么做"
    metadata: dict = field(default_factory=dict)  # 耗时、tokens、版本、trace_id 等
```

**为什么 `suggestion` 字段是关键设计？**

Naive 做法中，Agent 收到错误后需要自己推断如何恢复——这依赖于 LLM 的推理能力，而 LLM 在缺乏工具内部知识的情况下容易做出错误的恢复决策。`suggestion` 字段将工具开发者的领域知识注入到错误信息中：工具开发者比 LLM 更清楚"这个工具失败时，怎样做最可能成功"。

**对比示例**：

```
Naive (错误被吞):
  tool_result = ""
  → Agent: "结果是空的，说明操作成功了只是没输出"
  → Agent 继续基于错误假设工作 ← 幻觉螺旋

Orchestrated (错误被结构化):
  tool_result = {
    "success": false,
    "error_type": "TIMEOUT",
    "error_message": "工具 read_large_file 执行超时（>30s）",
    "suggestion": "请尝试使用 offset 和 limit 参数分段读取文件"
  }
  → Agent: "操作失败了，因为超时。建议用分段方式读取"
  → Agent 调整策略：用 offset/limit 分 3 次读取 ← 正确恢复
```

### 3.3 工具注册表 (ToolRegistry)

工具注册表是工具元数据的**单一事实来源（Single Source of Truth）**。它的核心能力不是简单的 key-value 存取，而是**语义搜索**——根据当前任务描述，从数十个工具中筛选出最相关的 2-5 个候选。

**为什么语义搜索重要？** 如果将所有工具（可能 50+ 个）的完整 Schema 都塞入 LLM 上下文，会造成两个问题：(a) token 浪费——每个工具的 Schema 可能占用数百 tokens；(b) 选择质量下降——LLM 在过多候选中做选择时错误率显著上升（内部数据：5 选 1 准确率 94%，10 选 1 降到 82%）。

```python
class ToolRegistry:
    """
    设计原则：
      1. 注册与调度分离——注册表只负责存储和查询，不负责执行
      2. 支持静态注册（启动时加载）和动态注册（运行时通过 MCP 发现）
      3. 语义搜索：根据任务描述找到最匹配的工具
    """

    def __init__(self):
        self._tools: dict[str, Tool] = {}
        self._embedding_index = None  # 语义搜索索引

    def register(self, tool: Tool) -> None:
        """静态注册：启动时加载所有已知工具"""
        if tool.name in self._tools:
            raise ToolConflictError(
                f"工具 '{tool.name}' 已注册，版本: {self._tools[tool.name].version}"
            )
        self._tools[tool.name] = tool

    def register_dynamic(self, tool: Tool, ttl_seconds: int = 3600) -> None:
        """动态注册（如通过 MCP 协议发现的新工具），带 TTL 自动过期"""
        self._tools[tool.name] = tool
        self._schedule_eviction(tool.name, ttl_seconds)

    def filter_by_task(
        self,
        task_description: str,
        category: Optional[ToolCategory] = None,
        max_results: int = 5,
    ) -> list[Tool]:
        """
        语义搜索：根据任务描述返回最相关的 top-N 工具。
        用于 Phase 2 中减少 LLM 的选择空间。

        实现策略：
          1. 先用 category 硬过滤（如果指定）
          2. 再用 embedding cosine similarity 排序
          3. 截取 top-N
        """
        candidates = [
            t for t in self._tools.values()
            if not t.deprecated and (category is None or t.category == category)
        ]
        if self._embedding_index:
            query_embedding = self._embed(task_description)
            scored = [
                (t, cosine_similarity(query_embedding, self._get_embedding(t)))
                for t in candidates
            ]
            scored.sort(key=lambda x: x[1], reverse=True)
            return [t for t, score in scored[:max_results]]
        else:
            # 降级：关键词匹配
            return candidates[:max_results]
```

**搜索策略的量化权衡**：

| 策略 | 召回率 | 延迟 | 适用场景 |
|------|:---:|:---:|---------|
| 全量返回 | 100% | 0ms | 工具 < 20 个 |
| 关键词匹配 | ~70% | 1ms | 工具 20-100 个 |
| Embedding 相似度 | ~90% | 50ms | 工具 100-1000 个 |
| 混合 (Keyword + Embedding) | ~95% | 60ms | 生产推荐 |

### 3.4 执行计划 (ExecutionPlan)

`ExecutionPlan` 是 Phase 2（规划决策）与 Phase 3（执行编排）之间的**接口契约**。它是一个结构化的 DAG 描述——不是自然语言计划，而是编排器能直接执行的节点列表和依赖关系。

```python
@dataclass
class ToolNode:
    """DAG 中的一个节点 = 一次工具调用"""
    node_id: str                          # 唯一节点 ID
    tool_name: str                        # 工具名
    arguments: dict[str, Any]             # 绑定后的参数
    depends_on: list[str] = field(default_factory=list)  # 依赖的 node_id 列表
    timeout_override_ms: Optional[int] = None
    skip_on_failure: bool = False         # 依赖节点失败时是否跳过而非中止
    condition: Optional[str] = None       # 条件执行表达式（如 "result.count > 0"）


@dataclass
class ExecutionPlan:
    plan_id: str
    nodes: list[ToolNode]
    strategy: Literal["sequential", "parallel", "dag"] = "dag"
    global_timeout_ms: int = 300_000      # 整个 plan 的超时
    max_parallelism: int = 5              # 全局最大并发数
    on_global_failure: Literal["abort", "continue", "fallback"] = "abort"
```

**关键设计决策**：`ExecutionPlan` 不包含"如何执行"的指令（重试几次、超时多久）——这些信息已经定义在 `Tool` 的元数据中。编排器从 `Tool` 元数据中读取执行策略，而非从 Plan 中。这保证了**执行策略的一致性**：无论 Plan 从何而来（LLM 生成、缓存复用、人工编写），同一个工具总是以同样的策略被执行。

## 4. 编排模式与调度策略

编排模式的选择取决于工具调用间的**依赖关系**。正确的模式选择直接影响执行效率——选错模式的代价可能是数倍的执行时间增加。

### 4.1 串行编排

**适用场景**：后一个工具的输入严格依赖前一个工具的输出。例如：读文件 → 解析内容 → 修改 → 写回。

**优点**：实现简单，调试容易（线性 trace，每一步的因果关系清晰）。**局限**：性能低下，不能利用并行加速。

```
串行编排 (Sequential):
  [A] ──→ [B] ──→ [C] ──→ [D]
   0s      1s      2s      3s    总耗时 = sum(各步耗时)
```

核心实现要点是**前序结果的上下文注入**：后续节点的参数中允许使用 `${node_id.result.field}` 占位符引用前序节点的输出，编排器在执行前自动解析。

### 4.2 并行编排

**适用场景**：多个工具调用之间无依赖关系。例如：同时查询两个独立 API、并行搜索多个代码库。

**核心问题**：不加限制的并行是危险的。给 20 个独立工具不加限制地并发调用 (`asyncio.gather(*all_tools)`)，下游 API 收到 20 个并发请求 → 触发 429 Rate Limit → 全部失败。更糟的情况是：某代码分析 Agent 并行调用 30 个 `grep` 命令，瞬间 fork 30 个子进程，导致开发机 OOM。

```
并行编排 (Parallel):
  [A] ──┐
  [B] ──┤                        总耗时取决于信号量
  [C] ──┤──>  Semaphore(5)       = max(各步耗时)
  [D] ──┤     (同一时刻最多 5 个)
  [E] ──┘
```

**量化建议**：默认并发数 = 5（适配大多数 API 的速率限制默认值），最大并发数 = 10（需要用户显式确认）。

```python
class ParallelExecutor:
    def __init__(self, max_concurrency: int = 5):
        self.semaphore = asyncio.Semaphore(max_concurrency)

    async def execute(
        self,
        nodes: list[ToolNode],
        orchestrator: "Orchestrator",
    ) -> dict[str, ExecutionUnit]:
        async def _execute_with_semaphore(node: ToolNode):
            async with self.semaphore:
                return await orchestrator.execute_single(node, node.arguments)

        tasks = [_execute_with_semaphore(node) for node in nodes]
        await asyncio.gather(*tasks, return_exceptions=True)
        return self._results
```

### 4.3 DAG 编排

**适用场景**：复杂依赖关系——A 和 B 可并行，两者都完成后才触发 C；C 和 D 可并行，两者都完成后才触发 E。

**这是工具编排中最核心的调度模式。** DAG 调度器基于拓扑排序 + 就绪队列实现，核心算法如下：

```
算法：基于拓扑排序的 DAG 调度

输入: plan.nodes (所有节点，含 depends_on 依赖关系)
输出: results (每个节点的执行结果)

1. 计算每个节点的入度（依赖计数）: in_degree[node] = len(node.depends_on)
2. 构建下游索引: downstream[A] = [B, C] 表示 A 完成时需要通知 B 和 C
3. 入度为 0 的节点进入「就绪队列」
4. while 就绪队列非空:
   a. 从队列取节点（受 Semaphore 并发限制）
   b. 并行执行该节点
   c. 节点完成后，遍历 downstream[node]:
      - 将下游节点的入度减 1
      - 若入度减到 0 且上游全部成功 → 下游节点入队
   d. 若上游有失败且下游节点未设置 skip_on_failure → 跳过该下游节点
5. 输出所有结果

时间复杂度: O(V + E)，空间复杂度: O(V)
```

**DAG 示例——天气查询任务**：

```
DAG 结构:
  [weather_beijing] ──┐
                      ├──> [calc_diff]
  [weather_shanghai] ─┘

调度过程:
  T0:   入度=0 的节点入队 → [weather_beijing, weather_shanghai]
  T0:   两个节点并发执行（受 Semaphore 限制）
  T1s:  weather_beijing 完成 → downstream 中 calc_diff 入度-1 (now 1)
  T1.2s: weather_shanghai 完成 → calc_diff 入度-1 (now 0) → calc_diff 入队
  T1.2s: calc_diff 开始执行（参数中 ${weather_beijing.result.temperature} 已解析为实际温度）
  T1.3s: calc_diff 完成 → 全部节点完成
```

### 4.4 条件分支与 Map 原语

编排器需要处理 Phase 2 输出的控制流原语。这不是 LLM 推理时的分支——而是**编排器根据工具返回结果进行的确定性分支**。

**条件分支**：执行工具 A → 根据 A 返回的结果选择执行 B 序列或 C 序列。条件表达式（如 `result.count > 0`）在编排器层面求值，不依赖 LLM 推理。

**Map 原语**：对列表中的每个元素执行相同的工具。例如，grep 发现 20 个引用 → 对每个引用位置调用 `read_file` 获取上下文。Map 执行时受并发限制，不会一次性启动所有调用。

这两种原语的价值在于：它们让编排器能处理**动态执行图**——不是所有工具调用都在 Plan 生成时就确定，有些取决于中间结果。

### 4.5 降级编排

降级编排（Fallback Orchestration）使编排器在主工具不可用时自动切换到备用方案。这需要在工具定义时声明降级路径：

```python
# 工具定义时声明降级链
Tool(
    name="search_attractions",
    fallback_tool="get_recommended_attractions",
    fallback_args_mapping={"city": "location", "date": "date"},
    ...
)
```

编排器的降级逻辑：尝试主工具 → 主工具失败 → 检查 `tool.fallback_tool` → 若存在，映射参数并调用备用工具 → 在结果的 `metadata` 中记录 `fallback_from`。这保证 Agent 能看到"这个结果是降级工具产生的"，从而在后续推理中考虑这一信息。

### 4.6 聚合编排

聚合编排（Aggregate Orchestration）对应 Map-Reduce 模式：并行执行多个工具 → 收集所有结果 → 调用一个聚合工具将结果合并为单一输出。典型场景：并行搜索多个数据源 → 合并去重排序 → 返回统一结果集。

```
聚合编排 (Aggregate):
  [search_web] ──┐
  [search_docs] ─┼──> [merge_and_rank] ──> 统一搜索结果
  [search_code] ─┘
```

## 5. 健壮性与容错

编排层的核心价值之一是**统一提供健壮性保证**，而非由每个工具调用方自行处理。以下五个机制构成了编排层的容错体系。

### 5.1 超时控制

**设计原则**：双层超时——单次工具调用超时 + 整体 ExecutionPlan 超时。两个层级独立触发，互不依赖。

**量化建议（按工具类型）**：

| 工具类型 | 默认超时 | 理由 |
|---------|:---:|------|
| READ (读文件) | 10s | 文件系统操作通常在 100ms 内完成；10s 已覆盖极端情况 |
| WRITE (写文件) | 30s | 写入大文件和 git 操作可能较慢 |
| NETWORK (HTTP API) | 30s | 覆盖 P99 延迟 + 2 次重试 |
| COMPUTE (计算) | 120s | 计算密集型可能耗时较长 |
| SUBAGENT (子代理) | 300s | 子代理有自己的内部超时 |

超时处理不是简单抛异常。编排器的超时处理返回一个**结构化的超时结果**，携带给 Agent 的操作建议：

```python
# 超时时返回的 ToolResult
ToolResult(
    success=False,
    error_type="timeout",
    error_message=f"工具 '{tool.name}' 在 {timeout_ms}ms 内未响应",
    suggestion="建议: 1) 减少数据量 2) 检查网络连接 3) 尝试分段调用",
)
```

### 5.2 重试机制

**设计原则**：指数退避 + 随机抖动 + 错误分类。不是所有错误都值得重试。

**错误分类决策**：

| 错误类型 | 是否重试 | 原因 |
|---------|:---:|------|
| TimeoutError | ✅ 重试 | 网络抖动是暂时的 |
| ConnectionError | ✅ 重试 | 连接池耗尽可能是瞬时的 |
| 5xx HTTP | ✅ 重试 | 服务端临时故障 |
| RateLimitError (429) | ✅ 重试 | 等待配额恢复后可成功 |
| 4xx HTTP (参数错误) | ❌ 不可重试 | 参数错误不会因重试而消失 |
| PermissionError | ❌ 不可重试 | 权限不会因重试而获取 |
| ValidationError | ❌ 不可重试 | Schema 校验失败是确定性的 |

**量化参数**：

| 参数 | 值 | 说明 |
|------|:---:|------|
| base_delay | 1s | 初始退避 |
| max_delay | 32s | 退避上限（防止等待过久） |
| multiplier | 2 | 指数因子（1s → 2s → 4s → 8s → 16s → 32s 封顶） |
| jitter | ±25% | 随机抖动（防止惊群效应——多个重试同时到达服务端） |
| max_retries | 2 | 含首次 = 最多 3 次尝试 |

### 5.3 幂等性保证

**问题**：`send_email` 工具超时后编排器重试，用户收到两封相同的邮件。`create_transfer` 工具超时重试，创建了两笔相同的转账。

**根因**：编排器只负责可靠地调用工具，它无法知道工具的副作用是什么。因此幂等性必须由编排器和工具配合保证：工具声明幂等键参数，编排器基于幂等键缓存调用结果。

```python
class IdempotencyGuard:
    """
    幂等性守卫——防止重试导致副作用重复。

    工作流：
      1. 客户端传入 idempotency_key（如 UUID）
      2. 编排器在执行前检查缓存：key 是否已成功执行过
      3. 如果是 → 直接返回缓存结果（不再次执行工具）
      4. 如果否 → 执行并缓存结果（TTL: 24h，只缓存成功的调用）

    存储后端：Redis（分布式）或本地 dict（单机）
    """

    async def execute_idempotent(
        self, tool: Tool, arguments: dict,
        idempotency_key: str, execute_fn: Callable,
    ) -> ToolResult:
        cache_key = f"idempotent:{tool.name}:{idempotency_key}"
        cached = await self.storage.get(cache_key)
        if cached:
            return ToolResult.from_json(cached)
        result = await execute_fn()
        if result.success:
            await self.storage.set(cache_key, result.to_json(), ttl=86400)
        return result
```

### 5.4 熔断与限流

**熔断器（Circuit Breaker）** 是编排层的最后一道防线。当某个工具的失败率超过阈值时，自动熔断不再调用——防止级联失败。

```
熔断器三态流转:

  CLOSED (正常) ──失败率 ≥ 50%──> OPEN (熔断)
                                      │
                                      │ 30s 后
                                      ▼
                                 HALF_OPEN (探测)
                                   │       │
                            探测成功│       │探测失败
                                   ▼       ▼
                                 CLOSED   OPEN
```

**量化参数**：

| 参数 | 值 | 说明 |
|------|:---:|------|
| 失败阈值 | 50% | 滑动窗口内失败率超过此值 → 熔断 |
| 窗口大小 | 60s | 滑动窗口长度 |
| 最小调用次数 | 10 | 窗口内至少 10 次调用才计算失败率（防止小样本误判） |
| 熔断时长 | 30s | 熔断多久后允许一次探测调用 |
| 半开最大探测 | 1 次 | 同一时刻只允许 1 个探测调用 |

**令牌桶限流器（Rate Limiter）** 防止对同一工具的调用频率超过下游承载能力：

| 工具类别 | 建议速率 | 理由 |
|---------|:---:|------|
| READ | 100 req/s | 文件系统 I/O 通常不是瓶颈 |
| HTTP API (免费) | 10 req/s | 大多数免费/低配额 API |
| HTTP API (付费) | 60 req/s | 如 OpenAI API Tier 3 |

## 6. 可观测性设计

可观测性不是事后添加的"打印日志"，而是工具编排的**一等设计约束**。每次工具调用都产生一条统一格式的 trace 记录：

```python
class ToolCallTracer:
    """
    为每次工具调用生成统一 trace，与 OpenTelemetry 集成。

    每条 trace 必须包含:
      - trace_id + span_id（符合 W3C Trace Context）
      - tool_name, tool_version
      - arguments（脱敏后——移除 API Key、密码等敏感字段）
      - result_summary（截断到 500 chars——防止 trace 自身成为存储负担）
      - duration_ms, token_count
      - error_type + error_message（如果失败）
      - retry_count（含首次 = 第几次尝试成功的）
      - parent_span_id（如果该调用是 DAG 的一部分）
    """
```

**核心指标**：

| 指标名 | 类型 | 描述 |
|-------|------|------|
| `orchestrator.call.total` | Counter | 工具调用总次数 |
| `orchestrator.call.duration_ms` | Histogram | 调用耗时分布（按 tool_name 分组） |
| `orchestrator.call.retry_count` | Histogram | 重试次数分布 |
| `orchestrator.call.failure_rate` | Gauge | 失败率（按 error_type 分组） |
| `orchestrator.call.success_rate` | Gauge | 成功率（最近 100 次调用的滑动窗口） |
| `orchestrator.fallback.count` | Counter | 降级触发次数（按 primary_tool 分组） |
| `orchestrator.circuit_breaker.state` | Gauge | 各工具熔断器状态 (0=CLOSED, 1=OPEN, 2=HALF_OPEN) |
| `orchestrator.rate_limiter.throttled` | Counter | 被限流拒绝的调用次数 |

**告警规则**：

- 某工具的 `failure_rate` > 30%（5 分钟滑动窗口） → 告警
- 某工具的 `circuit_breaker.state = OPEN` → 告警
- `fallback.count` 增长速率 > 10/min → 告警（大量降级说明主工具普遍不可用）
- `duration_ms` P99 超过工具声明的 `timeout_ms` → 告警（超时设置可能不合理）

## 7. 与其他模块的关系

工具编排层不是孤立的。它与其他七个机制有明确的接口和交互契约：

| 关联模块 | 关系说明 | 接口触点 |
|---------|---------|---------|
| **01-四相循环** | Phase 2 产出 ExecutionPlan，Phase 3 通过编排器执行，Phase 4 消费编排器返回的 ToolResult 做验证 | `orchestrator.execute_plan(phase2_plan)` → Phase 4 检查 `unit.result.success` |
| **03-进度跟踪** | 编排器每完成一个工具调用，触发 `progress.on_tool_complete(node_id, status)`。对于长时间 DAG，进度跟踪器展示 "3/8 工具已完成" | `orchestrator.on_node_complete = lambda u: progress.update(u.node_id, u.status)` |
| **04-上下文工程** | 编排器返回的 ToolResult 在注入 Agent context 前需经 `trim_tool_result()` 裁剪。超过 50K token 的结果自动摘要 | `trimmed = context_manager.trim_tool_result(raw_result, max_tokens=50_000)` |
| **05-任务拆解** | 一个工具调用的结果可能触发新的子任务拆解。例如 grep 发现 20 个引用 → 拆解为 20 个「更新引用」子任务 | `if tool_result.needs_decomposition: task_list.add_subtasks(decompose(tool_result))` |
| **06-验证循环** | 工具编排返回的结构化 ToolResult 是验证循环的输入。验证循环在 Phase 4 中消费这些结果进行分层验证 | Phase 4: `verify_loop.assert_outcome(tool_result, expected=plan.expected_outcome)` |
| **07-子代理分治** | 当工具类型为 `SUBAGENT` 时，编排器递归创建子编排器实例。子编排器拥有独立的 ToolRegistry 和 token 预算 | 子编排器 = `Orchestrator(registry=sub_registry, max_parallelism=3)` |
| **08-GAN 三角色** | Generator 调用编排器执行工具；Evaluator 检查编排器返回的 ToolResult 序列（而非 Generator 的自我描述）来评分 | Evaluator 评分依据: `for unit in orchestrator.results: if not unit.result.success: score -= weight` |

## 8. 常见反模式与陷阱

### 8.1 错误吞并——最致命的陷阱

**症状**：`try: ... except Exception: return ""`。工具失败后 Agent 收到空字符串或 `null`。

**事故案例**：某电商客服 Agent 的代码在工具异常时返回空字符串。Agent 在 7 次工具调用中累积了 3 次被吞并的错误，最终向用户回复"您的退款已处理，金额 ¥0"——因为 `calculate_refund` 返回了空字符串，而 Agent 将其解释为 `amount = 0`。

**修复**：每个工具调用必须返回结构化 `ToolResult`，其中的 `success` 字段是 Agent 的第一眼判断依据。编排器确保不存在"非结构化工具返回"的路径。

### 8.2 回调地狱式编排

**症状**：每个工具调用的回调中嵌套下一个工具调用，10 个工具调用后缩进 10 层，错误处理散落各处。

**事故案例**：某 Agent 的回调地狱代码在添加第 7 个工具后，一个 `None` 返回值穿透了 4 层回调未被捕获，导致 Agent 向用户回复了空的退款确认。

**修复**：使用声明式 DAG。编排器负责控制流，业务逻辑只定义工具和依赖关系。不要手动编排工具调用的顺序和嵌套。

### 8.3 过度并行

**症状**：给 20 个独立工具不加限制地并发调用。下游 API 收到 20 个并发请求 → 触发 429 Rate Limit → 全部失败。

**事故案例**：某代码分析 Agent 并行调用 30 个 `grep` 命令，瞬间 fork 30 个子进程，导致开发机 OOM。

**修复**：`asyncio.Semaphore(5)`——默认并发限制 5，最大 10（需显式确认）。并行是优化手段，不是默认行为。

### 8.4 忽略幂等性

**症状**：写操作类型的工具超时后编排器重试，导致副作用重复执行。

**事故案例**：某 FinTech Agent 的 `create_transfer` 工具超时重试，创建了两笔相同的转账（金额翻倍）。

**修复**：(1) 关键写操作工具携带 `idempotency_key` 参数；(2) 编排器在重试前检查幂等缓存，相同 key 返回缓存结果而非重新执行。

### 8.5 结果未裁剪

**症状**：`read_large_file` 返回 500KB 文本，直接注入 Agent context → token 瞬间从 30K 飙到 180K → 上下文溢出。

**事故案例**：某 DevOps Agent 读取了 200MB 的日志文件，未裁剪直接返回，context 溢出导致 Agent 后续 15 分钟的工作全部丢失。

**修复**：所有工具返回在注入 context 前必须经过 `trim_tool_result()` 裁剪，默认上限 50K tokens。对于大结果，采用智能摘要而非粗暴截断：结构化结果保留 key + 截断 value；文本结果保留前 1/3 + 后 1/3。

### 8.6 同步阻塞异步上下文

**症状**：在 `async` 编排器中使用 `requests.get()` 而非 `httpx.AsyncClient`，阻塞事件循环。

**事故案例**：某 Agent 的工具编排器中混用了同步 HTTP 客户端，在 3 个并行 HTTP 调用中阻塞了整个事件循环，导致本应 500ms 完成的并行调用耗时 15s。

**修复**：编排器初始化时检测所有工具 `executor` 类型，拒绝注册同步 executor（或自动包装为 `run_in_executor`）。

### 8.7 无超时控制

**症状**：工具定义中 `timeout_ms = None` → 编排器无限等待 → 单个挂起的工具调用卡死整个 Agent。

**事故案例**：某 Agent 调用第三方天气 API 时网络中断，TCP 连接在无超时配置下悬挂了 23 分钟，Agent 在此期间无任何响应。

**修复**：所有工具必须有 `timeout_ms` 默认值（类型默认 + 可单独覆盖）。编排器层再加全局 `global_timeout_ms` 双层保护。不存在"无超时"的合法配置。

## 9. 实战演练：完整用例

**场景**：用户请求"查询北京和上海的当前温度，计算温差"。

### DAG 结构

```
  [weather_beijing] ──┐
                      ├──> [calc_diff]
  [weather_shanghai] ─┘
```

### 代码示例（核心路径）

```python
# 1. 创建工具注册表并注册工具
registry = ToolRegistry()
registry.register(Tool(
    name="get_weather",
    description="查询指定城市的当前天气",
    parameters_schema={
        "type": "object",
        "properties": {"city": {"type": "string"}},
        "required": ["city"],
    },
    executor=get_weather_impl,
    category=ToolCategory.NETWORK,
    timeout_ms=10_000,
    max_retries=1,
))
registry.register(Tool(
    name="calculate_difference",
    description="计算两个数值的差值",
    parameters_schema={
        "type": "object",
        "properties": {"a": {"type": "number"}, "b": {"type": "number"}},
        "required": ["a", "b"],
    },
    executor=calculate_difference_impl,
    category=ToolCategory.COMPUTE,
    timeout_ms=5_000,
    max_retries=0,
))

# 2. Phase 2 产出的 ExecutionPlan (DAG)
plan = ExecutionPlan(
    plan_id="weather-diff-001",
    strategy="dag",
    max_parallelism=3,
    nodes=[
        ToolNode(node_id="w1", tool_name="get_weather", arguments={"city": "北京"}),
        ToolNode(node_id="w2", tool_name="get_weather", arguments={"city": "上海"}),
        ToolNode(
            node_id="diff",
            tool_name="calculate_difference",
            arguments={
                "a": "${w1.result.temperature}",
                "b": "${w2.result.temperature}",
            },
            depends_on=["w1", "w2"],
        ),
    ],
)

# 3. 编排器执行
orchestrator = Orchestrator(registry, max_parallelism=5)
results = await orchestrator.execute_plan(plan)

# 4. 输出结果
for node_id, unit in results.items():
    status = "SUCCESS" if unit.result.success else "FAILED"
    print(f"[{status}] {node_id}: {unit.result.data} "
          f"(attempts={unit.attempt})")
```

1. **w1 和 w2 的并行执行是自动的**——编排器根据 DAG 依赖关系计算出两者无依赖，自动并行调度。业务代码无需手写任何并行逻辑。

3. **参数引用自动解析**——`${w1.result.temperature}` 在执行 `diff` 节点前被编排器自动替换为实际值 `35`。

## 10. 总结

1. **工具编排是一层独立中间件**——不是 Agent 代码中的零散 try/except/retry。它提供统一的超时、重试、限流、熔断、幂等和可观测性。其核心信条是：Agent 与外部世界的每一次交互，必须经过编排层的完整处理管线，没有旁路，没有例外。

2. **结构化错误是恢复的基础**。`ToolResult.success` 让 Agent 一眼知道成败，`error_type` 让 Agent 理解错误类别并选择不同应对策略，`suggestion` 给 Agent 提供领域知识驱动的恢复建议。三者缺一不可。

3. **DAG 调度是编排的核心**。拓扑排序 + 就绪队列 + Semaphore 并发控制 = 任意复杂依赖关系的高效执行。这套算法的优雅之处在于：业务代码只描述"什么依赖什么"，编排器负责"如何最高效地执行"。

4. **防御性设计可量化**。每个参数都有明确的值和选择理由——并发上限 5（不是随便设的）、超时 30s（覆盖 P99 + 2 次重试）、重试指数退避 1s→2s→4s（不是固定间隔）、熔断阈值 50%（平衡敏感度和稳定性）、结果裁剪 50K tokens（预留 context 空间的 25%）。

5. **编排层是控制流的执行引擎**。它在四相循环中承担 Phase 3 的职责，与权限闸（Phase 3 前置检查）、验证循环（Phase 4 消费 ToolResult）、进度跟踪（每次调用后通知）形成紧密协作。它不是孤立的模块，而是 Harness 控制流体系的核心枢纽。
