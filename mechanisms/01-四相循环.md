# 机制详解：四相循环 (4-Phase Loop)

> **对应失效**：① 循环失控 (Loop Runaway)
> **核心贡献**：把一个朴素的"调用-执行"循环改造成 4 阶段的结构化迭代，强制每轮收敛。
> **所属支柱**：控制流（主要）、状态流（辅助）

---

## 一、为什么需要四相循环？

### 1.1 朴素循环的致命问题

Naive Agent 的循环只有两个状态：

```
LLM思考 → 工具执行 → LLM思考 → 工具执行 → ...
```

这个结构有三个致命缺陷：

1. **没有"准备"环节**：LLM 在信息不足时就开始行动（比如还没读文件就开始改代码）
2. **没有"验证"环节**：LLM 觉得做完了就做完了，对不对没人知道
3. **没有"收敛"压力**：循环没有内置的收敛机制，LLM 总能找到"再做一件事"的理由

### 1.2 四相循环的结构

```
for iteration in range(MAX_ITERATIONS):
    ┌──────────────────────────────┐
    │  Phase 1: GATHER (收集)      │  ← 我在哪？我要做什么？我需要什么信息？
    │  读取文件、检索上下文、        │
    │  理解当前状态                 │
    ├──────────────────────────────┤
    │  Phase 2: ACT (行动)         │  ← 做一件明确的、原子的事
    │  修改文件、执行命令、          │
    │  调用 API                    │
    ├──────────────────────────────┤
    │  Phase 3: VERIFY (验证)      │  ← 做对了吗？用真机工具验证
    │  运行测试、检查输出、          │
    │  截图对比                    │
    ├──────────────────────────────┤
    │  Phase 4: ITERATE (迭代)     │  ← 基于验证结果决定下一步
    │  通过→下一子任务              │
    │  失败→分析原因→重试            │
    │  全完成→退出                  │
    └──────────────────────────────┘
```

## 二、四相详解

### 2.1 Phase 1: GATHER (收集上下文)

**核心原则**：**先看再动**。Agent 在行动前必须有足够的信息。

```
GATHER 阶段要回答的问题：
  1. 当前子任务的目标是什么？
  2. 与这个子任务相关的代码/文件在哪里？
  3. 上一步的结果是什么？有什么需要关注的？
  4. 我需要但还没有的信息是什么？
```

**GATHER 阶段的典型操作**：

```python
def gather_phase(task, progress):
    """收集当前子任务所需的上下文"""
    
    # 1. 读取任务清单，确定当前子任务
    current_subtask = progress.current_subtask
    context = {"subtask": current_subtask}
    
    # 2. 根据子任务类型收集相关信息
    if current_subtask.type == "code_modification":
        # 读取要修改的文件
        context["target_file"] = read_file(current_subtask.target_file)
        # 搜索引用位置
        context["references"] = grep(current_subtask.symbol_name)
        # 读取测试文件
        context["tests"] = read_file(current_subtask.test_file)
    
    elif current_subtask.type == "bug_fix":
        # 读取错误日志
        context["error_log"] = read_file(current_subtask.error_log)
        # 读取相关源代码
        context["source_files"] = read_files(current_subtask.related_files)
    
    elif current_subtask.type == "dependency_update":
        # 读取当前版本
        context["current_version"] = read_dependency_file()
        # 检查 changelog
        context["changelog"] = fetch_changelog(current_subtask.package_name)
    
    # 3. 检查是否有前一步的遗留问题
    if progress.last_verification and progress.last_verification.failed:
        context["previous_failure"] = progress.last_verification
    
    return context
```

**GATHER 的反模式**：
- ❌ 一口气读完整个项目的所有文件（收集太多，浪费时间 + 污染 context）
- ❌ 不读就直接改（"我猜这个文件应该是..."）
- ❌ 收集了信息但不理解就行动

### 2.2 Phase 2: ACT (行动)

**核心原则**：**一次只做一件事**，且这件事必须是可以验证的。

```
ACT 阶段的设计原则：
  1. 原子性：一个 ACT 操作 = 一个可验证的产出
  2. 明确性：操作的目标和预期结果必须明确
  3. 可逆性：尽量选择可以撤销的操作（git checkout → 修改 → git diff）
```

**ACT 的粒度对比**：

```python
# ❌ 太粗：一个 ACT 做了太多事
act("重构整个 UserService 模块")
# → 改了 5 个文件，12 个方法 → 验证失败时不知道哪里出错

# ✅ 合适：一个 ACT 只做一件事
act("重命名 UserService.getUserName 为 getUsername")
# → 改了 1 个方法名 → grep 验证 → 通过/失败 → 明确可追踪

# ✅ 合适：原子但有意义的操作
act("抽取 IUserService 接口，包含 5 个公共方法签名")
# → 新建 1 个文件，改 1 个文件 → 编译验证 → 明确可追踪
```

**ACT 阶段的执行模式**：

```python
def act_phase(subtask, context):
    """执行一个原子操作"""
    
    # 1. 操作前快照（用于回滚和 diff）
    before_snapshot = git_diff()
    
    # 2. 执行操作
    if subtask.action == "edit_file":
        result = edit_file(subtask.file, subtask.old_string, subtask.new_string)
    elif subtask.action == "run_command":
        result = bash(subtask.command)
    elif subtask.action == "create_file":
        result = write_file(subtask.file, subtask.content)
    
    # 3. 操作后快照（用于验证）
    after_snapshot = git_diff()
    
    # 4. 获取操作的具体变化
    changes = diff(before_snapshot, after_snapshot)
    
    return ActResult(
        success=result.success,
        changes=changes,
        artifacts=result.artifacts  # 生成的文件、日志等
    )
```

### 2.3 Phase 3: VERIFY (验证)

**核心原则**：**绝不信任模型的自我判断**。用真机工具产生客观的验证信号。

```
验证的三个层次：
  L1: 语法/编译层  → 代码能不能跑？ (compile / lint)
  L2: 逻辑/功能层  → 功能对不对？ (unit test / integration test)
  L3: 行为/体验层  → 用户体验对不对？ (Playwright / screenshot)
```

**VERIFY 阶段的实现**：

```python
def verify_phase(subtask, act_result):
    """多层验证"""
    
    verifications = []
    
    # L1: 编译/语法验证
    if subtask.language in ["python", "typescript", "go", "rust", "java"]:
        l1_result = run_compilation_check(subtask)
        verifications.append(l1_result)
        if not l1_result.passed:
            return VerificationResult(
                passed=False,
                level=1,
                reason=f"编译失败: {l1_result.output}"
            )
    
    # L2: 单元测试
    if subtask.test_file:
        l2_result = run_tests(subtask.test_file)
        verifications.append(l2_result)
        if not l2_result.passed:
            return VerificationResult(
                passed=False,
                level=2,
                reason=f"测试失败: {l2_result.failed_tests}"
            )
    
    # L3: 集成/行为验证（关键子任务）
    if subtask.requires_e2e_verification:
        l3_result = run_e2e_verification(subtask)
        verifications.append(l3_result)
    
    return VerificationResult(
        passed=all(v.passed for v in verifications),
        level=max(v.level for v in verifications),
        details=verifications
    )
```

**验证失败时的处理**：

```
验证失败 ≠ 任务失败。验证失败 = 需要修正后重试。

失败分类：
  类型 A "小错" — 拼写错误、漏改引用 → 自动修复，重试（最多 3 次）
  类型 B "中错" — 逻辑理解有误、方案需要调整 → 回到 GATHER，重新理解
  类型 C "大错" — 方向错误、需要推翻重来 → 暂停，请求人工判断
```

### 2.4 Phase 4: ITERATE (迭代)

**核心原则**：**基于验证结果做出明确的下一步决策**。

```
ITERATE 的决策树：
  VERIFY 通过？
    ├── 是 → 还有子任务？
    │   ├── 是 → GOTO Phase 1 (下一个子任务)
    │   └── 否 → ✅ 全部完成，退出循环
    └── 否 → 是第几次失败？
        ├── < 3 次 → 分析原因 → GOTO Phase 1 (修正重试)
        └── >= 3 次 → 🛑 暂停，请求人工介入
```

**收敛机制**：

```python
class ConvergenceControl:
    """多层收敛机制，确保 Agent 不会无限循环"""
    
    MAX_TOTAL_ITERATIONS = 25     # 硬上限
    MAX_RETRIES_PER_SUBTASK = 3   # 单子任务最大重试次数
    MAX_NO_PROGRESS_STREAK = 3    # 连续无进展的最大容忍次数
    MAX_SIMILAR_ATTEMPTS = 2      # 相同的失败尝试
    
    def should_continue(self, iteration, progress):
        # 硬上限
        if iteration >= self.MAX_TOTAL_ITERATIONS:
            return StopReason.HARD_LIMIT, "达到最大迭代次数"
        
        # 无进展检测
        if progress.no_progress_streak >= self.MAX_NO_PROGRESS_STREAK:
            return StopReason.STUCK, "连续无进展，可能卡死"
        
        # 重复失败检测（Agent 在试同样的错误方案）
        if progress.similar_failure_count >= self.MAX_SIMILAR_ATTEMPTS:
            return StopReason.REPEATING, "重复相同的失败，需要人工介入"
        
        return StopReason.CONTINUE, None
```

## 三、四相循环的完整伪代码

```python
def four_phase_loop(task: str, task_list: TaskList, max_iterations=25):
    """
    Harness 的主循环 —— 四相循环
    这是 Agent 的核心执行引擎
    """
    progress = load_or_create_progress(task, task_list)
    
    for iteration in range(max_iterations):
        current_subtask = task_list.get_next_pending()
        
        # ============================================================
        # Phase 1: GATHER — 收集上下文
        # ============================================================
        context = {}
        
        # 收集与当前子任务相关的文件
        if current_subtask.related_files:
            for f in current_subtask.related_files:
                context[f] = read_file(f)
        
        # 如果是重试（前一次验证失败），注入失败上下文
        if current_subtask.attempt_number > 0:
            context["previous_failure"] = {
                "attempt": current_subtask.attempt_number,
                "error": current_subtask.last_error,
                "verification_output": current_subtask.last_verification_output,
                "hint": generate_fix_hint(current_subtask)
            }
        
        # 注入必要的环境信息
        context["git_status"] = run("git status --short")
        context["current_branch"] = run("git branch --show-current")
        
        # ============================================================
        # Phase 2: ACT — 执行动作
        # ============================================================
        
        # 构建消息给 LLM
        messages = build_messages(current_subtask, context)
        response = llm.chat(messages, tools=available_tools)
        
        # 执行工具调用
        for tool_call in response.tool_calls:
            # 权限检查
            if requires_approval(tool_call):
                approved = request_user_approval(tool_call)
                if not approved:
                    return ToolResult(success=False, error="USER_DENIED")
            
            # 结构化的工具执行（工具编排）
            result = orchestrated_tool_call(tool_call)
            messages.append(format_tool_result(tool_call, result))
        
        # ============================================================
        # Phase 3: VERIFY — 验证结果
        # ============================================================
        
        verification = None
        
        # 编译/语法层验证
        if current_subtask.verify_compile:
            compile_result = run_compile_check(current_subtask)
            if not compile_result.passed:
                verification = VerificationResult(
                    passed=False,
                    level=1,
                    message=f"编译失败:\n{compile_result.output}"
                )
        
        # 测试层验证
        if not verification or verification.passed:
            if current_subtask.verify_tests:
                test_result = run_tests(current_subtask.test_target)
                verification = VerificationResult(
                    passed=test_result.passed,
                    level=2,
                    message=test_result.summary
                )
        
        # 行为层验证（UI 截图等）
        if not verification or verification.passed:
            if current_subtask.verify_e2e:
                e2e_result = run_playwright_check(current_subtask)
                verification = VerificationResult(
                    passed=e2e_result.passed,
                    level=3,
                    message=e2e_result.summary,
                    artifacts=e2e_result.screenshots
                )
        
        # 如果所有验证层都跳过了（该子任务无需验证），默认通过
        if verification is None:
            verification = VerificationResult(passed=True, level=0, message="无需验证")
        
        # ============================================================
        # Phase 4: ITERATE — 决定下一步
        # ============================================================
        
        if verification.passed:
            # 子任务完成
            current_subtask.mark_completed(verification)
            progress.save()
            
            # 里程碑检查：是否需要 git commit
            if current_subtask.is_milestone:
                git_commit(f"✅ {current_subtask.description}")
            
            # 全部完成？
            if task_list.all_completed():
                break  # 退出循环
            else:
                continue  # 下一个子任务
        
        else:
            # 子任务失败
            current_subtask.attempt_number += 1
            current_subtask.last_error = verification.message
            current_subtask.last_verification_output = verification
            
            # 达到最大重试次数？
            if current_subtask.attempt_number >= MAX_RETRIES_PER_SUBTASK:
                current_subtask.mark_failed()
                
                # 根据失败策略决定
                if task_list.failure_strategy == "skip_and_continue":
                    continue  # 跳过，继续下一个
                elif task_list.failure_strategy == "ask_user":
                    user_decision = ask_user(current_subtask)
                    if user_decision == "skip":
                        continue
                    elif user_decision == "abort":
                        break
                    elif user_decision == "manual_fix":
                        # 等待用户手动修复 ⟮后继续
                        wait_for_user()
                        continue
            
            progress.save()
    
    # 循环结束
    return progress.summary()
```

## 四、四相循环的设计要点

### 4.1 为什么是四个阶段而不是三个或五个？

```
三阶段（太简）：ACT → VERIFY → ITERATE（缺 GATHER）
  问题：Agent 在信息不足时就开始行动
  后果：行动基于错误假设 → 验证失败 → 回退 → 浪费一轮

四阶段（平衡）：GATHER → ACT → VERIFY → ITERATE
  优点：信息 → 行动 → 验证 → 迭代，清晰完整
  

五阶段（太繁）：PLAN → GATHER → ACT → VERIFY → ITERATE
  问题：PLAN 和 GATHER 的功能有重叠，增加概念负担
  反例：计划往往是在 GATHER 信息的过程中形成的
```

### 4.2 每阶段的时间/Token 分配

```
理想分配比例（每个完整迭代）：
  GATHER:  ~20% (读文件、搜索、理解)
  ACT:     ~30% (执行修改)
  VERIFY:  ~30% (运行测试、检查)
  ITERATE: ~20% (评估结果、决定方向)

实际情况中，早期迭代 GATHER 偏多，后期迭代 VERIFY 偏多。
```

### 4.3 嵌套循环的可能性

```python
# 高级用法：在 Phase 2 (ACT) 内部嵌套一个微循环
# 用于处理同一子任务内的多次工具调用

def act_phase_with_micro_loop(subtask, context):
    """ACT 阶段的微循环：可能需要多次工具调用才能完成一个原子操作"""
    
    for micro_iteration in range(5):  # 微循环也有上限
        response = llm.chat(messages, tools)
        
        if not response.tool_calls:
            break  # LLM 认为操作完成
        
        for tc in response.tool_calls:
            result = execute_tool(tc)
            messages.append(result)
    
    # 注意：微循环之后，仍然要经过 Phase 3 (VERIFY)
```

## 五、与其他机制的协作

| 协作机制 | 协作关系 |
|---------|---------|
| **任务拆解** | 任务拆解后的子任务清单是四相循环的"路书"——循环按清单逐项执行 |
| **工具编排** | 四相循环的 ACT 阶段使用工具编排来执行具体工具调用 |
| **验证循环** | 四相循环的 VERIFY 阶段使用验证循环的机制来验证结果 |
| **上下文工程** | 上下文工程在四相循环的每一轮监控 tokens，决定是否压缩 |
| **进度跟踪** | 四相循环的 ITERATE 阶段触发进度持久化 |

## 六、四相循环的局限性

1. **固定节奏不适合所有任务**：探索性任务（如"帮我理解这个代码库"）可能不需要严格的 Gather-Act-Verify 节奏
2. **阶段划分增加了单轮成本**：每轮都要走完四个阶段 → 对简单任务来说过度工程化
3. **验证的可靠性取决于验证工具**：如果验证工具覆盖不全，VERIFY 阶段只是走过场
4. **无法应对未知-未知**：如果任务本身定义不清，四相循环也只是在规范地做错事

---

## 七、总结

四相循环是 Harness 的**骨架**——它给 Agent 提供了一个结构化的执行节律。

它的核心贡献不是让 Agent "更聪明"，而是让 Agent **更可控**：
- 每一步都有明确的意图（GATHER）
- 每一步都有明确的行动（ACT）
- 每一步都有明确的验证（VERIFY）
- 每一步都有明确的决策（ITERATE）
