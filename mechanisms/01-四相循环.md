## 1. 问题定义：循环失控的根源

### 1.1 什么是循环失控

**循环失控（Loop Runaway）** 是指 Agent 在执行多步任务时，陷入无限或近似无限的迭代循环，无法在合理的时间和资源预算内收敛到终止状态的现象。

其本质不是「模型不够聪明」，而是**控制流（Control Flow）架构的结构性缺陷**——Naive Agent 的 while 循环将终止决策权完全委托给 LLM 的「不再调用工具」信号，而 LLM 并没有内在的收敛保证。

### 1.2 Naive 循环为什么必然失败

考虑最简形式的 Agent 循环：

```python
messages = [system_prompt, user_task]
while True:
    response = llm.chat(messages, tools=all_tools)
    messages.append(response)
    if not response.tool_calls:
        break  # ← 唯一的终止条件：LLM 自己决定"不调工具了"
    for tc in response.tool_calls:
        result = execute_tool(tc)
        messages.append(result)
```

这一结构隐含了三个**无法通过提升模型能力来解决**的系统性问题：

**问题一：终止信号的不可靠性。** LLM 的 `stop_reason` 为 `tool_calls` 或 `end_turn` 仅表示模型在当前上下文中的判断，不表示任务客观上已完成。模型可能因以下原因错误地发出 `end_turn`：上下文窗口接近上限导致模型「遗忘」了剩余步骤；中间某一轮的工具返回被截断或为空，模型基于不完整信息做出终止判断；模型在长上下文中的注意力衰减导致其「丢失了线程」。反之，模型也可能持续发出 `tool_calls`——每次微调一个变量名、每次多读一个文件——因为它没有「够了」的内在概念。

**问题二：反馈循环的正反馈特性。** 在 Naive 循环中，messages 列表只增不减。每轮迭代追加 2-4 条消息（assistant response + tool results），而这些消息会完整进入下一轮的 LLM 输入。结果是：上下文线性膨胀 → 每轮推理成本线性增长 → 模型注意力在长上下文中衰减 → 决策质量下降 → 需要更多轮次来完成任务 → 上下文进一步膨胀。这是一个典型的**正反馈循环（Positive Feedback Loop）**，最终必然导致 Context 溢出（失效 ②）或成本失控（失效 ⑧）。

**问题三：缺乏相变边界。** Naive 循环是一个连续的过程——LLM 思考 → 调用工具 → LLM 思考 → 调用工具——中间没有明确的「阶段切换点」。没有阶段切换点意味着：(a) 无法在阶段之间插入检查点（checkpoint）；(b) 无法对某个阶段单独设置超时；(c) 无法在阶段切换时做状态校验和收敛判断；(d) 无法在阶段粒度上报指标。换句话说，Naive 循环是不可观测、不可恢复、不可中断的。

### 1.3 四相循环的结构化响应

四相循环的核心思想是：**在连续的执行流中强制插入三个相变边界（Phase Boundary），将一次迭代拆分为四个职责明确、输入/输出可验证的阶段。**

```
Naive 循环:
  LLM → Tool → LLM → Tool → LLM → Tool → ... (连续流，无边界)

四相循环:
  ┌─────────────────────────────────────────────────────────┐
  │  Iteration N                                            │
  │                                                         │
  │  [Perceive] ──┬── [Plan] ──┬── [Execute] ──┬── [Verify]│
  │  上下文装配    │   规划决策   │   工具编排     │   验证修正 │
  │              Phase         Phase           Phase        │
  │              Boundary      Boundary        Boundary     │
  │              (checkpoint)  (checkpoint)    (checkpoint) │
  └─────────────────────────────────────────────────────────┘
```

三个相变边界带来的结构性优势：

| 能力 | Naive 循环 | 四相循环 |
|------|:---:|:---:|
| **收敛保证** | 无（依赖 LLM 自觉停止） | 有（收敛控制器 + 硬上限 + Phase 4 强制裁决） |
| **可恢复性** | 无（crash = 全部丢失） | 每个相变边界写入 checkpoint |
| **可观测性** | 低（只有 messages 在增长） | 高（相位切换时输出结构化日志 + 指标） |
| **可中断性** | 差（无法安全中断） | 好（每个相变边界是安全中断点） |
| **故障隔离** | 无（一个工具崩溃可能污染整个 messages） | 有（Phase 边界限制了故障的传播范围） |
| **成本可控性** | 差（token 消耗无感知） | 好（Phase 1 做预算核算，Phase 4 判断是否提前终止） |

## 2. 架构定位：骨架的隐喻

四相循环是 Harness 系统的**执行骨架（Execution Skeleton）**。它不替代任何其他模块，但所有其他模块都挂载在它上面运行。

```
                         ┌──────────────────────────┐
                         │    GAN 三角色架构          │
                         │   (宏观评审，第 8 机制)     │
                         └────────────┬─────────────┘
                                      │ 全局 DONE 后触发
                                      ▼
┌─────────────────────────────────────────────────────────────────┐
│                       四相循环 (执行骨架)                         │
│                                                                 │
│  ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐    │
│  │ Phase 1  │──▶│ Phase 2  │──▶│ Phase 3  │──▶│ Phase 4  │    │
│  │ 感知装配  │   │ 规划决策  │   │ 执行编排  │   │ 验证修正  │    │
│  │          │   │          │   │          │   │          │    │
│  │ 上下文   │   │ 任务拆解  │   │ 工具编排  │   │ 验证循环  │    │
│  │ 工程 ────┤   │ ────────┤   │ ────────┤   │ ────────┤    │
│  │ (机制4)  │   │ (机制5)  │   │ (机制2)  │   │ (机制6)  │    │
│  └──────────┘   └──────────┘   └──────┬─────┘   └──────────┘    │
│                                       │                         │
│                                  ┌────┴─────┐                  │
│                                  │ 子代理分治 │                  │
│                                  │ (机制7)   │                  │
│                                  └──────────┘                  │
│                                                                 │
│  横跨全部 4 个 Phase:  进度跟踪 (机制3)  ← 每相边界持久化        │
└─────────────────────────────────────────────────────────────────┘
```

**关键架构约束（关注点分离）**：

- 四相循环只做**执行节律控制**（什么时候进入哪个 Phase，Phase 之间如何流转）
- 不做 token 计数 → 委托给上下文工程模块
- 不做工具调用细节 → 委托给工具编排模块
- 不做进度落盘 → 委托给进度跟踪模块
- 不做子任务验证工具的选择 → 委托给验证循环模块

这种关注点分离使得每个模块可以独立演进和测试。四相循环的代码不因工具数量增加而修改，不因验证策略变化而修改。

## 3. Phase 1：感知与上下文装配 (Perceive & Assemble)

### 3.1 形式化定义

**Phase 1 的核心职责**：在当前迭代轮次的起点，回答一个精确的问题——「Agent 此刻需要知道什么，才足以做出正确的下一步决策？」

形式化地，Phase 1 是一个函数：

```
Perceive: (Progress, Messages, Subtask, Environment) → ContextBundle
```

其关键约束是：**输出必须是一个有限的、有 token 预算上限的上下文包，而非完整的消息历史。** 这是 Phase 1 区别于 Naive 循环「把所有 messages 塞给 LLM」的核心差异。

**为什么这一相是必要的。** Naive 循环中，LLM 在每一轮都看到完整的 messages 列表。随着迭代增加，早期的不相关细节、已完成的子任务的中间过程、探索性的死胡同——这些信息持续占据上下文窗口，稀释了 LLM 对当前子任务的注意力。Phase 1 通过**主动裁剪**打破这种信息累积：只保留与当前子任务语义相关的信息，将已完成任务的细节替换为结构化摘要。

### 3.2 输入/输出契约

```
输入 (Input):
  progress: ProgressSnapshot
    ├── task_id: str                         # 任务唯一标识
    ├── completed_subtasks: list[SubtaskSummary]  # 已完成子任务的摘要
    ├── current_subtask_id: str | None       # 当前正在执行的子任务 ID
    ├── last_checkpoint_phase: Phase | None  # 最近一次 checkpoint 所在的 Phase
    └── is_resuming: bool                    # 是否为 Session 恢复

  messages: Message[]
    └── 完整的消息历史（可能非常长）

  current_subtask: Subtask | None
    ├── description: str                     # 子任务描述
    ├── acceptance_criteria: list[str]       # 验收标准
    ├── attempt_number: int                  # 当前子任务的第几次尝试
    └── last_failure: FailureContext | None  # 上一次失败上下文

  environment: EnvironmentSnapshot
    ├── git_branch: str
    ├── git_status: str
    ├── cwd: str
    └── timestamp_utc: datetime

输出 (Output):
  context: ContextBundle
    ├── system_prompt: str                   # 稳定不变的 system prompt
    ├── task_context: str                    # 当前子任务描述 + 验收标准
    ├── relevant_history: Message[]          # 裁剪后的消息（≤ 指定 token 量）
    ├── environment_snapshot: dict           # 当前环境状态快照
    ├── previous_failure: FailureContext | None
    ├── token_budget_remaining: int          # 本迭代剩余 token 预算
    └── metrics: PhaseMetrics               # Phase 1 自身的耗时和裁剪指标
```

**数据契约的强制约束**：

1. `relevant_history` 的 token 数 ≤ `token_budget_remaining * 0.6`（为 Phase 2-4 预留至少 40% 空间）
2. `system_prompt` 必须与上一轮完全相同（保证 Prompt Cache 命中）
3. 若 `is_resuming = True`，必须首先从最近 checkpoint 恢复状态，再执行裁剪
4. `previous_failure` 若存在，其注入量 ≤ 2000 tokens（防止重试时上下文膨胀）

### 3.3 核心处理逻辑

Phase 1 的执行分为五个步骤，每个步骤有明确的输入和预期产出：

**步骤 1：状态恢复 (State Recovery)。** 仅在 `progress.is_resuming = True` 时执行。从最近的 checkpoint 中恢复 `current_subtask_id` 和已完成子任务列表。如果 checkpoint 数据损坏或版本不兼容，降级策略为：将 `is_resuming` 置为 `False`，从任务清单的第一个未完成子任务重新开始，同时记录 `recovery_failed` 事件。

**步骤 2：上下文裁剪 (Context Pruning)。** 这是 Phase 1 最关键的工程决策。与「保留最近 N 条消息」的简单截断不同，语义裁剪的策略是：

- 与 `current_subtask.description` 语义相似度 ≥ 阈值的消息 → 保留原文
- 已完成子任务的中间执行过程 → 替换为 `output_summary`（由进度跟踪模块维护）
- 与当前子任务无关的探索性消息 → 丢弃
- 最近 3 轮交互（6 条消息）→ 无论语义相关性如何，强制保留

```python
async def perceive_and_assemble(
    progress: ProgressSnapshot,
    messages: list[Message],
    current_subtask: Subtask | None,
    environment: EnvironmentSnapshot,
    context_manager: ContextManager,
    token_budget: TokenBudgetManager,
) -> ContextBundle:
    # 步骤 1: 状态恢复
    recovered_state = None
    if progress.is_resuming:
        checkpoint = await progress.recover_last_checkpoint()
        if checkpoint and checkpoint.is_valid():
            recovered_state = checkpoint
            logger.info("phase1.resume",
                last_phase=checkpoint.current_phase,
                last_iteration=checkpoint.iteration)
        else:
            logger.warning("phase1.recovery_failed",
                reason="checkpoint corrupted or incompatible")

    # 步骤 2: 上下文裁剪 — 按语义相关性筛选
    if current_subtask:
        relevant_history = await context_manager.crop_by_semantic_relevance(
            messages=messages,
            target=current_subtask.description,
            max_tokens=token_budget.remaining * 0.6,
            preserve_recent_n=6,
        )
    else:
        relevant_history = messages[-15:]  # 初始轮次：尚未拆解，保留最近 15 条

    # 步骤 3: 环境快照
    env_snapshot = {
        "git_branch": environment.git_branch,
        "git_status": await environment.git_status_short(),
        "cwd": environment.cwd,
        "timestamp_utc": datetime.utcnow().isoformat(),
    }

    # 步骤 4: 失败上下文注入（仅重试场景）
    failure_context = None
    if current_subtask and current_subtask.attempt_number > 0:
        failure_context = truncate_to_tokens({
            "attempt": current_subtask.attempt_number,
            "last_verdict": current_subtask.last_verification_output,
            "last_error_type": current_subtask.last_error_type,
            "suggested_fix": current_subtask.suggested_fix,
        }, max_tokens=2000)

    # 步骤 5: 组装并返回
    return ContextBundle(
        system_prompt=SYSTEM_PROMPT_STABLE,
        task_context=current_subtask.description if current_subtask else "分析用户任务",
        relevant_history=relevant_history,
        environment_snapshot=env_snapshot,
        previous_failure=failure_context,
        token_budget_remaining=token_budget.remaining,
        metrics=PhaseMetrics(
            history_original_count=len(messages),
            history_cropped_count=len(relevant_history),
            cropped_tokens=count_tokens(relevant_history),
        ),
    )
```

### 3.4 边界条件与异常处理

| 边界条件 | 处理策略 |
|---------|---------|
| `messages` 为空 | 仅使用 `system_prompt` + `task_description` 构建首轮 context；记录 `empty_messages` 告警 |
| `current_subtask` 为 None 且 `messages` 非空 | 说明处于第一轮迭代（尚未拆解任务）。保留最近 15 条消息，不执行语义裁剪 |
| `token_budget.remaining` 低于最低阈值（如 4000 tokens） | 触发**紧急压缩**：仅保留 system_prompt + 当前子任务描述 + 最近 2 轮交互；记录 `critical_budget` 事件；将 `token_budget_remaining` 标记为 `CRITICAL` |
| 语义裁剪后 `relevant_history` 为空 | 回退到简单截断策略（最近 8 条消息）；记录 `semantic_crop_fallback` 事件 |
| checkpoint 恢复后发现 `current_subtask` 已不存在于任务清单 | 任务清单可能被外部修改。从任务清单中取第一个 `pending` 子任务；记录 `subtask_desync` 事件 |

## 4. Phase 2：规划与工具决策 (Plan & Decide)

### 4.1 形式化定义

**Phase 2 的核心职责**：基于 Phase 1 装配的有限上下文，产出一个**结构化、可验证、可审计**的本轮执行计划。

形式化地：

```
Plan: (ContextBundle, ToolRegistry, TaskList, LLM) → PlanWithTools
```

**为什么 Phase 2 需要与 Phase 3 分离。** Naive 循环中，「决定做什么」和「实际去做」是耦合在同一个 LLM 推理步骤中的——LLM 输出 `tool_calls` 的同时也隐含地做了规划。这种耦合导致两个问题：(a) 规划的质量无法独立评估——你只能在工具调用完成后才知道规划是否合理；(b) 当执行失败时，没有独立的规划记录用于诊断是「计划错了」还是「执行错了」。Phase 2 的独立存在使得每个 plan 成为一个可审计的决策点。

### 4.2 输入/输出契约

```
输入 (Input):
  context: ContextBundle                     # Phase 1 的输出
  tool_registry: ToolRegistry                # 可用工具注册表
  task_list: TaskList                        # 宏观任务清单
  model: LLMProvider                         # LLM 接口
  convergence_controller: ConvergenceController  # 收敛检测器

输出 (Output):
  plan: PlanWithTools
    ├── iteration_id: str                    # 本轮唯一标识
    ├── objective: str                       # 本轮原子目标（≤ 100 字）
    ├── selected_tools: ToolBinding[]         # 选中的工具及其参数
    ├── execution_strategy: ExecutionStrategy # SEQUENTIAL | PARALLEL | CONDITIONAL
    ├── expected_outcome: str                # 预期结果（供 Phase 4 比对）
    ├── estimated_tokens: int                # 预估本轮 token 消耗
    ├── is_final_iteration: bool             # 是否预期这是最后一轮
    └── rationale: str                       # 为什么选择这个方案
```

**数据契约的强制约束**：

1. `selected_tools` 中的所有工具必须来自 `tool_registry`，且参数必须通过对应工具的 JSON Schema 校验
2. `execution_strategy = PARALLEL` 时，所有选中工具必须被标注为 `parallel_safe = true`
3. `estimated_tokens` 必须 ≤ `context.token_budget_remaining * 0.35`（为 Phase 3 的工具返回和 Phase 4 的验证逻辑预留空间）
4. 若 `context.previous_failure != None` 且 `attempt_number ≥ 2`，则本轮 `selected_tools` 不得与上一轮完全相同（强制策略变更）

### 4.3 核心处理逻辑

Phase 2 的核心工程决策是**工具预筛选（Tool Pre-filtering）**和**收敛检测**。

**工具预筛选。** 不将全部工具（可能有 50+ 个）的 Schema 塞入 LLM 上下文——这既浪费 token，又增加了 LLM 选择错误工具的概率。而是根据当前子任务的类型（如 `code_modification`、`data_analysis`、`file_operation`），从工具注册表中筛选出 2-5 个候选工具，仅将这些工具的 Schema 提供给 LLM。

**收敛检测。** 在调用 LLM 之前，Phase 2 先检查是否陷入了「规划僵化（Plan Stagnation）」——连续 N 轮产出了高度相似的 plan。检测方式：计算当前 plan 与之前 plan 的 cosine similarity。若 similarity ≥ 0.9 且连续出现 ≥ 2 次，则强制从候选工具集中移除上一轮使用的工具，迫使 LLM 换策略。

```python
async def plan_and_decide(
    context: ContextBundle,
    tool_registry: ToolRegistry,
    task_list: TaskList,
    model: LLMProvider,
    convergence: ConvergenceController,
) -> PlanWithTools:
    current_subtask = task_list.current_subtask

    # 步骤 1: 按子任务类型预筛选工具（2-5 个候选）
    candidate_tools = tool_registry.filter_by_subtask_type(
        phase=current_subtask.phase,
        task_type=current_subtask.type,
    )

    # 步骤 2: 收敛检测 — 是否陷入规划僵化
    if convergence.is_plan_stagnating(context.relevant_history):
        logger.warning("phase2.plan_stagnation",
            stagnation_count=convergence.stagnation_count)
        convergence.force_tool_rotation(candidate_tools)

    # 步骤 3: 调用 LLM 生成 plan
    plan = await model.chat(
        messages=[{"role": "system", "content": PLANNER_SYSTEM_PROMPT}]
            + context.relevant_history
            + [{"role": "user", "content": _build_planning_prompt(
                context=context,
                candidate_tools=candidate_tools,
                previous_failure=context.previous_failure)}],
        tools=[],  # Phase 2 不调用工具，LLM 输出结构化 plan 本身
        response_format={"type": "json_schema", "schema": PlanWithTools.schema()},
        max_tokens=2000,
    )

    # 步骤 4: 客户端校验 — 不信任 LLM 输出
    _validate_plan(plan, candidate_tools, context.token_budget_remaining)

    # 步骤 5: 收敛控制器记录
    convergence.record_plan(plan)

    return plan
```

### 4.4 边界条件与异常处理

| 边界条件 | 处理策略 |
|---------|---------|
| 候选工具集为空 | 当前子任务类型无法匹配任何工具。将错误信息注入 `context`，触发 `ESCALATE`；记录 `no_matching_tools` 事件 |
| LLM 输出的 plan 不合法（Schema 校验失败） | 重试 1 次（将校验错误信息注入 prompt 要求 LLM 修正）。两次均失败 → `ESCALATE` |
| 收敛检测为 `STAGNATION` 但 `force_tool_rotation` 后候选工具为空 | 已经没有可换的工具 → `ESCALATE` |
| LLM 输出的 `estimated_tokens` 超过预算 | 要求 LLM 缩小计划范围（减少工具数量或选择更轻量的工具），重试 1 次。仍不满足 → `ESCALATE` |
| `task_list.current_subtask` 为 None | 说明所有子任务已完成或任务清单尚未生成。若是前者 → 标记 `is_final_iteration = True`，plan 为「汇总报告」；若是后者 → 首轮 plan 为「分析并拆解任务」 |

## 5. Phase 3：执行与工具编排 (Execute & Orchestrate)

### 5.1 形式化定义

**Phase 3 的核心职责**：将 Phase 2 的结构化计划转换为实际的工具调用序列，收集每次调用的结果，形成结构化的执行记录。

形式化地：

```
Execute: (PlanWithTools, ContextBundle, ToolOrchestrator, PermissionGate) → ExecutionResult
```

**为什么 Phase 3 需要工具编排器（Tool Orchestrator）作为中介。** Phase 3 不直接调用裸工具。每一工具调用都必须经过工具编排器的包装——编排器负责：参数校验、权限前置检查、超时控制、重试策略、结果格式化。这样做的原因是：如果 Phase 3 直接调用裸工具，那么超时处理、重试逻辑、错误格式化会散布在 Phase 3 的代码中，导致 Phase 3 的复杂度与工具数量成正比增长。通过编排器这一抽象层，Phase 3 的代码与具体工具解耦。

### 5.2 输入/输出契约

```
输入 (Input):
  plan: PlanWithTools                        # Phase 2 的输出
  context: ContextBundle                     # Phase 1 的输出
  tool_orchestrator: ToolOrchestrator         # 工具编排模块
  permission_gate: PermissionGate            # 权限闸
  subagent_manager: SubagentManager | None   # 子代理管理器（可选）

输出 (Output):
  result: ExecutionResult
    ├── iteration_id: str                    # 与 plan.iteration_id 对应
    ├── tool_calls: ToolCallRecord[]          # 每次工具调用的完整记录
    │   ├── tool_name: str
    │   ├── arguments: dict
    │   ├── result: ToolResult               # 结构化的成功/失败
    │   ├── duration_ms: int
    │   └── permission_blocked: bool
    ├── artifacts: Artifact[]                # 产生的文件、截图等
    ├── exceptions: OrchestratedError[]       # 结构化的异常列表
    ├── total_duration_ms: int
    └── messages_appended: Message[]          # 本轮新增的 messages
```

**数据契约的强制约束**：

1. `ToolCallRecord.result` 必须是结构化的 `ToolResult`（包含 `success: bool`、`error_type: str`、`error_message: str`、`suggestion: str`），绝不能是裸字符串
2. 每个工具调用前必须先通过 `permission_gate.check()` — 权限拒绝时返回 `ToolResult.permission_denied()` 而非抛异常
3. `messages_appended` 必须在每次工具调用后**增量追加**（不等所有调用完成），以保证即使后续工具失败，已完成的部分结果仍然可审计
4. 若 `execution_strategy = PARALLEL`，通过 `subagent_manager` 并发执行，每个子代理拥有独立的四相循环实例

### 5.3 核心处理逻辑

```python
async def execute_and_orchestrate(
    plan: PlanWithTools,
    context: ContextBundle,
    tool_orchestrator: ToolOrchestrator,
    permission_gate: PermissionGate,
    subagent_manager: SubagentManager | None = None,
) -> ExecutionResult:
    tool_calls: list[ToolCallRecord] = []
    artifacts: list[Artifact] = []
    messages_appended: list[Message] = []

    if plan.execution_strategy == ExecutionStrategy.PARALLEL and subagent_manager:
        # 可并行的工具调用 → 委托子代理并发执行
        results = await subagent_manager.dispatch_parallel(
            tools=plan.selected_tools, context=context)
        # ... 收集结果到 tool_calls, artifacts

    elif plan.execution_strategy == ExecutionStrategy.CONDITIONAL:
        # 有条件依赖 → 串行但根据中间结果动态调整后续调用
        results = await _execute_conditional(plan, context, tool_orchestrator)

    else:  # SEQUENTIAL
        for tool_binding in plan.selected_tools:
            # 权限前置检查
            permission = await permission_gate.check(
                tool_name=tool_binding.name,
                tool_args=tool_binding.arguments)
            if not permission.allowed:
                denied = ToolResult.permission_denied(
                    tool_name=tool_binding.name,
                    reason=permission.reason,
                    suggestion=permission.suggestion)
                tool_calls.append(ToolCallRecord(
                    tool=tool_binding.name,
                    result=denied,
                    permission_blocked=True))
                messages_appended.append(denied.to_message())
                continue  # 跳过该工具，不阻断整个 Phase

            # 通过编排器执行（含超时、重试、结果格式化）
            orchestrated = await tool_orchestrator.execute(
                tool_name=tool_binding.name,
                arguments=tool_binding.arguments,
                timeout_ms=tool_binding.timeout_ms or 30_000,
                retry_policy=tool_binding.retry_policy)
            tool_calls.append(ToolCallRecord(
                tool=tool_binding.name,
                arguments=tool_binding.arguments,
                result=orchestrated,
                duration_ms=orchestrated.metadata.duration_ms))
            messages_appended.append(orchestrated.to_message())
            if orchestrated.metadata.artifacts:
                artifacts.extend(orchestrated.metadata.artifacts)

    return ExecutionResult(
        iteration_id=plan.iteration_id,
        tool_calls=tool_calls,
        artifacts=artifacts,
        exceptions=[tc.result for tc in tool_calls if not tc.result.success],
        total_duration_ms=sum(tc.duration_ms for tc in tool_calls),
        messages_appended=messages_appended,
    )
```

### 5.4 边界条件与异常处理

| 边界条件 | 处理策略 |
|---------|---------|
| 所有工具调用都因权限被拒 | 无任何可执行的操作。Phase 3 仍正常返回 `ExecutionResult`（所有 `ToolCallRecord.permission_blocked = True`），由 Phase 4 判定为 `ESCALATE` |
| 某工具调用超时 | 由工具编排器的重试策略处理（指数退避，最多 3 次）。3 次均超时 → `ToolResult(success=False, error_type="TIMEOUT")` |
| 执行过程中 `asyncio.CancelledError` | 停止执行后续工具；已完成的工具调用记录不丢失；将当前状态通过 Phase 边界 checkpoint 持久化；重新抛出 `CancelledError` |
| `subagent_manager.dispatch_parallel` 中某一子代理崩溃 | 子代理的崩溃不传播到主循环。该子代理返回 `ToolResult(success=False, error_type="SUBAGENT_CRASH")`；其他子代理继续执行 |
| 工具返回的数据量过大（如读取了一个 50MB 的日志文件） | 工具编排器执行**结果截断**：保留前 2000 字符和后 500 字符，中间替换为 `[…truncated N chars…]`；在 metadata 中记录原始大小 |

## 6. Phase 4：验证与反馈修正 (Verify & Correct)

### 6.1 形式化定义

**Phase 4 的核心职责**：对 Phase 3 的执行结果做出**有证据支撑的裁决**，并决定下一轮迭代的流转方向。

形式化地：

```
Verify: (ExecutionResult, PlanWithTools, Subtask) → VerificationVerdict
```

**Phase 4 是四相循环中最关键的一相。** 一个薄弱的 Phase 4（例如只检查 `tool_calls` 中是否有 `success=False`，或只信任 LLM 的自我评价）会使整个四相循环退化回 Naive 循环——因为循环失去了唯一的外部、客观的收敛信号。

Phase 4 的设计原则是**分层验证（Layered Verification）**：

- **L1 — 语法/格式验证**：工具返回的结构是否完整？必填字段是否存在？返回类型是否与 Schema 一致？
- **L2 — 功能/单元验证**：执行结果是否通过了针对该子任务的测试用例？
- **L3 — 集成/端到端验证**：在真实环境中，产出物是否能正常工作？
- **L4 — 人工验证**：对于高风险操作，暂停并等待人工确认。

每一层验证失败时**立即返回失败裁决**，不继续后续层（快速失败原则）。

### 6.2 输入/输出契约

```
输入 (Input):
  result: ExecutionResult                    # Phase 3 的输出
  plan: PlanWithTools                        # Phase 2 的输出（用于比对预期）
  subtask: Subtask                           # 当前子任务（含验收标准）
  verify_loop: VerifyLoop                    # 验证循环模块
  convergence: ConvergenceController         # 收敛控制器

输出 (Output):
  verdict: VerificationVerdict
    ├── iteration_id: str
    ├── passed: bool                         # 本轮是否通过验证
    ├── level: VerificationLevel             # L1_COMPILE | L2_UNIT_TEST | L3_E2E | L4_HUMAN
    ├── evidence: VerificationEvidence[]     # 验证证据（测试输出、截图、diff）
    ├── score: float | None                  # 评分（如果适用，0.0-10.0）
    ├── action: PhaseAction                  # NEXT | RETRY | RETRY_WITH_NEW_STRATEGY | ESCALATE | DONE
    ├── retry_context: FailureContext | None # 如果 RETRY，提供修正上下文
    └── completion_signal: CompletionSignal | None  # 如果 DONE，提供完成信号
```

**VerificationVerdict.action 的决策矩阵**：

| 条件 | action |
|------|--------|
| 全部验证通过 + 所有子任务完成 | `DONE` |
| 全部验证通过 + 还有子任务未完成 | `NEXT` |
| L1 失败（编译/格式错误） | `RETRY`（信号明确，直接重试） |
| L2 失败（功能/单元测试），且是首次失败 | `RETRY` |
| L2 失败，且与上一轮是同类错误 | `RETRY_WITH_NEW_STRATEGY` |
| L3 失败（E2E） | `RETRY_WITH_NEW_STRATEGY` |
| 同一子任务连续失败 3 次 | `ESCALATE` |
| Token 预算耗尽 | `ESCALATE` |

### 6.3 核心处理逻辑

```python
async def verify_and_correct(
    result: ExecutionResult,
    plan: PlanWithTools,
    subtask: Subtask,
    verify_loop: VerifyLoop,
    convergence: ConvergenceController,
) -> VerificationVerdict:
    # 收敛前置检查：同一子任务连续失败 3 次 → 直接 ESCALATE
    if convergence.consecutive_failures >= 3:
        return VerificationVerdict(
            iteration_id=plan.iteration_id, passed=False,
            level=VerificationLevel.L1_COMPILE,
            action=PhaseAction.ESCALATE,
            retry_context=FailureContext(
                reason=f"子任务 {subtask.id} 连续失败 3 次"))

    # L1: 编译/语法验证
    if subtask.requires_compile_check:
        l1 = await verify_loop.run_compile_check(result)
        if not l1.passed:
            return _fail_verdict(plan, VerificationLevel.L1_COMPILE,
                [l1], convergence, subtask)

    # L2: 单元/功能验证
    if subtask.requires_unit_test:
        l2 = await verify_loop.run_tests(subtask.test_target, incremental=True)
        if not l2.passed:
            return _fail_verdict(plan, VerificationLevel.L2_UNIT_TEST,
                [l2], convergence, subtask)

    # L3: 端到端验证
    if subtask.requires_e2e_verification:
        l3 = await verify_loop.run_e2e(subtask)
        if not l3.passed:
            return VerificationVerdict(
                iteration_id=plan.iteration_id, passed=False,
                level=VerificationLevel.L3_E2E,
                evidence=[l3],
                action=PhaseAction.RETRY_WITH_NEW_STRATEGY,
                retry_context=FailureContext.from_l3(l3))

    # 全部通过 — 检查是否还需继续
    if subtask.task_list.all_completed():
        return VerificationVerdict(
            iteration_id=plan.iteration_id, passed=True,
            level=VerificationLevel.L2_UNIT_TEST,
            action=PhaseAction.DONE,
            completion_signal=CompletionSignal(
                summary=f"任务完成：{subtask.task_list.completed_count}/{subtask.task_list.total_count}",
                total_iterations=convergence.total_iterations,
                estimated_cost=convergence.estimated_cost))

    return VerificationVerdict(
        iteration_id=plan.iteration_id, passed=True,
        level=VerificationLevel.L2_UNIT_TEST,
        action=PhaseAction.NEXT)
```

### 6.4 边界条件与异常处理

| 边界条件 | 处理策略 |
|---------|---------|
| 子任务不要求任何验证（如纯只读查询） | 跳过 L1-L3，直接以 `passed=True` 返回。但仍检查 `result.exceptions`：若有异常 → 标记 `passed=False, action=RETRY` |
| 验证工具本身执行失败（如 pytest 崩溃） | 这是**元失败（Meta-Failure）**——验证工具不可用。不标记子任务失败，标记为 `VERIFY_TOOL_UNAVAILABLE`，返回 `RETRY`（等待验证工具恢复）；记录 `verify_tool_failure` 事件 |
| `plan.expected_outcome` 为空 | 无法做预期比对。降级为仅做 L1 格式验证（检查 `ToolResult.success` 和必填字段完整性） |
| 验证证据（如测试输出）超过 token 限制 | 截断到 3000 tokens（保留前 2000 + 后 1000），中间替换为截断标记。原始完整证据存储到文件路径，在 `VerificationEvidence` 中记录该文件路径 |
| L4 人工验证超时 | 设置人工验证的超时时间（如 30 分钟）。超时后自动降级：若 L1-L3 全部通过 → 以 `passed=True, action=DONE` 继续（承担剩余风险）；记录 `human_verify_timeout` 事件 |

## 7. 状态机与流转规则

### 7.1 合法状态转换图

```
                        ┌─────────┐
                        │  IDLE   │  ← 初始 / Session 恢复后
                        └────┬────┘
                             │ start()
                             ▼
                   ┌─────────────────────┐
                   │  PHASE_1: PERCEIVE  │  ← 感知与上下文装配
                   └──────────┬──────────┘
                              │ ContextBundle 就绪
                              ▼
                   ┌─────────────────────┐
                   │  PHASE_2: PLAN      │  ← 规划与工具决策
                   └──────────┬──────────┘
                              │ PlanWithTools 校验通过
                              ▼
                   ┌─────────────────────┐
                   │  PHASE_3: EXECUTE   │  ← 执行与工具编排
                   └──────────┬──────────┘
                              │ ExecutionResult 收集完毕
                              ▼
                   ┌─────────────────────┐
                   │  PHASE_4: VERIFY    │  ← 验证与反馈修正
                   └──┬───┬───┬────┬────┘
                      │   │   │    │
          ┌───────────┘   │   │    └──────────────┐
          ▼               │   ▼                    ▼
   ┌────────────┐    ┌────┴──────┐    ┌──────────────────┐
   │  DONE (终止)│    │ ESCALATE  │    │ PHASE_1 (下一轮) │
   │ 任务完成     │    │ (升人工)   │    │ 下一个子任务       │
   └────────────┘    └───────────┘    └──────────────────┘

异常跳转（任意 Phase 均可触发）:
  - 任意 Phase 内 timeout     → INTERRUPTED → 保存 checkpoint → 终止
  - 任意 Phase 内 crash       → CRASHED → 下次启动从最近的 checkpoint 恢复
  - PHASE_3 权限被全部拒绝     → ESCALATE（没有可执行的操作）
  - Token 预算耗尽             → DEGRADED_COMPLETION → 优雅降级终止
  - 用户手动中止               → CANCELLED → 保存 checkpoint → 终止
```

### 7.2 流转规则的形式化定义

Phase 之间的流转不是由代码中的固定调用顺序决定的，而是由 Phase 4 产出的 `VerificationVerdict.action` 驱动：

| 当前 Phase | Verdict.action | 下一 Phase | 说明 |
|-----------|---------------|-----------|------|
| VERIFY | `NEXT` | PERCEIVE (下一子任务) | 当前子任务通过验证，推进到下一个子任务 |
| VERIFY | `RETRY` | PERCEIVE (同一子任务) | 重试当前子任务，注入 `previous_failure` |
| VERIFY | `RETRY_WITH_NEW_STRATEGY` | PLAN (同一子任务) | 跳过 Phase 1，从 Phase 2 重新规划 |
| VERIFY | `ESCALATE` | 终止 (升人工) | 记录升人工原因和当前状态 |
| VERIFY | `DONE` | 终止 (正常完成) | 输出 CompletionSignal |
| 任意 Phase | (超时/crash) | 终止 → 下次恢复 | 保存 checkpoint |

### 7.3 收敛控制器

收敛控制器（ConvergenceController）是实现「强制收敛」的核心组件。它维护硬限制（Hard Limits）和软收敛（Soft Convergence）两层策略：

```python
@dataclass
class ConvergenceController:
    # ── 硬限制：绝对不可逾越 ──
    max_total_iterations: int = 25           # 总迭代次数上限
    max_iterations_per_subtask: int = 5      # 单个子任务最大重试
    max_session_duration_seconds: int = 3600  # 1 小时绝对上限

    # ── 软收敛：达到阈值触发策略变更而非直接终止 ──
    max_consecutive_failures: int = 3        # 连续失败 → 升人工
    max_no_progress_streak: int = 3          # 连续无进展 → 终止
    max_similar_plan_streak: int = 2         # 相同 plan 连续出现 → 换策略

    # ── 运行时状态 ──
    total_iterations: int = 0
    subtask_iterations: dict[str, int] = field(default_factory=dict)
    consecutive_failures: int = 0
    no_progress_streak: int = 0
    previous_plan_objectives: list[str] = field(default_factory=list)

    def should_continue(self, phase: Phase,
                        verdict: VerificationVerdict | None = None) -> StopDecision:
        self.total_iterations += 1

        # 硬限制优先
        if self.total_iterations >= self.max_total_iterations:
            return StopDecision.STOP_HARD_LIMIT
        if self._session_elapsed() >= self.max_session_duration_seconds:
            return StopDecision.STOP_TIMEOUT

        # 连续失败检测
        if verdict and not verdict.passed:
            self.consecutive_failures += 1
            self.no_progress_streak += 1
            if self.consecutive_failures >= self.max_consecutive_failures:
                return StopDecision.ESCALATE
            if self.no_progress_streak >= self.max_no_progress_streak:
                return StopDecision.STOP_STAGNATION
        else:
            self.consecutive_failures = 0
            self.no_progress_streak = 0

        return StopDecision.CONTINUE
```

**收敛控制器的设计原则**：(a) 硬限制是安全网，不是常规退出路径——如果任务频繁因硬限制终止，说明任务拆解粒度或收敛策略需要调整；(b) 软收敛的阈值应可配置且可按子任务类型差异化——例如 `code_generation` 子任务的 `max_iterations_per_subtask` 应高于 `file_read` 子任务；(c) 所有收敛事件（触发硬限制、触发软收敛、升人工）必须产出结构化日志。

## 8. 生产级横切关注点

### 8.1 可观测性设计

可观测性（Observability）不是事后添加的「打印日志」，而是四相循环的**一等设计约束**。每个 Phase 的进入和退出必须产出结构化日志，携带一致的上下文标签。

**日志规范**：

```
所有日志必须携带以下标签:
  - task_id: str          # 任务唯一标识
  - iteration: int        # 当前迭代轮次
  - phase: str            # 当前 Phase (perceive|plan|execute|verify)
  - subtask_id: str       # 当前子任务 ID（如有）
```

**核心指标**：

| 指标名 | 类型 | 描述 |
|-------|------|------|
| `four_phase_loop.iteration.total` | Counter | 总迭代次数 |
| `four_phase_loop.phase.duration_ms` | Histogram | 每相耗时分布（按 phase 标签分组） |
| `four_phase_loop.phase.token_consumed` | Histogram | 每相 token 消耗分布 |
| `four_phase_loop.verify.pass_rate` | Gauge | Phase 4 验证通过率（最近 100 轮滑动窗口） |
| `four_phase_loop.verify.fail_by_level` | Counter | 按 L1/L2/L3/L4 分组的验证失败次数 |
| `four_phase_loop.convergence.escalation_rate` | Gauge | 升人工率（最近 100 个任务） |
| `four_phase_loop.convergence.stagnation_count` | Counter | 僵化检测触发次数 |
| `four_phase_loop.context.pruning_ratio` | Gauge | 上下文裁剪比例（裁剪后/裁剪前） |

**告警规则**：

- `phase.duration_ms` P99 > 60s → 告警（某个 Phase 执行异常缓慢）
- `verify.pass_rate` < 50%（30 分钟滑动窗口）→ 告警（验证通过率异常低，可能是验证逻辑自身有问题或模型存在系统性问题）
- `escalation_rate` > 20% → 告警（过多任务需要人工介入，可能是任务拆解粒度过细或模型能力不足）
- `context.pruning_ratio` > 0.9 → 告警（裁剪过于激进，可能丢失关键信息）

### 8.2 可恢复性设计

可恢复性（Recoverability）的核心机制是**相间检查点（Phase Checkpoint）**。每次 Phase 完成后、进入下一个 Phase 之前，将当前状态原子写入持久化存储。

**Checkpoint 数据结构**：

```python
@dataclass
class PhaseCheckpoint:
    task_id: str
    iteration: int
    current_phase: Phase              # 刚完成的 Phase
    phase_output: dict                # 当前 Phase 的产出物（ContextBundle / PlanWithTools / ExecutionResult / VerificationVerdict）
    progress_summary: ProgressSummary  # 进度摘要
    created_at: datetime
    ttl_seconds: int = 86400          # 24 小时后自动清理
```

**Checkpoint 的写入约束**：

1. **原子写入**：先写 `.tmp` 文件，完成后再 `rename`（POSIX 原子操作）。防止写入中途 crash 导致 checkpoint 损坏。
2. **版本标记**：每次写入携带 schema 版本号。恢复时检查版本兼容性。
3. **TTL 机制**：checkpoint 不是永久数据，24 小时后自动清理。长期状态应通过进度跟踪模块管理。
4. **写入频率**：每 Phase 完成后写入 1 次。不写入 Phase 内部中间状态（避免性能开销）。

**恢复流程**：

```
Session 启动:
  1. 检查是否存在未过期 checkpoint
  2. 若存在:
     a. 恢复 task_id, iteration, current_phase
     b. 恢复 phase_output（上一个 Phase 的产出物）
     c. 从 current_phase 的下一个 Phase 开始继续执行
     d. 记录 resume 事件
  3. 若不存在:
     a. 从 IDLE 开始全新执行
```

**关键设计决策**：恢复粒度是 Phase 级别而非工具调用级别。如果 Phase 3 在执行第 3 个工具时 crash，恢复后 Phase 3 会从头执行该 Phase（重新执行所有工具调用）。这就要求 Phase 3 中使用的工具要么是幂等的，要么由工具编排层通过幂等性 token 保证重复调用的安全性。

### 8.3 可中断性设计

可中断性（Interruptibility）指的是四相循环能够在收到外部中断信号（SIGTERM、用户取消、超时）时，安全地停止执行并保存当前状态。

**中断信号类型与处理策略**：

| 信号 | 触发条件 | 处理策略 |
|------|---------|---------|
| `SIGTERM` / `SIGINT` | 进程被终止 / 用户 Ctrl+C | 完成当前 Phase 后保存 checkpoint → 退出 |
| `CancelledError` | asyncio 任务被取消 | 在最近的相变边界捕获 → 保存 checkpoint → 重新抛出 |
| Phase 超时 | 当前 Phase 执行时间超过 `timeout_seconds` | 强制中断当前 Phase → 保存 checkpoint（标记为 `timeout`）→ 退出 |
| Session 超时 | `max_session_duration_seconds` 到期 | 完成当前 Phase 后不进入下一 Phase → 输出进度摘要 → 退出 |
| Token 预算耗尽 | `token_budget.remaining ≤ 0` | 跳过剩余 Phase → 输出已完成工作的摘要 → 降级终止 |

**实现要点**：

```python
async def _run_phase(self, phase_enum: Phase, ctx: PhaseContext) -> PhaseContext:
    try:
        result_ctx = await asyncio.wait_for(
            self.phases[phase_enum].execute(ctx),
            timeout=self.phases[phase_enum].timeout_seconds)
    except asyncio.TimeoutError:
        logger.error("phase.timeout", task_id=ctx.task_id, phase=phase_enum.value)
        ctx.data["phase_error"] = f"{phase_enum.value}_timeout"
        # 超时后仍保存 checkpoint（当前 Phase 的部分产出可能仍有价值）
        await self._save_checkpoint(ctx, phase_enum)
        raise PhaseTimeoutError(phase_enum)
    except asyncio.CancelledError:
        logger.warning("phase.cancelled", task_id=ctx.task_id, phase=phase_enum.value)
        await self._save_checkpoint(ctx, phase_enum)
        raise  # 重新抛出，让上层处理
    return result_ctx
```

**设计原则**：(a) 中断不丢数据——任何中断都必须在保存 checkpoint 后才能退出；(b) 中断点只在相变边界——Phase 执行中途不响应中断（保证 Phase 内状态的局部一致性）；(c) 中断信息对用户透明——用户恢复时，应被告知中断原因、中断位置、已完成和未完成的工作。

## 10. 常见反模式与陷阱

### 10.1 相位泄漏 (Phase Leakage)

**症状**：某一 Phase 的代码中混入了属于另一 Phase 的逻辑。最常见的形态：Phase 3 的执行代码中嵌入验证逻辑（`if result.contains("error"): retry()`），绕过了 Phase 4 的统一裁决。

**后果**：验证逻辑散落各处，没有统一的验证层级、没有收敛检测、没有重试上限。某 FinTech 公司的内部 Agent 因在 Phase 3 中嵌入隐式重试逻辑，导致同一 bug 被「修复」8 次而从未触发 Phase 4 的 ESCALATE。

**解决**：在类型层面强制执行职责边界。Phase 3 的返回值类型是 `ExecutionResult`，其字段列表不包含任何验证结论（如 `passed: bool`）。验证结论只能由 Phase 4 产出。

### 10.2 Phase 4 薄弱化 (Weak Phase 4)

**症状**：Phase 4 只做表面验证——检查 `ToolResult.success == True`，或仅让 LLM 自我评价——而没有分层真机验证。

**后果**：四相循环退化回 Naive 循环。Phase 4 失去了作为独立、客观收敛信号源的价值。

**识别方法**：如果 Phase 4 的代码中不包含任何外部工具调用（pytest、linter、Playwright、API 请求），说明 Phase 4 薄弱。

### 10.3 状态膨胀 (State Bloat)

**症状**：`PhaseContext.data` 字典在多轮循环后膨胀到数百个 key，每次 checkpoint 序列化耗时超过 2 秒。

**根因**：每轮 Phase 3 的工具返回被完整存入 `ctx.data`，未被及时释放。

**解决**：(a) 大对象（超过 10KB）存储引用（文件路径或对象键）而非值；(b) checkpoint 写入时对 `data` 做深度截断；(c) 已完成子任务的中间状态在 Phase 1 中通过 TTL 机制自动清理。

### 10.4 忽略幂等性假设

**症状**：Phase 3 中某个工具调用超时后被重试，但工具本身非幂等（如 `write_file`），导致文件内容被重复拼接。

**根因**：四相循环的设计隐含假设：恢复时可能重新执行已执行过的 Phase。如果 Phase 内的操作不幂等，重复执行会产生副作用累积。

**解决**：(a) 工具编排层支持幂等性 token——同一 token 的操作只执行一次；(b) 写操作使用「临时文件 + 原子 rename」模式；(c) 如果工具不可改造为幂等，则在 Phase 3 中标记该工具为 `non_idempotent`，恢复时跳过该工具并记录警告。

### 10.5 硬编码相位顺序

**症状**：`await phase1(); await phase2(); await phase3(); await phase4()` 硬编码在代码中，无法处理 Phase 4 判决 `RETRY_WITH_NEW_STRATEGY` 时直接从 Phase 4 跳到 Phase 2 的需求。

**解决**：相位的流转必须由状态机驱动，而非硬编码顺序。循环控制器的 `run()` 方法依据 Phase 4 的 `Verdict.action` 决定下一 Phase，而不是无条件推进。

## 12. 总结

1. **四相循环解决的是控制流问题**——Agent 不是不够聪明，而是缺乏一个结构化的执行节律来保证收敛。四相循环通过三个相变边界将连续的执行流切分为四个独立可验证的阶段。

2. **Phase 1（感知装配）的核心不是「收集信息」而是「裁剪信息」**。在 token 预算约束下，选择性地保留与当前子任务相关的上下文，是防止 Context 溢出的第一道防线。

3. **Phase 4（验证修正）是四相循环的心脏**。分层验证（L1→L2→L3→L4）和收敛控制器共同构成了防止循环失控的双重保障。Phase 4 薄弱 = 四相循环退化回 Naive 循环。

4. **相变边界是生产级能力的基础**。可观测性（结构化日志 + 指标）、可恢复性（checkpoint + 原子写入）、可中断性（超时控制 + 优雅降级）——全部依赖于明确的相变边界。没有相变边界，这些能力就无法系统性地实现。

5. **量化所有关键路径**：每相耗时分布、验证通过率、收敛触发频次、升人工率。只有量化才能知道 Harness 在哪个环节、哪个 Phase、哪种任务类型上表现不足——进而针对性地优化。
