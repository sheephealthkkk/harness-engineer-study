# 机制详解：任务拆解 (Task Decomposition)

> **对应失效**：② Context 溢出 (Context Overflow) —— 根源治理
> **核心贡献**：把大任务拆解成 JSON 格式的子任务清单，强制 Agent 每次迭代只处理一件事。每次事后标记状态再取下一件。
> **所属支柱**：输入流（限制视野）、控制流（分步约束）、状态流（减少单任务负担）

---

## 一、Context 溢出的根源

### 1.1 为什么 Agent 的 context 会爆炸？

表面原因是 messages 无限增长。但根源是 **Agent 一次想做的事太多了**：

```
Agent 一次想做 10 件事:
  → 每轮思考: 这 10 件事的策略、依赖关系、优先级排序
  → 每轮行动: 可能切换在不同事之间
  → 每轮结果: 10 件事的中间结果都在 context 里
  → Context 必然爆炸

Agent 一次只做 1 件事:
  → 每轮思考: 只关注这 1 件事
  → 每轮行动: 只围绕这 1 件事
  → 完成 → 保存摘要 → 忘记细节 → 下一件
  → Context 保持精简
```

**上下文工程（压缩）是治标，任务拆解是治本。**

### 1.2 任务拆解的理念

> 不是让 Agent 少干活，而是让 Agent **每次只专注于一件事**，
> 完成后再专注于下一件事。// "分而治之"的工程化表达。

### 2.2 任务清单的关键字段

```
每个子任务必须包含:
  - id: 唯一标识（数字或短字符串）
  - description: 人类可读的任务描述（一句话说清楚）
  - phase: 阶段分类 (analyze / design / implement / verify)
  - status: 当前状态 (pending / in_progress / completed / failed / skipped / blocked)
  - depends_on: 前置依赖的子任务 ID 列表
  - verification_method: 验证方式
  - verification_criteria: 明确的验收标准（关键是"明确" —— 不能模糊）

鼓励包含:
  - parallel_group: 并行组标识（同组子任务可以并行执行）
  - estimated_tokens: 预估 token 消耗
  - output_summary: 完成后的产出摘要（后续子任务不需要知道细节）
```

## 三、任务拆解的原则

### 3.1 原子性原则

```
好的拆解: 每个子任务只做一件可验证的事

❌ "实现导出功能"
   太粗，包含后端 + 前端 + 多种格式 + 测试

✅ "实现 CSV 导出核心逻辑"
   明确、可独立完成、可独立验证

❌ "优化代码"
   太模糊，不知道要做什么、不知道什么时候算做好

✅ "将 UserService.getUserById 的查询从 3 次 N+1 优化为 1 次 JOIN 查询"
   明确、可验证（看 SQL 日志）
```

### 3.2 可验证性原则

```python
# 每个子任务必须有明确的验收标准

# ❌ 模糊的验收标准
verification_criteria: "确保功能正确"
# → 什么叫"正确"？无法自动化验证

# ✅ 明确的验收标准
verification_criteria: "单元测试 test_csv_export_normal, test_csv_export_empty, "
                       "test_csv_export_large(10K rows) 全部通过"
# → 可以用 pytest 自动化验证，通过/不通过是明确的
```

### 3.3 有序依赖原则

```
analyze → design → implement → verify

每个阶段依赖前一个阶段的产出：
  design 依赖 analyze 的结论（字段清单、现有工具情况）
  implement 依赖 design 的方案（API 设计、脱敏规则）
  verify 依赖 implement 的代码（完整的实现）
```

### 3.4 可并行标记原则

```
parallel_group 机制：

同一 parallel_group 的子任务没有相互依赖 → 可以并行

示例：
  parallel_group: "export-impl"
    - id: 3, "实现 CSV 导出"
    - id: 4, "实现 Excel 导出"
  → 可以同时启动两个子代理分别处理
  → 完成后汇总结果再继续 id=5
```

## 四、Agent 如何执行任务清单

### 4.1 任务清单是"路书"

```python
class TaskExecutor:
    """
    Agent 的视角：任务清单 = 每次迭代的路书
    """
    
    def execute_task_list(self, task_list):
        """按任务清单逐项执行"""
        
        for subtask in self.get_next_ready_subtasks(task_list):
            # 检查依赖是否满足
            if not all_deps_completed(subtask.depends_on, task_list):
                continue
            
            # 标记为 in_progress
            subtask.status = "in_progress"
            save_progress(task_list)
            
            # === 执行单个子任务（四相循环） ===
            for iteration in range(MAX_ITERATIONS):
                # GATHER: 只收集与这个子任务相关的上下文
                context = self.gather_for_subtask(subtask)
                
                # ACT: 执行这个子任务的原子操作
                result = self.act_for_subtask(subtask, context)
                
                # VERIFY: 用该子任务指定的验证方式验证
                verification = self.verify_subtask(subtask, result)
                
                if verification.passed:
                    # 完成 → 保存摘要（不需要细节）
                    subtask.status = "completed"
                    subtask.output_summary = self.summarize(result)
                    save_progress(task_list)
                    
                    # Context 清理：上一个子任务的细节可以压缩了
                    self.context_manager.forget_subtask_details(subtask.id)
                    break
                else:
                    # 失败 → 重试或标记失败
                    if iteration >= MAX_RETRIES:
                        subtask.status = "failed"
                        save_progress(task_list)
                        self.handle_failure(subtask)
                    else:
                        # 注入失败上下文，重试
                        self.context_manager.inject_failure_context(subtask, verification)
    
    def get_next_ready_subtasks(self, task_list):
        """
        找到下一个（批）可以执行的子任务
        考虑依赖关系和并行组
        """
        ready = []
        
        for subtask in task_list.subtasks:
            if subtask.status != "pending":
                continue
            
            # 检查依赖
            deps_ready = all(
                task_list.get(dep_id).status == "completed"
                for dep_id in subtask.depends_on
            )
            
            if deps_ready:
                ready.append(subtask)
        
        # 如果有并行组，返回同组的所有就绪子任务
        # 主 Agent 可以决定启动子代理并行处理
        return ready
```

### 4.2 与四相循环的配合

```
四相循环 ≈ 每个子任务的"微观执行引擎"
任务清单 ≈ 整个任务的"宏观路线图"

宏观: 任务清单
  子任务 1 → 子任务 2 → 子任务 3 → ... → 全部完成
                ↑
微观: 四相循环 (每个子任务内部)
  GATHER → ACT → VERIFY → ITERATE → (通过) → 下一个子任务
```

## 五、拆解策略

### 5.1 自上而下拆解 (Top-Down)

```
适合: 目标明确、有参考经验的任务

1. 先确定顶层阶段: analyze → design → implement → verify
2. 每个阶段拆成 2-5 个原子子任务
3. 确定依赖关系
4. 标记并行可能性
```

### 5.2 增量拆解 (Incremental)

```
适合: 探索性任务，事前不知道全部工作量

1. 先只拆解第一步（如 "分析用户需求"）
2. 完成第一步后，根据分析结果拆解后续步骤
3. 每完成一个阶段，规划下一个阶段
4. 保持任务清单的动态性——子任务可以增加、修改、删除

实现:
  task_list 允许在执行过程中追加、调整未开始的子任务
  已完成的子任务不可修改（保证审计追溯）
```

### 5.3 LLM 辅助拆解

```python
def decompose_task_with_llm(task_description, project_context):
    """
    使用 LLM 来做一个初始的任务拆解
    然后由 Harness 系统（或者人工）审核、修正
    """

        {"role": "user", "content": json.dumps({
            "task": task_description,
            "project_context": project_context,
            "requirements": [
                "每个子任务必须是原子的、可独立验证的",
                "必须标注依赖关系",
                "必须为每个子任务指定验证方式",
                "尽可能标记可并行的子任务 (parallel_group)",
                "预计每个子任务的 token 消耗"
            ]
        })}
    ])
    
    # LLM 返回 task_list JSON
    task_list = json.loads(response.content)
    
    # 验证 task_list 的正确性
    validate_task_list(task_list)
    
    # 用户确认（重要！任务拆解决定了整个执行方向）
    if not user_approves(task_list):
        return revise_task_list(task_list, user_feedback)
    
    return task_list
```

## 六、与其他机制的协作

| 协作机制 | 协作关系 |
|---------|---------|
| **四相循环** | 任务清单是四相循环的路书，四相循环按清单逐项执行每个子任务 |
| **上下文工程** | 完成子任务后，上下文工程压缩该子任务的细节，只保留摘要 |
| **进度跟踪** | 每个子任务的状态变更 → 触发进度持久化 |
| **子代理分治** | 同 parallel_group 的子任务可以委托给子代理并行执行 |
| **验证循环** | 每个子任务使用其指定的 verification_method 进行验证 |

## 七、总结

任务拆解是 Context 溢出的**根源治理**——不是等 context 满了再想办法，而是不让它有机会满。

核心原则：
1. **原子性**：每个子任务只做一件可独立验证的事
2. **一次一件**：Agent 每轮迭代只关注当前子任务
3. **完成即忘**：子任务完成后保存摘要，释放 context 空间
4. **灵活拆解**：根据任务类型选择自上而下或增量拆解
