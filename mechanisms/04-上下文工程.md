# 机制详解：上下文工程 (Context Engineering)

> **对应失效**：② Context 溢出 (Context Overflow)、③ Cache Miss (Prompt Cache 命中失败)、⑧ 成本失控 (Cost Runaway)
> **核心贡献**：监控 messages 的 token 数量，超过阈值触发压缩或重置；保持 system prompt 前缀绝对稳定以最大化 Prompt Cache 命中。
> **所属支柱**：输入流（主要）、状态流（主要）

---

## 一、上下文工程的三个维度

上下文工程不只是"怎么压缩 context"——那是最后一个维度的最后一招。完整的上下文工程包含三个维度：

```
上下文工程 = 放什么 × 怎么放 × 什么时候清

放什么 (Input Selection):     选择哪些信息进入 Agent 的视野
怎么放 (Format & Layout):     信息以什么结构、什么顺序排列
什么时候清 (Lifecycle):       信息什么时候该被压缩或移除
```

---

## 二、维度一：放什么 (Input Selection)

### 2.1 分层信息模型

```
固定层 (Static Layer) — 跨所有 session 不变
  ├── System Prompt (角色定义、行为准则、工具使用规范)
  ├── CLAUDE.md (项目级配置：编码规范、常用命令、注意事项)
  └── Tool Definitions (可用工具的 Schema 定义)

会话层 (Session Layer) — 当前 session 存活
  ├── 用户任务描述
  ├── 对话历史 (messages)
  ├── 子代理返回的结果摘要
  └── 压缩后的历史摘要

动态层 (Dynamic Layer) — 每次请求可能变化
  ├── 当前时间和工作目录
  ├── Git 状态 (当前分支、未提交文件)
  ├── Progress 信息 (当前子任务、已完成进度)
  ├── 当前文件内容 (read_file 的结果)
  └── 检索结果 (grep/glob 的输出)
```

### 2.2 信息放入决策树

```python
def should_include_in_context(information, task, progress):
    """
    不是所有信息都值得放进 context。
    每一条放入 context 的信息都在消耗 tokens → 消耗金钱和空间。
    """
    
    # 相关度检查
    if not is_relevant_to_current_subtask(information, progress.current_subtask):
        # 与当前子任务无关 → 排除
        return False
    
    # 时效性检查
    if is_stale(information, max_age_seconds=300):
        # 信息可能过时 → 先刷新再放入
        return refresh_first(information)
    
    # 信息密度检查
    if is_trivial(information):
        # 琐碎信息（如 "命令在 12ms 内执行完毕"） → 排除
        return False
    
    # 大小检查
    if len(information) > MAX_SINGLE_ITEM_TOKENS:
        # 单条信息太大 → 先摘要/截断再放入
        return summarize_first(information)
    
    return True
```

### 2.3 CLAUDE.md：项目级的固定上下文

CLAUDE.md 是上下文工程中"固定层"的核心。它存放的是**不随任务变化而变化**的项目级信息。

```markdown
# CLAUDE.md 示例

## 项目信息
- 项目名称: E-Commerce Platform
- 语言: Python 3.12 + TypeScript 5.5
- 框架: FastAPI (后端) + React 19 (前端)

## 编码规范

- TypeScript: 遵循 Prettier, ESLint strict config
```

## 三、维度二：怎么放 (Format & Layout)

### 3.1 Prompt Cache 友好的布局

这是上下文工程中最容易被忽视但影响最大的设计决策。

**Anthropic Prompt Cache 的工作原理**：
- API 自动识别请求之间的共同前缀
- 共同前缀被缓存，不必重新计算
- 缓存命中后：费用降低 90%，延迟降低 80%
- **关键约束**：只有从 messages 数组**开头**算起的连续相同内容才会被缓存

```python
# ✅ Cache 友好的消息布局
messages = [
    # 第 1 条: System Prompt — 永久不变
    {"role": "system", "content": STABLE_SYSTEM_PROMPT},
    
    # 第 2-N 条: 这些也不变的话，也会被缓存
    # ...
    
    # 尾部: 新内容在最后面追加
    {"role": "user", "content": new_content}
]

# ❌ Cache 不友好的做法
messages[0]["content"] = f"{STABLE_SYSTEM_PROMPT}\n当前时间: {dynamic_time}"
# ↑ 每次时间都不同 → 前缀不同 → Cache 永远不命中 → 每次都全价
```

**正确的动态信息注入**：

```python
# ✅ 把动态信息放在 user message 中，而不是 system prompt 中
messages = [
    {"role": "system", "content": STABLE_SYSTEM_PROMPT},  # ← 绝对不变
    # ...
    {
        "role": "user", 
        "content": json.dumps({
            "type": "system_status",
            "current_time": datetime.now().isoformat(),
            "working_directory": os.getcwd(),
            "git_branch": get_git_branch(),
            "progress": progress.summary()
        })
    }
]
```

**Cache 断点机制**：
Anthropic 允许手动指定 Cache 断点（最多 4 个）。在断点之前的内容会被缓存：

```python
# 使用 cache_control 标注缓存断点
messages = [
    {
        "role": "system",
        "content": [
            {
                "type": "text",
                "text": STABLE_SYSTEM_PROMPT,
                "cache_control": {"type": "ephemeral"}  # ← 断点 1
            }
        ]
    },
    {
        "role": "user",
        "content": [
            {
                "type": "text",
                "text": task_description,
                "cache_control": {"type": "ephemeral"}  # ← 断点 2
            }
        ]
    },
    # 后续消息不设断点，它们会每次重新计算
]
```

### 3.2 Token 预算可视化

```python
class TokenBudget:
    """
    管理整个 session 的 token 使用
    """
    
    # 硬限制
    MAX_CONTEXT_TOKENS = 160_000   # 单次 API 调用最大 context
    MAX_SESSION_TOKENS = 1_000_000 # 整个 session 最大累计 tokens
    
    # 软限制（触发动作）
    WARNING_LEVEL = 80_000    # 警告 Agent 精简输出
    COMPACTION_LEVEL = 120_000  # 触发上下文压缩
    HARD_RESET_LEVEL = 155_000  # 接近极限，强制重置
    
    # 预算消耗追踪
    tokens_used_this_request = 0
    tokens_used_this_session = 0
    estimated_cost = 0.0
    
    def check_before_request(self, messages) -> str:
        """每次 API 调用前检查"""
        
        current_tokens = count_tokens(messages)
        
        if current_tokens > self.HARD_RESET_LEVEL:
            return "HARD_RESET"
        
        if current_tokens > self.COMPACTION_LEVEL:
            return "COMPACT"
        
        if current_tokens > self.WARNING_LEVEL:
            return "WARNING"
        
        if self.tokens_used_this_session > self.MAX_SESSION_TOKENS * 0.9:
            return "SESSION_NEAR_LIMIT"
        
        return "OK"
```

## 四、维度三：什么时候清 (Lifecycle)

### 4.1 三级管理策略

```
L1: 摘要压缩 (Compaction)
  触发: tokens > 120K
  操作: 中间过程的详细信息 → 结构化摘要
  成本: 低（保留语义，丢失细节）
  
L2: 子代理卸载 (Subagent Offload)
  触发: tokens > 140K 且存在可独立执行的子任务
  操作: 把大型独立工作委托给子代理
  成本: 中（子代理有自己独立的 context，返回时才合并）
  
L3: 上下文重置 (Context Reset)
  触发: tokens > 155K
  操作: 保留 system prompt + 进度文件 + 最后 2 轮
        其余的用进度文件中的摘要代替
  成本: 高（损失对话连续性，但进度不丢）
```

### 4.2 L1: 摘要压缩 (Compaction)

```python
def compact_context(messages, progress):
    """
    压缩中间过程：保留头尾，中间替换为摘要
    
    压缩前 (160K tokens):
      [system] [task] [轮1] [轮2] ... [轮35]  ← 太多了
    
    压缩后 (~50K tokens):
      [system] [task] [轮1-33 摘要] [轮34] [轮35]
    """
    
    # 1. 保留头部
    head = messages[0:4]    # system prompt + 任务描述 + 前 2 轮
    
    # 2. 保留尾部（最近的最重要）
    tail = messages[-6:]    # 最后 3 轮交互
    
    # 3. 中间部分生成摘要
    middle = messages[4:-6]
    
    if len(middle) > 0:
        # 提取中间过程的"决策节点"——不只是总结，更是梳理
        key_decisions = extract_key_decisions(middle)
        errors_and_recoveries = extract_errors(middle)
        completed_work = progress.get_completed_summaries()
        
        summary = f"""## 中间过程摘要 ({len(middle)} 轮交互)

### 已完成的工作
{chr(10).join(f'- {w}' for w in completed_work)}

### 关键决策
{chr(10).join(f'- {d}' for d in key_decisions)}

### 遇到的错误与恢复
{chr(10).join(f'- {e}' for e in errors_and_recoveries)}

### 当前状态
- 进度: {progress.completed_count}/{progress.total_count} 子任务完成
- 当前子任务: {progress.current_subtask.description}
"""
        
        # 4. 重组 messages
        compacted = (
            head +
            [{"role": "user", "content": summary}] +
            tail
        )
        
        return compacted
    
    return messages


def extract_key_decisions(messages):
    """
    从中间过程提取关键决策点
    
    不是把所有对话都放到摘要里，而是提取：
    - 方向性决策（如 "我们决定用方案 B 而不是方案 A"）
    - 重要发现（如 "发现 UserService 和 EmailService 有循环依赖"）
    - 策略变更（如 "之前的方案不行，改用流式处理"）
    """
    decisions = []
    for msg in messages:
        if msg.role == "assistant" and contains_decision_marker(msg.content):
            decisions.append(extract_decision(msg.content))
    return decisions
```

### 4.3 L3: 上下文重置 (Context Reset)

```python
def hard_reset_context(messages, progress):
    """
    当压缩也不够时，进行激进重置。
    这不是"丢失信息"——关键信息已经在 progress 文件里了。
    """
    
    # 保留的核心：system prompt + 当前子任务上下文
    reset_messages = [
        messages[0],  # system prompt（永远保留）
        {
            "role": "user",
            "content": json.dumps({
                "type": "context_reset_notice",
                "message": "上下文已重置。之前过程的摘要如下。",
                "task": progress.task_description,
                "completed_work": progress.get_completed_summaries(),
                "current_subtask": {
                    "id": progress.current_subtask.id,
                    "description": progress.current_subtask.description,
                    "attempts_so_far": progress.current_subtask.attempts,
                    "last_error": progress.current_subtask.last_error,
                },
                "environment": {
                    "git_branch": get_git_branch(),
                    "working_directory": os.getcwd(),
                }
            })
        }
    ]
    
    # 保留最近 2 轮交互（维持连续性）
    if len(messages) >= 4:
        reset_messages.extend(messages[-4:])
    
    return reset_messages
```

## 五、Prompt Cache 优化策略汇总

### 5.1 Cache 命中的四大原则

```
1. 前缀稳定原则
   System Prompt 的内容在 session 内绝对不变
   → 把动态信息放在 user message 中

2. 前缀最大化原则
   尽可能把不变的内容放在前面
   → CLAUDE.md 放在 system prompt 中，放在 messages[0]

3. 断点策略原则
   手动标注 cache_control 断点（最多 4 个）
   → 在 system prompt、任务描述、主要工具定义之后设置断点

4. 避免污染原则
   不在 system prompt 后面插入清理、提示等中间消息
   → 需要注入管理信息时，放在新 user message 中
```

### 5.2 Cache 优化后的成本对比

```
同一个任务，100 轮迭代，200K token 上下文窗口:

无 Cache 优化:
  每轮都重新计算整个 context
  平均 context 大小: 100K tokens
  100 轮 × 100K tokens = 10M input tokens
  费用: 10M × $3/1M = $30 (以 Claude Sonnet 为例)

有 Cache 优化:
  System Prompt (10K) + 工具定义 (5K) + 任务描述 (2K) = 17K 被缓存
  每轮实际计算: 100K - 17K × 90% = ~85K (cache 命中部分打 1 折)
  100 轮费用: 17K × $3 × 0.1 + 83K × $3 = ~$25.51 (约节省 15%)
  
长任务中节省更多:
  如果有子代理分治和压缩，context 不会无限增长
  加上 cache 命中 → 费用可节省 40-60%
```

## 六、上下文工程与其他机制的交叉

| 场景 | 上下文工程做什么 | 配合的机制 |
|------|---------------|-----------|
| 新子任务开始 | 注入子任务上下文 + 清除前一个子任务的细节 | 任务拆解 |
| 子代理返回 | 接收子代理的结果摘要（不受子代理中间过程污染） | 子代理分治 |
| Session 崩溃恢复 | 从进度文件重建工作上下文 | 进度跟踪 |
| Context 即将爆炸 | 触发压缩或重置 | (自我触发) |
| 收到系统信号 | 紧急保存当前 context 快照 | 进度跟踪 |

## 七、总结

上下文工程是 Harness 的**内存管理系统**。就像操作系统管理 RAM，上下文工程管理 Agent 的"注意力空间"。

三个核心原则：
1. **该看的时候看清楚**（放什么）——选择最相关的信息进入视野
2. **不变的放前面不动它**（怎么放）——最大化 Prompt Cache 命中
3. **该忘的时候果断忘**（何时清）——通过压缩和重置保持 context 健康

> 上下文工程不是让 Agent 记更多，而是让 Agent 在该记的时候记，在该忘的时候忘。
> 就像人类的注意力——不是把看到的一切都记住，而是聚焦于当前最重要的事。
