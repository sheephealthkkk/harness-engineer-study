## 1. 概述与定位

### 1.1 什么是上下文工程

**上下文工程 (Context Engineering)** 不是"把 prompt 写好"。它是管理 Agent 与 LLM 之间**所有交互信息**的系统性工程方法——覆盖从原始用户输入到最终 LLM API 调用的全流程信息处理管线。

```
上下文工程 ≠ Prompt Engineering

Prompt Engineering 关心: "怎么把话说清楚"（一代工程）
Context Engineering 关心:  "把什么放进去、怎么放、放多少、什么时候清出去"（二代工程）
```

**一句话定义**：上下文工程是 Harness 系统的**内存管理器**——它决定了 LLM 在每一刻"看到什么"，从而决定了 LLM 能做出多好的决策。

### 1.2 为什么上下文工程至关重要

| 维度 | 问题 | 上下文工程的回应 |
|------|------|---------------|
| **经济性** | LLM token 成本随上下文长度线性增长（Claude Sonnet: $3/1M input tokens）。一个 150K token 的无管理上下文每次调用花费 $0.45 | 压缩后 30K token → 每次调用 $0.09，节省 80%。10 万次调用/月 → 节省 $36,000 |
| **准确性** | "Lost in the Middle" 效应：LLM 对上下文中间位置的信息关注度最低，关键指令放在中间可能被忽略 | 结构化分层注入：关键约束置顶，近期对话置底，中间放检索片段 |
| **延迟** | 上下文长度每翻一倍，首 token 延迟增加 ~40%（Anthropic 内部数据） | 保持上下文 < 50K tokens，P50 延迟控制在 2s 内 |
| **可扩展性** | Agent 任务持续数小时、数十轮工具调用，原始对话历史无法无限增长 | 压缩+遗忘机制：旧信息→摘要→长期存储，为新信息腾出空间 |

### 1.3 大厂真实场景

| 产品 / 平台 | 上下文工程方式 | 核心特点 |
|------------|-------------|---------|
| **OpenAI Assistant API** | `truncation_strategy` + `tool_outputs` 管理 | `auto` 模式自动截断最早的消息；`last_messages` 保留最近 N 条。每次 run 结束后可选择清理 tool_outputs |
| **Anthropic Claude** | Prompt Caching + Projects 知识库 | `cache_control` 手动标注缓存断点（最多 4 个），命中后费用降 90%。Projects 支持将文档注入 system prompt 前缀 |
| **LangChain Memory** | `ConversationSummaryMemory` + `VectorStoreRetrieverMemory` | 摘要记忆：长对话→LLM 摘要；向量记忆：按语义检索相关历史片段 |
| **字节 Coze** | "变量" + "知识库" + 插件上下文 | 变量传递跨插件状态；知识库 RAG 注入领域知识；插件上下文按需加载 |
| **Google Gemini** | 原生 1M+ token 窗口 + 上下文缓存 | 超长原生窗口减少了压缩需求，但成本与延迟仍随长度增长——上下文工程在超长窗口时代不是变少了，而是从"怎么压缩"转变为"怎么不浪费窗口" |

## 2. 上下文的核心组成

上下文不是一块扁平的文本。它由六个不同来源、不同生命周期、不同优先级的信息层组成：

```
┌─────────────────────────────────────────────────────────────┐
│                    上下文六层模型                              │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│  L1: 静态基础上下文 (Static Base)                             │
│  ┌──────────────────────────────────────────────────────┐   │
│  │ · System Prompt（角色、行为准则、输出格式）              │   │
│  │ · 安全护栏（禁止内容、脱敏规则）                        │   │
│  │ · CLAUDE.md / 项目规范（编码风格、常用命令）            │   │
│  │ · Tool Definitions（工具名、描述、参数 JSON Schema）    │   │
│  │                                                        │   │
│  │ 生命周期: Session 内永久保留，绝不修改                   │   │
│  │ Token 占比: ~15-25%（取决于工具数量和规范详细程度）       │   │
│  └──────────────────────────────────────────────────────┘   │
│                                                              │
│  L2: 动态对话上下文 (Conversation Context)                    │
│  ┌──────────────────────────────────────────────────────┐   │
│  │ · 用户消息（原始输入、澄清问题、反馈）                    │   │
│  │ · Agent 回复（推理链、决策、生成的文本）                 │   │
│  │ · 用户对 Agent 产出的反馈（接受/拒绝/修改意见）          │   │
│  │                                                        │   │
│  │ 生命周期: 受滑动窗口 + 摘要压缩管理                      │   │
│  │ Token 占比: ~30-50%（任务交互越复杂占比越高）            │   │
│  └──────────────────────────────────────────────────────┘   │
│                                                              │
│  L3: 工具调用上下文 (Tool Call Context)                       │
│  ┌──────────────────────────────────────────────────────┐   │
│  │ · 工具调用输入参数（JSON）                               │   │
│  │ · 工具返回结果（可能是大段文本、JSON、二进制描述）       │   │
│  │ · 工具调用元数据（耗时、token 数、是否截断）             │   │
│  │                                                        │   │
│  │ 生命周期: 与所属任务步骤绑定，完成后可压缩/丢弃          │   │
│  │ Token 占比: ~20-40%（数据密集型任务占比高）              │   │
│  └──────────────────────────────────────────────────────┘   │
│                                                              │
│  L4: 记忆上下文 (Memory Context)                              │
│  ┌──────────────────────────────────────────────────────┐   │
│  │ · 短期记忆: 当前 session 内提取的关键事实               │   │
│  │   （如 "用户确认使用 Python 3.12"）                     │   │
│  │ · 长期记忆: 跨 session 的用户偏好和历史                 │   │
│  │   （如 "用户偏好 pytest 而非 unittest"）                │   │
│  │                                                        │   │
│  │ 生命周期: 短期=当前 session, 长期=持久化到外部存储       │   │
│  │ Token 占比: ~5-10%                                      │   │
│  └──────────────────────────────────────────────────────┘   │
│                                                              │
│  L5: 检索上下文 (Retrieval Context)                           │
│  ┌──────────────────────────────────────────────────────┐   │
│  │ · 从向量数据库按语义检索的代码片段/文档                 │   │
│  │ · 从搜索引擎实时查询的结果                              │   │
│  │ · 从知识库匹配的 FAQ / 参考实现                         │   │
│  │                                                        │   │
│  │ 生命周期: 每轮 LLM 调用前动态刷新                        │   │
│  │ Token 占比: ~10-20%                                     │   │
│  └──────────────────────────────────────────────────────┘   │
│                                                              │
│  L6: 状态上下文 (State Context)                               │
│  ┌──────────────────────────────────────────────────────┐   │
│  │ · 当前四相循环的 Phase 和 Iteration                    │   │
│  │ · 进度跟踪中已完成的子任务摘要（来自 progress.json）    │   │
│  │ · 当前子任务的验收标准                                  │   │
│  │ · Token 预算剩余                                        │   │
│  │                                                        │   │
│  │ 生命周期: 随执行状态变化而更新                           │   │
│  │ Token 占比: ~5-10%                                      │   │
│  │ 注意: 状态上下文通常不直接给 LLM,而是影响 prompt 构造    │   │
│  └──────────────────────────────────────────────────────┘   │
│                                                              │
└─────────────────────────────────────────────────────────────┘
```

## 3. 上下文的生命周期

### 3.1 六阶段管线

```
每次 LLM 调用前，上下文经过六个阶段的处理管线：

  ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
  │ Collect  │ → │ Filter   │ → │ Compress │ → │ Organize │ → │ Inject   │ → │ Forget   │
  │ 收集     │   │ 过滤     │   │ 压缩     │   │ 组织     │   │ 注入     │   │ 遗忘     │
  └──────────┘   └──────────┘   └──────────┘   └──────────┘   └──────────┘   └──────────┘

触发时机:
  每次 LLM 调用前:  Collect → Filter → Compress → Organize → Inject (全管线)
  每 N 轮或阈值触发: Compress (重量级操作——仅在 token 超限或阶段切换时)
  会话结束或重置时:  Forget (将短期记忆转为长期存储，清理临时上下文)
```

### 3.2 各阶段详细设计

#### Collect（收集）

```python
async def collect_context(
    sources: ContextSources,
    current_phase: Phase,
    progress: ProgressSnapshot,
) -> RawContext:
    """从六个来源收集原始上下文数据"""
    return RawContext(
        static_base={
            "system_prompt": sources.system_prompt,
            "claude_md": sources.claude_md,
            "tool_definitions": sources.tool_registry.list_for_llm(),
        },
        conversation=sources.messages[-50:],  # 最多取最近 50 条
        tool_results=sources.recent_tool_results(max_age_ms=120_000),  # 2 分钟内
        memories={
            "short_term": sources.memory.short_term.get_all(),
            "long_term": await sources.memory.long_term.search(
                query=progress.current_subtask.description,
                top_k=5,
            ),
        },
        retrieval=await sources.retriever.search(
            query=progress.current_subtask.description,
            top_k=3,
        ),
        state={
            "phase": current_phase.value,
            "iteration": progress.iteration,
            "completed_summaries": progress.get_completed_summaries(),
            "token_budget_remaining": progress.token_budget_remaining,
        },
    )
```

#### Filter（过滤）

```python
def filter_context(raw: RawContext, token_budget: TokenBudget) -> FilteredContext:
    """
    基于重要性评分过滤低价值信息。

    过滤规则（优先级递减）：
      1. 安全护栏——永远保留
      2. 当前子任务的验收标准——保留
      3. 用户最近 3 轮消息——保留
      4. 最近 2 次工具调用的完整结果——保留
      5. 更早的工具调用结果——只保留摘要（output_snapshot）
      6. 长期记忆中 similarity < 0.7 的条目——丢弃
      7. 检索结果中 relevance_score < 0.5 的条目——丢弃
      8. 超出 token_budget 的部分——按重要性分数从低到高丢弃
    """
    filtered = FilteredContext()

    # 规则 1-3: 高优先级——直接保留
    filtered.static_base = raw.static_base
    filtered.recent_conversation = raw.conversation[-6:]  # 最近 3 轮
    filtered.state = raw.state

    # 规则 4-5: 工具结果——按时间+重要性筛选
    for tr in raw.tool_results:
        age_ms = (now() - tr.timestamp).total_seconds() * 1000
        if age_ms < 60_000:  # 1 分钟内 → 完整保留
            filtered.tool_results.append(tr)
        elif tr.importance_score > 0.5:  # 重要 → 保留摘要
            filtered.tool_results.append(tr.to_summary())
        # 否则 → 丢弃

    # 规则 6-7: 记忆与检索——按相似度过滤
    filtered.memories = [m for m in raw.memories.long_term if m.similarity >= 0.7]
    filtered.retrieval = [r for r in raw.retrieval if r.relevance_score >= 0.5]

    # 规则 8: Token 预算硬约束
    total_tokens = estimate_tokens(filtered)
    if total_tokens > token_budget.max_context_tokens:
        # 从重要性最低的条目开始丢弃（工具结果 → 检索 → 早期对话）
        filtered = _trim_by_importance(filtered, token_budget.max_context_tokens)

    return filtered
```

#### Compress（压缩）

压缩是管线中最重量级的操作（可能需要额外 LLM 调用），因此在 §5 专门展开。

#### Organize（组织）

```python
def organize_context(filtered: FilteredContext, strategy: OrganizeStrategy) -> list[Message]:
    """
    确定各层信息的最终排列顺序。

    排列原则（基于 Anthropic Prompt Caching 最佳实践）：
      1. 最前面 = 最稳定 = 最高 Cache 命中 → System Prompt
      2. 其次 = 工具定义（session 内稳定）
      3. 中间 = 检索+记忆（中等变化频率）
      4. 倒数第二 = 工具结果摘要（变化频繁）
      5. 最后 = 当前任务 + 最近对话（每次请求都变）
    """
    organized = []

    # 区块 1: 静态基座 (Cache 断点 1)
    organized.append({
        "role": "system",
        "content": [
            {"type": "text", "text": filtered.static_base["system_prompt"],
             "cache_control": {"type": "ephemeral"}},
            {"type": "text", "text": filtered.static_base["claude_md"]},
        ]
    })

    # 区块 2: 工具定义 (Cache 断点 2)
    organized.append({
        "role": "user",
        "content": json.dumps({
            "available_tools": filtered.static_base["tool_definitions"],
        }),
    })

    # 区块 3: 长期记忆 + 检索结果
    organized.append({
        "role": "user",
        "content": json.dumps({
            "relevant_memories": filtered.memories,
            "retrieved_context": filtered.retrieval,
            "system_state": filtered.state,
        }),
    })

    # 区块 4: 已完成子任务摘要
    if filtered.state.get("completed_summaries"):
        organized.append({
            "role": "user",
            "content": f"## 已完成的工作\n{filtered.state['completed_summaries']}",
        })

    # 区块 5: 工具调用结果 (最近)
    for tr in filtered.tool_results:
        organized.append({"role": "tool", "content": tr.to_message()})

    # 区块 6: 最近对话 (每次请求变化的部分)
    organized.extend(filtered.recent_conversation)

    return organized
```

#### Inject（注入）

注入阶段处理的是**将 organized messages 与 LLM API 调用对接**——包括将超长内容拆分为多次调用的 chunk（如果使用长上下文策略），以及处理 API 层面的特殊参数（如 Anthropic 的 `cache_control`、OpenAI 的 `truncation_strategy`）。

#### Forget（遗忘）

```python
async def forget_context(
    memory: MemoryBackend,
    context_items: list[ContextItem],
    session_id: str,
):
    """
    遗忘策略——决定哪些信息从短期上下文移除，哪些转入长期存储。

    触发时机：
      - 会话结束
      - Context 超过硬上限触发 Reset
      - 子任务切换（上一个子任务的细节可以遗忘）
    """
    for item in context_items:
        if item.should_persist_to_long_term:
            # 关键决策、用户偏好 → 转入长期记忆
            await memory.long_term.upsert(
                key=item.generate_memory_key(),
                value=item.to_compressed_dict(),
                ttl_days=30,
            )
        elif item.is_transient:
            # 临时工具结果 → 直接丢弃
            pass
        else:
            # 对话历史 → 保留最近 N 轮，其余丢弃
            pass

    # 清理机制：超过 30 天未访问的长期记忆自动过期
    await memory.long_term.evict_expired()
```

## 4. 上下文组织与注入策略

### 4.1 滑动窗口 (Sliding Window)

**适用场景**：短会话任务（< 15 轮交互），任务目标在初始几轮已明确。

**实现**：
```python
def sliding_window(messages: list[Message], window_size: int = 10) -> list[Message]:
    """保留最近 window_size 条消息（即 5 轮交互）"""
    # 永远保留 system prompt (messages[0])
    system = messages[:1]
    # 保留最近 window_size 条
    recent = messages[-window_size:] if len(messages) > window_size else messages[1:]
    return system + recent
```

**量化参数**：`window_size=10`（5 轮交互）是甜点——覆盖了 LLM 理解当前讨论所需的上下文，同时保持 token 可控。

**优点**：实现极简，无额外 LLM 调用成本。**局限**：早期关键信息（如用户原始需求、全局约束）在窗口滑出后永久丢失，导致 Agent "遗忘初衷"。

### 4.2 递归摘要 (Recursive Summarization)

**适用场景**：长任务（> 20 轮交互），需要保留历史脉络但无法保留完整对话。

**实现**：
```python
async def recursive_summarize(
    messages: list[Message],
    token_threshold: int = 4000,
    summarizer: LLMProvider,  # 可使用轻量模型 (Haiku/GPT-4o-mini)
) -> list[Message]:
    """
    递归摘要——当对话历史超过阈值时生成摘要。

    算法：
      1. 将 messages 按 token 量分块（每块 ≤ token_threshold）
      2. 对第一个块调用轻量 LLM 生成摘要
      3. 将摘要与下一块拼接，继续摘要
      4. 重复直到所有块被摘要化
      5. 最终产出一个覆盖全对话的摘要 + 最近 6 条原始消息

    成本分析:
      - 摘要 LLM 调用次数: ceil(total_tokens / token_threshold)
      - 每次摘要调用成本: ~$0.002 (Haiku)
      - 10 万 token 对话摘要总成本: ~$0.05
    """
    chunks = _split_into_chunks(messages, token_threshold)
    summary = ""

    for i, chunk in enumerate(chunks):
        if i == 0:
            summary = await summarizer.chat(
                prompt="请简洁摘要以下对话，保留所有关键事实、决策和未完成任务：",
                context=chunk,
                max_tokens=1000,
            )
        else:
            summary = await summarizer.chat(
                prompt=f"已有摘要: {summary}\n\n请整合以下新内容，更新摘要：",
                context=chunk,
                max_tokens=1000,
            )

    # 保留摘要 + 最近 3 轮原始对话
    recent = messages[-6:]
    return [
        {"role": "user", "content": f"[对话历史摘要]\n{summary}"}
    ] + recent
```

**量化参数**：摘要目标 token 为原始文本的 **15-20%**。每次摘要 LLM 调用的预算不应超过主 LLM 调用的 **5%**。

### 4.3 选择性注入 (Selective Injection)

**适用场景**：上下文来源多样（对话+工具结果+记忆+检索），需要智能选择。

```python
@dataclass
class ScoredContextItem:
    item: ContextItem
    score: float  # 0.0 ~ 1.0

def score_and_select(items: list[ContextItem], budget_tokens: int) -> list[ContextItem]:
    """
    为每条上下文计算重要性分数，按分数排序，选择 Top-N 直到填满 token 预算。

    评分因子：
      - recency: 最近的消息得分高（指数衰减，半衰期 = 5 轮）
      - relevance: 与当前子任务的语义相似度高
      - source_priority: System Prompt (1.0) > 用户消息 (0.9) > 
                          工具关键结果 (0.7) > 检索结果 (0.5) > 旧对话 (0.3)
      - user_feedback: 用户明确说"记住这个" → 分数 = 1.0
      - error_context: 验证失败信息 → 分数 × 1.5（防重复犯错）
    """
    scored = []
    now = datetime.utcnow()

    for item in items:
        # 时效性得分: 指数衰减，半衰期 5 轮
        age_rounds = (now - item.timestamp).total_seconds() / 30  # 假设每轮 30s
        recency_score = 1.0 * (0.5 ** (age_rounds / 5))

        # 相关性得分: 模拟（生产中使用 embedding cosine similarity）
        relevance_score = item.compute_relevance_to_current_task()

        # 来源优先级
        source_score = SOURCE_PRIORITY.get(item.source, 0.5)

        # 用户标记
        user_boost = 1.5 if item.user_marked_important else 1.0
        error_boost = 1.5 if item.is_error_context else 1.0

        item.score = (
            recency_score * 0.25 +
            relevance_score * 0.35 +
            source_score * 0.25 +
            user_boost * 0.10 +
            error_boost * 0.05
        )
        scored.append(item)

    # 按分数排序，贪心选择直到填满预算
    scored.sort(key=lambda x: x.score, reverse=True)
    selected = []
    token_count = 0
    for item in scored:
        if token_count + item.token_count <= budget_tokens:
            selected.append(item)
            token_count += item.token_count
        else:
            break

    return selected
```

### 4.4 结构化上下文 (Structured Context)

**适用场景**：工具调用密集、任务状态复杂的场景。

```python
def build_structured_context(
    goal: str,
    completed: list[dict],
    in_progress: dict,
    tool_results: list[dict],
    constraints: list[str],
) -> str:
    """
    将上下文以结构化 JSON 注入——比自然语言更省 token，更易被 LLM 解析。

    量化对比（实测）:
      自然语言描述: ~850 tokens
      结构化 JSON:  ~420 tokens (节省 50%)
    """
    return json.dumps({
        "goal": goal,
        "completed_steps": [
            {"id": s["id"], "result": s["summary"][:200]}
            for s in completed
        ],
        "current_step": {
            "id": in_progress["id"],
            "action": in_progress["description"],
            "attempt": in_progress.get("attempt", 1),
        },
        "relevant_tool_results": {
            tr["tool"]: _trim_result(tr["data"], max_chars=300)
            for tr in tool_results
        },
        "global_constraints": constraints,
    }, ensure_ascii=False, indent=2)
```

## 5. 上下文压缩技术

### 5.1 摘要压缩

**普通摘要**（一次性调用 LLM）：
```
输入: 前 10 轮对话 (约 12K tokens)
输出: 一段 400 token 的摘要
成本: ~$0.005
问题: 单次 LLM 调用有上下文限制; 摘要质量随输入长度下降
```

**迭代摘要**（分块多次调用——推荐用于超长内容）：
```python
async def iterative_summarize(
    long_text: str,
    chunk_size_tokens: int = 4000,
    target_summary_tokens: int = 800,
    summarizer: LLMProvider,
) -> str:
    """分块迭代摘要——适合超过 16K token 的文本"""
    chunks = token_aware_split(long_text, chunk_size_tokens)
    current_summary = ""

    for chunk in chunks:
        if not current_summary:
            prompt = f"请简洁摘要以下内容（保留所有关键数据、决策、结论）：\n{chunk}"
        else:
            prompt = (
                f"已有摘要:\n{current_summary}\n\n"
                f"请整合以下新内容，更新并生成一份连贯的摘要（不要只是拼接）：\n{chunk}"
            )

        current_summary = await summarizer.chat(
            prompt=prompt,
            max_tokens=target_summary_tokens,
        )

    return current_summary
```

**抽取式摘要**（不使用 LLM——快、零成本、但信息损失大）：
```python
def extractive_summarize(text: str, top_n: int = 10) -> str:
    """基于 TF-IDF 的关键句提取——零 LLM 成本"""
    sentences = split_sentences(text)
    if len(sentences) <= top_n:
        return text

    tfidf_matrix = TfidfVectorizer().fit_transform(sentences)
    scores = tfidf_matrix.sum(axis=1).A1  # 每句的 TF-IDF 总分
    top_indices = scores.argsort()[-top_n:][::-1]
    top_sentences = [sentences[i] for i in sorted(top_indices)]
    return " ".join(top_sentences)
```

### 5.2 结构化压缩

将自由文本转换为结构化事实——token 效率极高但需要额外的 LLM 调用：

```python
EXTRACT_FACTS_PROMPT = """
将以下文本中的关键事实提取为 JSON 键值对。规则：
1. 只提取可验证的事实，不要推断
2. 键使用简洁的英文/拼音，值使用原文中的表述
3. 如果有数字，保留精确值
4. 最多 15 个事实，按重要性排序

文本:
{text}

输出格式:
{{"facts": [{{"key": "...", "value": "...", "certainty": "high|medium"}}, ...]}}
"""

async def structured_compress(text: str, extractor: LLMProvider) -> dict:
    """
    结构化压缩——自由文本 → JSON 事实列表

    示例:
      输入: "用户张三说他在北京朝阳区工作，目前使用 Python 3.12，
            项目依赖 FastAPI 和 PostgreSQL 16，偏好 pytest 来写测试，
            不喜欢用 Docker，数据库连接字符串在 .env 里。"
      输出: {
        "facts": [
          {"key": "user_name", "value": "张三", "certainty": "high"},
          {"key": "location", "value": "北京朝阳区", "certainty": "high"},
          {"key": "python_version", "value": "3.12", "certainty": "high"},
          {"key": "web_framework", "value": "FastAPI", "certainty": "high"},
          {"key": "database", "value": "PostgreSQL 16", "certainty": "high"},
          {"key": "test_framework", "value": "pytest", "certainty": "high"},
          {"key": "dislikes_docker", "value": "true", "certainty": "high"},
          {"key": "db_connection_location", "value": ".env", "certainty": "high"}
        ]
      }

    Token 对比: 原始 120 tokens → 结构化 55 tokens (节省 54%)
    """
    response = await extractor.chat(
        prompt=EXTRACT_FACTS_PROMPT.format(text=text[:8000]),
        max_tokens=500,
    )
    return json.loads(response.content)
```

### 5.3 工具结果压缩

工具返回的数据往往是上下文膨胀的最大来源。压缩策略需根据数据类型自适应：

```python
TOOL_RESULT_COMPRESSION_RULES = {
    # 策略: (条件函数, 压缩函数)
    "truncate_head": (
        lambda data: isinstance(data, str) and len(data) > 5000,
        lambda data: data[:2500] + f"\n...[截断，原文 {len(data)} 字符]...\n" + data[-2500:],
    ),
    "summarize_array": (
        lambda data: isinstance(data, list) and len(data) > 20,
        lambda data: {
            "total_count": len(data),
            "sample": data[:5],
            "distribution": _compute_distribution(data),
        },
    ),
    "key_fields_only": (
        lambda data: isinstance(data, dict) and len(json.dumps(data)) > 5000,
        lambda data: {k: _trim_value(v) for k, v in data.items()
                      if k in {"result", "summary", "status", "count", "error"}},
    ),
    "pass_through": (
        lambda data: True,
        lambda data: data,
    ),
}


def compress_tool_result(tool_name: str, raw_data: Any) -> tuple[Any, bool]:
    """
    根据工具类型和返回数据特征自适应压缩。

    返回: (compressed_data, was_compressed)
    """
    for strategy_name, (condition, compressor) in TOOL_RESULT_COMPRESSION_RULES.items():
        if condition(raw_data):
            compressed = compressor(raw_data)
            was_compressed = strategy_name != "pass_through"
            logger.info(
                "context.tool_result_compressed",
                tool=tool_name,
                strategy=strategy_name,
                original_size=len(json.dumps(raw_data, default=str)),
                compressed_size=len(json.dumps(compressed, default=str)),
            )
            return compressed, was_compressed

    return raw_data, False
```

### 5.4 压缩时机决策树

```
是否触发压缩？
  │
  ├── 当前上下文 tokens < 软阈值 (80K)？
  │   └── YES → 不压缩，继续正常执行
  │
  ├── 当前上下文 tokens > 软阈值 (80K) 且 < 硬阈值 (120K)？
  │   └── YES → 触发轻量压缩
  │       ├── 对话历史: 前 50% 回合 → 单次 LLM 摘要
  │       ├── 工具结果: 按规则自适应压缩（不使用 LLM）
  │       └── 记忆/检索: 按分数过滤，只保留 Top-5
  │
  ├── 当前上下文 tokens > 硬阈值 (120K)？
  │   └── YES → 触发重量压缩
  │       ├── 对话历史: 全部 → 迭代 LLM 摘要
  │       ├── 工具结果: 全部 → 结构化压缩
  │       ├── 长期记忆: 按语义刷新检索
  │       └── 如果压缩后仍 > 150K → 触发上下文重置 (Reset)
  │
  └── 压缩成本 vs 保留成本？
      └── 如果 压缩 LLM 调用成本 > 保留原始内容的 token 成本 × 剩余轮次
          → 不压缩，保留原始内容
          → 仅当原始内容在后续 3+ 轮中会多次被计入 context 时才压缩

量化决策:
  保留 10K token 原始内容的成本 = 10K × $3/1M × 3 轮 = $0.09
  压缩 10K token 的成本 = 压缩 LLM 调用 ($0.005) + 2K 摘要 × $3/1M × 3 轮 ($0.018) = $0.023
  → 节省 $0.067 (74%) → 值得压缩
```

## 6. 实现模式与代码示例

```python
"""
上下文管理器 — 生产级简化实现
===============================
六层模型 · 六阶段管线 · 多策略 · 精确 token 计数 · 异步友好
"""

import asyncio
import json
import time
from dataclasses import dataclass, field
from enum import Enum
from typing import Any, Callable, Optional
import tiktoken
import structlog

logger = structlog.get_logger(__name__)


# =============================================================================
# 核心数据模型
# =============================================================================

class ContextSource(Enum):
    SYSTEM = "system"
    CONVERSATION = "conversation"
    TOOL_RESULT = "tool_result"
    MEMORY = "memory"
    RETRIEVAL = "retrieval"
    STATE = "state"


@dataclass
class ContextItem:
    """上下文管线中的最小数据单元"""
    id: str
    source: ContextSource
    content: Any  # str | dict | list
    timestamp: float = field(default_factory=time.time)
    token_count: int = 0
    importance_score: float = 0.5  # 0.0~1.0，由过滤阶段计算
    user_marked_important: bool = False
    is_error_context: bool = False
    should_persist_to_long_term: bool = False
    is_transient: bool = False  # True = 临时数据，完成后立即丢弃

    def compute_relevance_to_current_task(self) -> float:
        """模拟——生产中使用 embedding cosine similarity"""
        return self.importance_score


class OrganizeStrategy(Enum):
    SLIDING_WINDOW = "sliding_window"
    RECURSIVE_SUMMARY = "recursive_summary"
    SELECTIVE = "selective"
    STRUCTURED = "structured"
    HIERARCHICAL = "hierarchical"


# =============================================================================
# 上下文管理器
# =============================================================================

class ContextManager:
    """
    上下文管理器 — Harness 的内存管理系统

    职责边界：
      ✅ 管理所有 ContextItem 的生命周期
      ✅ 在每次 LLM 调用前执行 Collect → Filter → Compress → Organize → Inject
      ✅ Token 计数、预算管理、Cache 优化
      ❌ 不执行工具调用（那是工具编排的事）
      ❌ 不决定任务拆解（那是任务拆解的事）
    """

    def __init__(
        self,
        tokenizer_model: str = "claude-sonnet-4-6",
        soft_limit_tokens: int = 80_000,
        hard_limit_tokens: int = 120_000,
        max_context_tokens: int = 160_000,
        summarizer: Optional["LLMProvider"] = None,
    ):
        self.soft_limit = soft_limit_tokens
        self.hard_limit = hard_limit_tokens
        self.max_context = max_context_tokens
        self.summarizer = summarizer

        # 根据模型选择 tokenizer
        try:
            self.tokenizer = tiktoken.encoding_for_model(tokenizer_model)
        except KeyError:
            self.tokenizer = tiktoken.get_encoding("cl100k_base")

        # 六层上下文存储
        self._items: dict[str, ContextItem] = {}
        self._token_count_cache: int = 0
        self._dirty: bool = True  # 标记缓存是否失效

    # ── 收集 (Collect) ──────────────────────────────

    def add_item(self, item: ContextItem) -> None:
        """添加上下文项"""
        if item.token_count == 0:
            item.token_count = self._count_tokens(item.content)
        self._items[item.id] = item
        self._dirty = True

    def add_tool_result(self, tool_name: str, raw_data: Any) -> ContextItem:
        """添加工具返回结果——自动压缩"""
        compressed, was_compressed = compress_tool_result(tool_name, raw_data)
        item = ContextItem(
            id=f"tool_{tool_name}_{int(time.time() * 1000)}",
            source=ContextSource.TOOL_RESULT,
            content=compressed,
            token_count=self._count_tokens(compressed),
            importance_score=0.7 if not was_compressed else 0.5,
            is_transient=not was_compressed,  # 未压缩的小结果可快速丢弃
        )
        self.add_item(item)
        return item

    # ── 过滤 (Filter) ──────────────────────────────

    def filter_by_token_budget(self, budget_tokens: int) -> list[ContextItem]:
        """按 token 预算过滤——保留最重要的项直到填满预算"""
        items = sorted(self._items.values(), key=lambda x: x.importance_score, reverse=True)
        selected = []
        count = 0
        for item in items:
            if count + item.token_count <= budget_tokens:
                selected.append(item)
                count += item.token_count
            else:
                logger.debug("context.item_dropped", item_id=item.id, reason="budget")
        return selected

    # ── 组织 (Organize) ────────────────────────────

    def build_prompt(
        self,
        strategy: OrganizeStrategy = OrganizeStrategy.HIERARCHICAL,
        max_tokens: Optional[int] = None,
        current_phase: Optional[str] = None,
    ) -> list[dict]:
        """
        构建最终发送给 LLM 的 messages 列表。

        这是上下文管理器的对外主接口——每次 LLM 调用前调用此方法。
        """
        budget = max_tokens or self.max_context
        items = self.filter_by_token_budget(budget)

        messages = []

        # ── 根据策略组织 ──
        if strategy == OrganizeStrategy.SLIDING_WINDOW:
            messages = self._organize_sliding_window(items)
        elif strategy == OrganizeStrategy.SELECTIVE:
            messages = self._organize_selective(items)
        elif strategy == OrganizeStrategy.STRUCTURED:
            messages = self._organize_structured(items)
        elif strategy == OrganizeStrategy.HIERARCHICAL:
            messages = self._organize_hierarchical(items, current_phase)
        else:  # RECURSIVE_SUMMARY
            messages = self._organize_recursive_summary(items)

        # ── 最终尺寸检查 ──
        total_tokens = sum(self._count_tokens(m.get("content", "")) for m in messages)
        if total_tokens > self.max_context:
            logger.error(
                "context.over_limit",
                total_tokens=total_tokens,
                limit=self.max_context,
            )
            # 强制截断——不应该走到这里，但如果走到，使用 sliding_window 兜底
            messages = self._organize_sliding_window(items, window_size=6)

        return messages

    def _organize_hierarchical(self, items: list[ContextItem], phase: Optional[str]) -> list[dict]:
        """分层组织——热数据在前（Cache 友好），温冷数据在中，最新对话在尾"""
        messages = []

        # L1 热数据: System + 当前子任务 (Cache 断点 1)
        hot_system = [i for i in items if i.source == ContextSource.SYSTEM]
        for item in hot_system:
            messages.append({"role": "system", "content": item.content})

        # L1 热数据: 当前任务状态
        hot_state = [i for i in items if i.source == ContextSource.STATE]
        if hot_state:
            messages.append({"role": "user", "content": json.dumps(
                [i.content for i in hot_state], ensure_ascii=False
            )})

        # L2 温数据: 记忆 + 已完成子任务摘要 + 工具结果摘要
        warm_items = [i for i in items if i.source in (
            ContextSource.MEMORY, ContextSource.RETRIEVAL
        )]
        if warm_items:
            messages.append({"role": "user", "content": json.dumps(
                [{"source": i.source.value, "content": i.content} for i in warm_items],
                ensure_ascii=False,
            )})

        # L3 冷数据: 最近对话
        cold_conversation = [i for i in items if i.source == ContextSource.CONVERSATION]
        for item in cold_conversation[-6:]:  # 最近 3 轮
            messages.append({"role": "user" if item.id.startswith("user") else "assistant",
                            "content": item.content})

        return messages

    def _organize_sliding_window(self, items: list[ContextItem], window_size: int = 10) -> list[dict]:
        """滑动窗口——保留 system + 最近 window_size 条"""
        # System 永远保留
        system_items = [i for i in items if i.source == ContextSource.SYSTEM]
        non_system = [i for i in items if i.source != ContextSource.SYSTEM]

        messages = [{"role": "system", "content": i.content} for i in system_items]
        for item in non_system[-window_size:]:
            role = "user" if "user" in item.id.lower() else "assistant"
            messages.append({"role": role, "content": item.content})

        return messages

    def _organize_structured(self, items: list[ContextItem]) -> list[dict]:
        """结构化——全部内容打包为单个 JSON"""
        structured = {
            "goal": next((i.content for i in items if i.id == "goal"), ""),
            "completed": [i.content for i in items if i.source == ContextSource.STATE],
            "context": [{"source": i.source.value, "data": i.content} for i in items
                       if i.source not in (ContextSource.SYSTEM, ContextSource.CONVERSATION)],
            "recent_conversation": [
                i.content for i in items if i.source == ContextSource.CONVERSATION
            ][-6:],
        }
        system_items = [i for i in items if i.source == ContextSource.SYSTEM]
        return [
            {"role": "system", "content": system_items[0].content if system_items else ""},
            {"role": "user", "content": json.dumps(structured, ensure_ascii=False)},
        ]

    # ── Token 计数 ──────────────────────────────────

    def _count_tokens(self, content: Any) -> int:
        """精确 token 计数——使用模型原生 tokenizer"""
        if isinstance(content, str):
            return len(self.tokenizer.encode(content))
        elif isinstance(content, (dict, list)):
            return len(self.tokenizer.encode(json.dumps(content, ensure_ascii=False)))
        else:
            return len(self.tokenizer.encode(str(content)))

    @property
    def total_tokens(self) -> int:
        if self._dirty:
            self._token_count_cache = sum(item.token_count for item in self._items.values())
            self._dirty = False
        return self._token_count_cache

    # ── 压缩触发 ────────────────────────────────────

    async def maybe_compress(self) -> bool:
        """
        检查 token 使用量，按需触发压缩。

        Returns: True 如果执行了压缩操作
        """
        current = self.total_tokens

        if current > self.hard_limit:
            logger.warning("context.hard_limit_reached", tokens=current, limit=self.hard_limit)
            await self._heavy_compress()
            return True

        if current > self.soft_limit:
            logger.info("context.soft_limit_reached", tokens=current, limit=self.soft_limit)
            await self._light_compress()
            return True

        return False

    async def _light_compress(self):
        """轻量压缩——摘要早期对话 + 过滤低分项"""
        if self.summarizer is None:
            return

        conversation_items = [i for i in self._items.values()
                            if i.source == ContextSource.CONVERSATION]
        if len(conversation_items) > 20:
            # 前 50% → 摘要
            split = len(conversation_items) // 2
            old = conversation_items[:split]
            new_text = "\n".join(str(i.content) for i in old)

            summary = await self.summarizer.chat(
                prompt=f"请简洁摘要以下对话（保留关键决策和事实）：\n{new_text}",
                max_tokens=500,
            )

            # 替换旧项为摘要
            for item in old:
                del self._items[item.id]
            self.add_item(ContextItem(
                id=f"summary_{int(time.time())}",
                source=ContextSource.CONVERSATION,
                content=summary,
                importance_score=0.6,
            ))
            self._dirty = True

    async def _heavy_compress(self):
        """重量压缩——全部对话摘要 + 工具结果结构化"""
        if self.summarizer is None:
            # 没有摘要器 → 只能截断
            items = sorted(self._items.values(), key=lambda x: x.importance_score, reverse=True)
            keep_count = int(len(items) * 0.3)  # 保留 30%
            for item in items[keep_count:]:
                del self._items[item.id]
            self._dirty = True
            return

        await self._light_compress()

        # 工具结果 → 结构化摘要
        tool_items = [i for i in self._items.values()
                     if i.source == ContextSource.TOOL_RESULT]
        for item in tool_items:
            if item.token_count > 2000:
                compressed = await structured_compress(
                    json.dumps(item.content, ensure_ascii=False)[:4000],
                    self.summarizer,
                )
                item.content = compressed
                item.token_count = self._count_tokens(compressed)
                item.importance_score = 0.4

        self._dirty = True


# =============================================================================
# 与 LLM 调用层集成
# =============================================================================

async def llm_call_with_context(
    ctx_mgr: ContextManager,
    llm: "LLMProvider",
    user_message: str,
    phase: Optional[str] = None,
) -> str:
    """
    每次 LLM 调用的标准入口——封装上下文管线的全流程。

    用法：
      response = await llm_call_with_context(ctx_mgr, llm, "请继续处理下一个子任务")
    """

    # 1. 将用户消息作为新的上下文项加入
    ctx_mgr.add_item(ContextItem(
        id=f"user_msg_{int(time.time() * 1000)}",
        source=ContextSource.CONVERSATION,
        content=user_message,
        importance_score=0.9,
    ))

    # 2. 按需触发压缩
    await ctx_mgr.maybe_compress()

    # 3. 构建 prompt（组织 + 注入）
    messages = ctx_mgr.build_prompt(
        strategy=OrganizeStrategy.HIERARCHICAL,
        current_phase=phase,
    )

    # 4. 调用 LLM
    token_count = sum(ctx_mgr._count_tokens(m.get("content", "")) for m in messages)
    logger.info("context.llm_call", tokens=token_count, phase=phase, items=len(ctx_mgr._items))

    response = await llm.chat(messages)

    # 5. 将 LLM 回复作为新的上下文项加入
    ctx_mgr.add_item(ContextItem(
        id=f"assistant_msg_{int(time.time() * 1000)}",
        source=ContextSource.CONVERSATION,
        content=response.content,
        token_count=ctx_mgr._count_tokens(response.content),
        importance_score=0.8,
    ))

    return response.content
```

## 7. 进阶主题

### 7.1 相位感知的预算分配

不同 Phase 对上下文的需求不同——统一预算会导致有的 Phase 信息不足，有的浪费：

```python
PHASE_TOKEN_BUDGETS = {
    # Phase 1 (感知装配): 需要大量上下文——读取环境、理解状态
    "perceive": 0.40,   # 占 max_context 的 40% — 最需要看到全景
    # Phase 2 (规划决策): 需要工具描述 + 任务历史
    "plan": 0.35,       # 占 35% — 需要工具定义和既往决策
    # Phase 3 (执行编排): 通常只需要当前工具的参数和上下文
    "execute": 0.20,    # 占 20% — 聚焦于当前操作
    # Phase 4 (验证修正): 需要验收标准 + 执行结果
    "verify": 0.30,     # 占 30% — 需要比对预期与实际
}


def get_phase_budget(phase: str, max_context: int = 160_000) -> int:
    """根据当前 Phase 返回建议的 token 预算"""
    ratio = PHASE_TOKEN_BUDGETS.get(phase, 0.30)
    return int(max_context * ratio)
```

### 7.2 持久上下文缓存

在四相循环的多轮迭代中，避免重复注入相同信息：

```python
class PersistentContextCache:
    """
    持久上下文缓存——跨迭代保留已注入的高稳定性上下文。

    场景: Phase 1 已经告诉 LLM "用户是 VIP，偏好 pytest"
    → 后续 Phase 2/3/4 不需要重复注入这些信息
    → 缓存到 _persistent_items，只在首次注入时计算 token，后续跳过
    """

    def __init__(self):
        self._persistent: dict[str, ContextItem] = {}
        self._injected_in_current_round: set[str] = set()

    def mark_as_persistent(self, item: ContextItem) -> None:
        """标记为持久项——跨迭代保留"""
        self._persistent[item.id] = item

    def get_uninjected(self) -> list[ContextItem]:
        """获取本迭代尚未注入的持久项"""
        return [item for id_, item in self._persistent.items()
                if id_ not in self._injected_in_current_round]

    def mark_injected(self, item_ids: list[str]) -> None:
        self._injected_in_current_round.update(item_ids)

    def reset_round(self) -> None:
        """每轮迭代开始前重置注入记录"""
        self._injected_in_current_round.clear()

    def invalidate(self, item_id: str) -> None:
        """标记某持久项失效（如用户信息变更）"""
        self._persistent.pop(item_id, None)
```

### 7.3 Prompt Cache 优化

```python
class CacheOptimizer:
    """
    Prompt Cache 优化器——最大化 Anthropic cache_control 命中率。

    关键规则:
      1. System prompt 永远放在 messages[0]，内容 session 内不变
      2. 缓存断点最多 4 个——放在「稳定性最高」的内容区块后
      3. 动态信息（时间、进度、token 剩余）绝不放在缓存断点前
      4. 工具定义列表 session 内不变 → 放在缓存断点 2 后
    """

    CACHE_BREAKPOINTS = {
        "system_prompt": 0,      # messages[0] 后 — 永久缓存
        "tool_definitions": 1,   # 工具定义后 — session 内缓存
        "project_context": 2,    # CLAUDE.md 后 — 跨任务缓存
        "task_description": 3,   # 用户任务描述后 — 任务内缓存
    }

    def estimate_cache_savings(self, messages: list[dict]) -> dict:
        """
        估算当前 messages 布局的 Cache 节省比例。
        返回: {"cached_tokens": N, "total_tokens": M, "savings_pct": X%}
        """
        # 简化估算——假设系统 prompt 和工具定义被缓存
        system_tokens = self._count_tokens(messages[0].get("content", "")) if messages else 0
        total_tokens = sum(self._count_tokens(m.get("content", "")) for m in messages)
        cached = system_tokens  # 实际可能更多（取决于断点位置）

        return {
            "cached_tokens": cached,
            "total_tokens": total_tokens,
            "savings_pct": round(cached / total_tokens * 100, 1) if total_tokens > 0 else 0,
        }
```

```python
async def sanitize_context(item: ContextItem) -> ContextItem:
    """
    安全与隐私过滤——在注入 LLM 前自动脱敏。

    检测并处理:
      - 信用卡号 (\\d{4}-\\d{4}-\\d{4}-\\d{4})
      - 邮箱 (user@domain.com → u***@domain.com)
      - 手机号 (\\d{11} → 138****1234)
      - API Key (sk-..., ak-...)
      - IP 地址 (内部 IP 保留, 外部 IP 脱敏)
    """
    content_str = json.dumps(item.content, ensure_ascii=False) if isinstance(item.content, dict) else str(item.content)

    # 脱敏规则
    content_str = re.sub(r'\b\d{4}-\d{4}-\d{4}-\d{4}\b', '[CREDIT_CARD_REDACTED]', content_str)
    content_str = re.sub(r'\b[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Z|a-z]{2,}\b',
                         lambda m: f"{m.group(0)[0]}***@{m.group(0).split('@')[1]}", content_str)
    content_str = re.sub(r'(sk|ak)-[A-Za-z0-9]{20,}', '[API_KEY_REDACTED]', content_str)

    item.content = content_str
    item.token_count = len(content_str) // 4  # 粗略估算
    return item
```

## 8. 与其他模块的关系

| 关联模块 | 关系说明 | 生产示例 |
|---------|---------|---------|
| **01-四相循环** | 每个 Phase 有不同的上下文需求。Phase 1 需要全局视野（40% 预算），Phase 3 仅需当前操作上下文（20% 预算）。上下文管理器接收 `current_phase` 参数动态调整 | `ctx_mgr.build_prompt(current_phase="execute")` → 自动应用 Phase 3 的 token 预算和过滤策略 |
| **02-工具编排** | 工具编排器在每次工具返回后调用 `ctx_mgr.add_tool_result()` 进行自适应压缩。工具编排提供"结果预处理钩子"让上下文管理器介入 | `ctx_mgr.add_tool_result("search_code", raw_50kb_result)` → 自动压缩为 2KB 摘要 |
| **03-进度跟踪** | 上下文管理器从进度树读取已完成子任务的 `output_snapshot`，作为"已完成工作"上下文注入——LLM 不需要从对话历史中推断 | `completed_summaries = progress.get_completed_summaries()` → 注入为温数据层 |
| **05-任务拆解** | 每个子任务拥有独立的上下文命名空间。切换到新子任务时，旧子任务的详细上下文被压缩为摘要，context manager 释放该命名空间 | `ctx_mgr.switch_namespace(new_subtask.id)` → 自动执行旧命名空间的 Forget |
| **06-验证循环** | 验证失败的错误信息以 1.5× 重要性系数注入上下文——防止 LLM 在重试时犯相同错误 | `item.is_error_context = True` → `importance_score *= 1.5` |
| **07-子代理分治** | 子代理拥有独立的 ContextManager 实例（上下文隔离）。主代理通过 `PersistentContextCache` 向子代理传递必要的背景信息（≤ 500 tokens） | `sub_ctx_mgr = ContextManager()` + `sub_ctx_mgr.add_item(cached_context)` |
| **08-GAN 三角色** | Generator 需要开放性上下文（宽松过滤），Evaluator 需要严格规则上下文（紧凑、只含验收标准和产物），Coordinator 需要全局状态上下文 | 三个角色各自拥有独立的 ContextManager 实例，配置不同的过滤参数 |

## 9. 常见反模式与陷阱

### 9.1 永远不压缩

**症状**：上下文无限增长，messages 列表从 20 条膨胀到 500 条，每次 LLM 调用消耗 180K tokens（$0.54），延迟 8s+。

**事故**：某代码审查 Agent 运行 2 小时后，单次 API 调用的 input tokens 达到 195K，触发了 API 的硬限制错误——Agent 直接崩溃，之前 2 小时的工作全部丢失。

**修复**：强制 `soft_limit_tokens=80K` + `hard_limit_tokens=120K`。每次 `build_prompt()` 前调用 `maybe_compress()`。

### 9.2 过度压缩丢失关键信息

**症状**：摘要过于激进，LLM 摘要漏掉了关键约束（如"不要修改 tests/ 目录"），导致 Agent 违规操作。

**修复**：(1) 引入"永久上下文"分区，标记不可压缩的关键约束；(2) 压缩后检查——用简单的关键词匹配验证关键信息是否被保留；(3) 摘要 prompt 中显式要求"保留所有约束条件"。

### 9.3 固定窗口丢弃早期指令

**症状**：滑动窗口滑出第 2 轮用户说的"分析只针对 Python 文件"→ Agent 第 15 轮开始分析 Java 文件。

**修复**：将用户全局约束提取为 L4 记忆中的"持久事实"——独立于滑动窗口，在每次 `build_prompt()` 时固定注入。

### 9.4 不分来源等权注入

**症状**：工具返回的 50KB JSON 与用户的关键纠错指令同等对待——污染了 LLM 的注意力，导致它忽略了用户的修正。

**修复**：不同来源赋予不同的 `importance_score`：用户纠错 = 1.0，用户普通消息 = 0.9，工具结果 = 0.5-0.7，检索 = 0.5。

### 9.5 Token 计数不准确

**症状**：使用 gpt-4 tokenizer 估算 Claude 的 token 数 → 实际 token 数比估算多 15% → 预算控制失效。

**修复**：使用模型原生 tokenizer（Anthropic 的 `claude-tokenizer` 或 OpenAI 的 `tiktoken`）。在 `ContextManager` 初始化时根据模型自动选择。`_count_tokens()` 对所有内容的计数是硬标准——不依赖估算。

### 9.6 同步压缩阻塞主循环

**症状**：压缩 LLM 调用（耗时 3s）阻塞了 Agent 的主执行循环——用户等待 3s 后 Agent 才有下一步动作。

**修复**：压缩异步化——使用 `asyncio.create_task()` 在后台预压缩。主请求使用上一次压缩的结果（可能滞后 1-2 轮，但延迟增加为 0ms）。关键场景（如 token 预算接近硬上限）等待压缩完成。

## 11. 总结与扩展阅读

### 核心要点

1. **上下文工程是 Harness 的内存管理系统**——不是"把 prompt 写好"，而是系统性地管理 LLM 的注意力空间。六层模型 + 六阶段管线 + 五种组织策略构成了完整的信息处理框架。

2. **压缩是经济性核心**——压缩 80% 的上下文意味着 80% 的成本节省和 ~40% 的延迟降低。但需要压缩决策树来判断"什么时候值得压缩"。

3. **分层上下文 (Hot/Warm/Cold) 是最通用的组织策略**——类比操作系统虚拟内存，高频数据全量保留，低频数据摘要/检索。

4. **Prompt Cache 友好布局直接决定成本**——System Prompt 绝对稳定 + Cache 断点正确放置 = 90% 的 Cache 命中率折扣。

5. **压缩不是"越压缩越好"**——关键约束（用户偏好、全局规则）必须标记为不可压缩。按需重查 (re-query on demand) 是兜底策略。

### 与现有框架对比

| 框架 | 上下文管理能力 | 差距 |
|------|------------|------|
| **LangChain Memory** | `ConversationBufferMemory`, `ConversationSummaryMemory` | 缺少分层、缺少相位感知、缺少压缩时机决策 |
| **LlamaIndex ChatMemoryBuffer** | Token 限制 + 聊天历史窗口 | 聚焦于 RAG 场景，缺少 Agent 相位感知 |
| **DSPy** | `Signature` + `Predict` 中的上下文 | 模块化但缺少系统级的 token 预算管理 |
| **本方案** | 六层模型 + 六阶段管线 + 相位感知 + Prompt Cache 优化 | 专为 Harness Agent 长时运行设计 |
