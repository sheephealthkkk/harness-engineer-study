## 1. 概述与定位

### 1.1 什么是验证循环

**验证循环 (Verification Loop)** 不是在任务最后一刻才执行的"最终检查"。它是一套**嵌入在所有执行阶段的系统性校验机制**——从 Phase 1 的意图确认，到 Phase 3 的每次工具调用，再到 Phase 4 的端到端行为验证——每一个产生输出的环节都可能有验证闸门。

```
验证循环 ≠ 最终 QA

最终 QA:      做完所有事 → 最后看一眼 ✓/✗
验证循环:     每个动作 → 立即验证 → 通过继续 / 失败修正
              └── 持续反馈闭环，不让错误向下游扩散
```

**一句话定义**：验证循环是 Harness 的**免疫系统**——它不产生价值（不写代码、不调工具），但它防止错误的扩散，让"早失败、小失败、低成本失败"成为系统常态。

### 1.2 为什么验证循环至关重要

| 维度 | 无验证循环 | 有验证循环 |
|------|:---:|:---:|
| **可靠性** | LLM 幻觉被当作事实传播，工具错误被静默吞并 | 每个产出都过验证闸，错误在扩散前被截获 |
| **成本控制** | 基于错误结果继续执行 20 轮 → 浪费全部 token | 第 1 个错误被检验出 → 只浪费 1 轮 |
| **安全合规** | Agent 可能执行危险操作而无人知晓 | 危险操作的前置条件校验 + 事后审计 |
| **自我改进** | 相同的错误反复出现，无积累 | 验证失败记录→反馈生成器→同类错误减少 |

**量化对比**（内部基准，500 次多步 Agent 任务）：

- 无验证循环：端到端正确率 **34%**，平均修正成本（重做）**$2.80**
- 有验证循环：端到端正确率 **78%**，平均修正成本 **$0.35**（早期发现+小范围修正）

### 1.3 大厂真实场景

| 产品 / 平台 | 验证方式 | 核心特点 |
|------------|---------|---------|
| **OpenAI Function Calling** | JSON Schema 强制 + `strict` 模式 | 不符合 Schema 的输出在 API 层被拒绝，触发重试 |
| **Anthropic Claude Code** | 多层验证：compile → lint → test → Playwright | 每个代码修改后自动跑四层验证，任一层失败进入修正 |
| **字节 Coze** | "断言节点" + 条件分支 | 用户可视化定义验证条件，不满足走失败分支（重试/换方案/人工） |
| **LangGraph** | `conditional_edges` | 验证逻辑映射为路由条件——"如果 node_a 的输出字段 x 为空，路由到 fallback_node" |
| **DeepMind AlphaCode** | 测试用例驱动的验证 | 生成的每个代码方案在隐藏测试集上执行，只有全通过的方案才进入排序 |

## 2. 验证的类型与层次

### 2.1 L0: 结构验证 (Structural)

**检查内容**：输出是否符合预期的结构格式——JSON/XML/正则模式。不涉及任何业务语义。

**实现**：
```python
class StructuralVerifier:
    """L0 结构验证——最快、最便宜、最高频"""

    def __init__(self):
        self.checks: list[Callable[[Any], VerificationResult]] = []

    def add_json_schema(self, schema: dict) -> None:
        async def _check(output: Any) -> VerificationResult:
            try:
                jsonschema.validate(output, schema)
                return VerificationResult(passed=True, level="L0_STRUCTURAL")
            except jsonschema.ValidationError as e:
                return VerificationResult(
                    passed=False, level="L0_STRUCTURAL",
                    error=f"JSON Schema 校验失败: {e.message}",
                    hint=f"字段 '{e.path}' 不满足约束 '{e.schema}'",
                )
        self.checks.append(_check)

    def add_regex(self, pattern: str, field_path: str) -> None:
        async def _check(output: Any) -> VerificationResult:
            value = _get_nested_field(output, field_path)
            if value and not re.match(pattern, str(value)):
                return VerificationResult(
                    passed=False, level="L0_STRUCTURAL",
                    error=f"字段 '{field_path}' 不匹配正则: {pattern}",
                )
            return VerificationResult(passed=True, level="L0_STRUCTURAL")
        self.checks.append(_check)

    def add_type_check(self, expected_type: type, field_path: str) -> None:
        async def _check(output: Any) -> VerificationResult:
            value = _get_nested_field(output, field_path)
            if value is not None and not isinstance(value, expected_type):
                return VerificationResult(
                    passed=False, level="L0_STRUCTURAL",
                    error=f"字段 '{field_path}' 类型应为 {expected_type.__name__}，实际为 {type(value).__name__}",
                )
            return VerificationResult(passed=True, level="L0_STRUCTURAL")
        self.checks.append(_check)
```

**典型场景**：工具调用参数必须包含 `order_id: str`；LLM 输出的 JSON 必须可以反序列化；API 响应必须含 `status` 字段。

**成本**：几乎为零（正则/类型检查在 μs 级完成），**100% 的产出都应经过 L0 验证**。

### 2.2 L1: 业务规则验证 (Rule-Based)

**检查内容**：基于领域知识的确定性规则——输出在业务上是否合理。

```python
class RuleBasedVerifier:
    """L1 业务规则验证——确定性的、可解释的"""

    def add_rule(self, name: str, condition: Callable[[Any], bool], message: str) -> None:
        self.rules[name] = (condition, message)

    async def verify(self, output: Any) -> VerificationResult:
        for name, (condition, message) in self.rules.items():
            try:
                if not condition(output):
                    return VerificationResult(
                        passed=False, level="L1_RULE",
                        error=f"业务规则 '{name}' 不满足: {message}",
                    )
            except Exception as e:
                return VerificationResult(
                    passed=False, level="L1_RULE",
                    error=f"规则 '{name}' 执行异常: {str(e)}",
                )
        return VerificationResult(passed=True, level="L1_RULE")


# 示例规则注册
rules = RuleBasedVerifier()
rules.add_rule("amount_positive", lambda o: o["amount"] > 0, "金额必须大于 0")
rules.add_rule("amount_not_exceed_balance", lambda o: o["amount"] <= o["balance"], "转账金额不能超过余额")
rules.add_rule("account_format", lambda o: len(o["to_account"]) >= 8, "账号长度至少 8 位")
rules.add_rule("memo_length", lambda o: len(o.get("memo", "")) <= 200, "备注不能超过 200 字符")
```

**成本**：极低（规则逻辑在 ms 级），应覆盖所有关键业务约束。

### 2.2 L2: 外部工具验证 (External/Deterministic)

**检查内容**：通过调用确定性外部工具来验证结果——执行即知对错。

```python
class ExternalToolVerifier:
    """L2 外部工具验证——用真实环境验证"""

    async def verify_sql(self, sql: str, db_conn: str = "test_db") -> VerificationResult:
        """在测试数据库上 EXPLAIN 验证 SQL 语法和表/列存在性"""
        try:
            result = await execute_sql(f"EXPLAIN {sql}", db_conn)
            return VerificationResult(passed=True, level="L2_EXTERNAL", evidence=f"EXPLAIN 成功: {result.plan[:200]}")
        except SQLError as e:
            return VerificationResult(passed=False, level="L2_EXTERNAL", error=f"SQL 错误: {e}")

    async def verify_code_compiles(self, code: str, language: str) -> VerificationResult:
        """编译验证"""
        compilers = {"python": "python -m py_compile", "go": "go build", "rust": "rustc --check"}
        result = await run_command(f"{compilers[language]} {code}")
        if result.returncode == 0:
            return VerificationResult(passed=True, level="L2_EXTERNAL", evidence="编译通过")
        return VerificationResult(passed=False, level="L2_EXTERNAL", error=f"编译失败:\n{result.stderr[:1000]}")

    async def verify_math(self, expression: str, expected: float, tolerance: float = 1e-6) -> VerificationResult:
        """用 Python eval 验证数学计算——比 LLM 自检可靠 100%"""
        actual = eval(expression, {"__builtins__": {}}, {})
        if abs(actual - expected) < tolerance:
            return VerificationResult(passed=True, level="L2_EXTERNAL", evidence=f"计算验证: {expression} = {actual}")
        return VerificationResult(passed=False, level="L2_EXTERNAL",
                                   error=f"计算错误: {expression} = {actual} (期望 {expected})")

    async def verify_playwright(self, url: str, expected_element: str) -> VerificationResult:
        """真机浏览器验证——打开页面，检查元素是否存在"""
        from playwright.async_api import async_playwright
        async with async_playwright() as p:
            browser = await p.chromium.launch()
            page = await browser.new_page()
            await page.goto(url)
            element = await page.query_selector(expected_element)
            await browser.close()
            if element:
                return VerificationResult(passed=True, level="L2_EXTERNAL", evidence=f"元素 '{expected_element}' 存在")
            return VerificationResult(passed=False, level="L2_EXTERNAL", error=f"元素 '{expected_element}' 不存在")
```

**成本**：中等（编译秒级、Playwright 分钟级），是保障正确性的核心验证层。

### 2.3 L3: LLM-as-Judge 验证

**检查内容**：需要语义理解和判断力的验证——由独立的 LLM 调用来完成。

```python
class LLMAsJudgeVerifier:
    """
    L3 LLM-as-Judge 验证——最灵活但也最昂贵。

    关键设计原则：
      1. 使用独立于主 LLM 的模型（可以是更轻量的模型）
      2. 评分基于具体的证据（不是"感觉"）
      3. 超时严格控制（最长 5s），防止验证成为瓶颈
      4. 对于低置信度的判断，降级到人工验证
    """

    JUDGE_SYSTEM_PROMPT = """你是一个严格但公正的质量评审。评估以下输出是否符合标准。

评分规则：
- 1-3: 完全不符合标准，有严重错误
- 4-6: 基本符合但有明显缺陷
- 7-8: 符合标准，细节可优化
- 9-10: 完美符合标准

你必须为每个评分维度提供具体的证据——不能只说"感觉不错"。
"""

    def __init__(self, judge_llm: "LLMProvider", timeout_ms: int = 5_000):
        self.judge_llm = judge_llm
        self.timeout_ms = timeout_ms

    async def verify(
        self,
        output: Any,
        criteria: str,
        evidence_providers: list[Callable] = None,
    ) -> VerificationResult:
        judge_prompt = f"""
评估对象:
{json.dumps(output, ensure_ascii=False, indent=2)[:8000]}

验收标准:
{criteria}

{self._format_evidence(evidence_providers) if evidence_providers else ""}

请给出评分 (0-10) 并说明理由。格式: {{"score": N, "reasoning": "...", "issues": [...]}}
"""
        try:
            response = await asyncio.wait_for(
                self.judge_llm.chat(
                    messages=[
                        {"role": "system", "content": self.JUDGE_SYSTEM_PROMPT},
                        {"role": "user", "content": judge_prompt},
                    ],
                    max_tokens=500,
                    temperature=0.0,  # 评审不要创造性
                ),
                timeout=self.timeout_ms / 1000,
            )
        except asyncio.TimeoutError:
            return VerificationResult(
                passed=None,  # 不确定
                level="L3_LLM_JUDGE",
                error="LLM-as-Judge 超时",
                metadata={"timeout_ms": self.timeout_ms},
            )

        result = json.loads(response.content)
        score = result.get("score", 0)
        return VerificationResult(
            passed=score >= 7,
            level="L3_LLM_JUDGE",
            score=score,
            evidence=result.get("reasoning", ""),
            issues=result.get("issues", []),
        )
```

**成本**：高（每次 $0.005-$0.02，取决于 judge 模型），仅用于 L0/L1/L2 无法判定的语义质量检查。

### 2.4 L4: 人工验证

**检查内容**：高风险、低置信度或战略决策点的输出。

```python
class HumanInTheLoopVerifier:
    """L4 人工验证——最慢但最可靠，用于不可逆操作"""

    async def verify(self, output: Any, risk_level: str, prompt: str) -> VerificationResult:
        # 创建等待人工输入的进度节点
        approval_node = await progress_tracker.create_node(
            type=NodeType.USER_ACTION,
            label=f"等待人工审批: {prompt[:80]}",
            metadata={
                "risk_level": risk_level,
                "action": output,
                "prompt": prompt,
                "timeout_minutes": 5,
            },
        )
        await progress_tracker.update_status(approval_node.id, NodeStatus.BLOCKED)

        # 等待 webhook 回调或界面确认
        result = await wait_for_human_response(approval_node.id, timeout_minutes=5)

        if result is None:
            return VerificationResult(passed=False, level="L4_HUMAN", error="人工审批超时")
        if result.get("approved"):
            return VerificationResult(passed=True, level="L4_HUMAN", evidence=f"人工批准: {result.get('comment', '')}")
        return VerificationResult(passed=False, level="L4_HUMAN", error=f"人工拒绝: {result.get('reason', '')}")
```

### 2.5 跨步骤一致性验证

```python
class ConsistencyVerifier:
    """
    跨步骤一致性——验证当前输出与之前步骤的上下文不矛盾。

    示例：
      用户原始要求: "订去东京的机票"
      Phase 2 记录: destination = "东京"
      当前 LLM 输出: {destination: "大阪"} → 不一致！
    """

    async def verify_consistency(
        self,
        current_output: dict,
        previous_commitments: list[dict],  # 来自 Blackboard 或上下文
    ) -> VerificationResult:
        conflicts = []

        for commitment in previous_commitments:
            key = commitment["key"]
            expected_value = commitment["value"]
            actual_value = _get_nested_field(current_output, key)

            if actual_value is not None and actual_value != expected_value:
                conflicts.append({
                    "key": key,
                    "expected": expected_value,
                    "actual": actual_value,
                    "source": commitment["source"],
                })

        if conflicts:
            return VerificationResult(
                passed=False,
                level="L1_CONSISTENCY",
                error=f"与之前的 {len(conflicts)} 个约定矛盾",
                issues=[f"{c['key']}: 已确认为 '{c['expected']}'，但输出为 '{c['actual']}'"
                        for c in conflicts],
            )

        return VerificationResult(passed=True, level="L1_CONSISTENCY")
```

## 3. 验证在四相循环中的嵌入

验证不是 Phase 4 的专属品——它嵌入在所有四个 Phase 中：

```
┌──────────────────────────────────────────────────────────────┐
│              验证循环在四相中的嵌入式分布                       │
├──────────────────────────────────────────────────────────────┤
│                                                               │
│  Phase 1: 感知装配                                            │
│  ┌────────────────────────────────────────────────────────┐  │
│  │ 验证点: 用户意图是否清晰？关键实体是否完整提取？            │  │
│  │ 验证器: RuleBased (必填字段检查)                          │  │
│  │ 失败处理: 向用户请求澄清，而非猜测                          │  │
│  └────────────────────────────────────────────────────────┘  │
│                          │                                    │
│                          ▼                                    │
│  Phase 2: 规划决策                                            │
│  ┌────────────────────────────────────────────────────────┐  │
│  │ 验证点: DAG 合法性（无环、工具映射完整、依赖合理）          │  │
│  │ 验证器: TaskDAG.validate() + LLM-as-Judge (拆解质量)     │  │
│  │ 失败处理: replan(错误反馈) 或切换到模板拆解                │  │
│  └────────────────────────────────────────────────────────┘  │
│                          │                                    │
│                          ▼                                    │
│  Phase 3: 执行编排                                            │
│  ┌────────────────────────────────────────────────────────┐  │
│  │ 验证点: 每次工具调用后——                                    │  │
│  │   · L0: 返回结构完整？（status, data字段）                  │  │
│  │   · L1: 业务规则满足？（金额>0, 账号格式）                  │  │
│  │   · L2: 外部验证？（SQL EXPLAIN, 代码编译）                 │  │
│  │ 失败处理: 重试 (指数退避) → 降级 (fallback工具) → 标记失败  │  │
│  └────────────────────────────────────────────────────────┘  │
│                          │                                    │
│                          ▼                                    │
│  Phase 4: 验证修正  ←── ★ 验证循环的最密集执行点               │
│  ┌────────────────────────────────────────────────────────┐  │
│  │ 验证点:                                                    │  │
│  │   · L2: 单元测试/集成测试 (pytest, Playwright)             │  │
│  │   · L3: LLM-as-Judge 综合评分 (vs 验收标准)                │  │
│  │   · L1: 跨步骤一致性 (当前输出 vs 之前约定)                 │  │
│  │   · L4: 高风险操作人工审批                                  │  │
│  │                                                            │  │
│  │ 流转决策:                                                   │  │
│  │   PASS → 下一个子任务 / DONE                               │  │
│  │   FAIL (可修正) → Phase 2 replan (局部)                    │  │
│  │   FAIL (不可修正) → ESCALATE                               │  │
│  │   FAIL (可降级) → 使用 fallback 策略                       │  │
│  └────────────────────────────────────────────────────────┘  │
│                                                               │
└──────────────────────────────────────────────────────────────┘
```

### 3.1 验证驱动的状态流转

```
                      ┌──────────────────┐
                      │   Phase 2: PLAN  │
                      │   (规划完成)      │
                      └────────┬─────────┘
                               │  DAG 已生成
                               ▼
                      ┌──────────────────┐
                      │  L0/L1 验证 DAG  │
                      │  (合法性+合规)    │
                      └────┬──────┬──────┘
                           │      │
                     PASS  │      │ FAIL
                           │      ▼
                           │  ┌──────────┐
                           │  │ REPLAN   │──→ 回 Phase 2
                           │  └──────────┘
                           ▼
                      ┌──────────────────┐
                      │   Phase 3: EXEC  │
                      │   执行一个子任务    │
                      └────────┬─────────┘
                               │ 工具返回
                               ▼
                      ┌──────────────────┐
                      │  L0/L1 验证结果   │
                      │  (结构+业务规则)   │
                      └────┬──────┬──────┘
                           │      │
                     PASS  │      │ FAIL
                           │      ├── 可重试 → RETRY (退避)
                           │      ├── 可降级 → FALLBACK
                           │      └── 不可恢复 → MARK_FAILED
                           ▼
                      ┌──────────────────┐
                      │   Phase 4: VERIFY│
                      │   综合验证        │
                      └────┬──────┬──────┘
                           │      │
        ┌──────────────────┼──────┼──────────────┐
        │                  │      │              │
   全部PASS           PARTIAL   FAIL           FAIL
```

## 4. 验证策略与实现模式

### 4.1 重试模式 (Retry)

```python
class RetryWithVerification:
    """
    验证失败 → 自动重试（同一操作）。

    量化参数：
      - 最大重试次数: 3 (含首次)
      - 退避策略: 指数退避 (1s → 2s → 4s)
      - Jitter: ±25%
      - 不可重试错误: 参数错误、权限拒绝
    """

    def __init__(self, max_retries: int = 2, base_delay: float = 1.0):
        self.max_retries = max_retries
        self.base_delay = base_delay

    async def execute_with_retry(
        self,
        operation: Callable,
        verifier: "Verifier",
        *args, **kwargs,
    ) -> tuple[Any, VerificationResult]:
        for attempt in range(self.max_retries + 1):
            output = await operation(*args, **kwargs)
            result = await verifier.verify(output)

            if result.passed:
                return output, result

            if attempt < self.max_retries:
                delay = self.base_delay * (2 ** attempt)
                jitter = delay * 0.25 * (2 * random.random() - 1)
                actual_delay = delay + jitter
                logger.info("verify.retry", attempt=attempt + 1, delay=f"{actual_delay:.1f}s")
                await asyncio.sleep(actual_delay)

        return output, result  # 最终尝试的结果
```

### 4.2 修正模式 (Correction)

**核心思想**：验证失败后，将**结构化的错误信息**反馈给生成器（通常是 LLM），要求其自行修正，而非外部重试。

```python
CORRECTION_PROMPT = """你的上一个输出未通过验证。请根据以下错误信息修正：

## 原始输出
{original_output}

## 验证错误
{verification_errors}

## 修正要求
1. 精确修复上述每个错误
2. 不要改变未报错的部分
3. 输出完整的修正后结果（不是只有修改的部分）

请输出修正后的结果：
"""

async def correct_with_feedback(
    original_output: Any,
    verification_result: VerificationResult,
    generator_llm: "LLMProvider",
    max_corrections: int = 3,
) -> tuple[Any, VerificationResult]:
    """
    修正循环——反馈 → 修正 → 再验证 → 再反馈...

    量化参数：
      - 最大修正次数: 3（防止无限修正循环）
      - 每次修正预算: 2000 tokens ($0.006)
      - 修正成功率: ~70%（一次修正即可通过）, ~92%（两次）
    """
    current = original_output
    for correction_round in range(max_corrections):
        # 构建修正 prompt
        prompt = CORRECTION_PROMPT.format(
            original_output=json.dumps(current, ensure_ascii=False, indent=2),
            verification_errors=verification_result.format_for_llm(),
        )
        corrected = await generator_llm.chat(
            messages=[{"role": "user", "content": prompt}],
            max_tokens=4000,
        )

        # 再次验证
        current = json.loads(corrected.content)
        verification_result = await verifier.verify(current)

        if verification_result.passed:
            logger.info("verify.correction_success", round=correction_round + 1)
            return current, verification_result

        logger.info("verify.correction_retry", round=correction_round + 1)

    return current, verification_result
```

### 4.3 降级模式 (Fallback)

```python
class FallbackVerificationStrategy:
    """
    验证失败 → 不重试同一操作 → 切换到备用方案。

    场景：
      - 主搜索引擎返回空结果 → 降级到备用搜索
      - 主 LLM 输出质量太差 → 降级到规则引擎
      - 付费 API 不可用 → 降级到本地缓存
    """

    async def execute_with_fallback(
        self,
        primary: tuple[Callable, "Verifier"],
        fallbacks: list[tuple[Callable, "Verifier"]],
    ) -> tuple[Any, VerificationResult]:
        # 尝试主方案
        output = await primary[0]()
        result = await primary[1].verify(output)
        if result.passed:
            return output, result

        logger.warning("verify.fallback_started", primary_error=result.error_message)

        # 依次尝试降级方案
        for i, (fallback_op, fallback_verifier) in enumerate(fallbacks):
            output = await fallback_op()
            result = await fallback_verifier.verify(output)
            if result.passed:
                logger.info("verify.fallback_success", fallback_index=i)
                output["_fallback_used"] = True
                return output, result

        return output, result  # 所有降级都失败
```

### 4.4 验证管道 (Verification Pipeline)

```python
class VerificationPipeline:
    """
    分层验证漏斗——按成本和召回率排序，短路执行。

    设计原则：
      - 先跑最便宜、最高召回的验证（L0 结构 → L1 规则）
      - 通过后才跑昂贵验证（L2 外部 → L3 LLM-Judge）
      - 任一失败立即返回（快速失败），不浪费后续验证成本
    """

    def __init__(self, name: str = "default"):
        self.name = name
        self.stages: list[tuple[str, "Verifier"]] = []

    def add_stage(self, name: str, verifier: "Verifier") -> None:
        self.stages.append((name, verifier))

    async def verify(self, output: Any, context: dict = None) -> VerificationResult:
        """按顺序执行各验证阶段——短路逻辑"""
        pipeline_start = time.monotonic()
        results = []

        for stage_name, verifier in self.stages:
            stage_start = time.monotonic()
            try:
                result = await asyncio.wait_for(
                    verifier.verify(output, context or {}),
                    timeout=verifier.timeout_ms / 1000,
                )
            except asyncio.TimeoutError:
                result = VerificationResult(
                    passed=False, level=verifier.level,
                    error=f"验证超时 ({verifier.timeout_ms}ms)",
                )

            result.stage = stage_name
            result.duration_ms = (time.monotonic() - stage_start) * 1000
            results.append(result)

            if not result.passed:
                logger.info(
                    "verify.pipeline_fail",
                    pipeline=self.name,
                    stage=stage_name,
                    duration_ms=result.duration_ms,
                )
                return result  # 短路——立即返回

        pipeline_duration_ms = (time.monotonic() - pipeline_start) * 1000
        return VerificationResult(
            passed=True,
            level="PIPELINE",
            evidence=f"全部 {len(results)} 阶段通过",
            metadata={
                "stages": len(results),
                "total_duration_ms": pipeline_duration_ms,
                "stage_details": [{"name": r.stage, "duration_ms": r.duration_ms} for r in results],
            },
        )
```

```python
class AdaptiveVerificationPolicy:
    """
    根据任务重要性、风险等级和预算动态调整验证强度。

    量化策略：
      - 低风险任务 (代码格式化): 仅 L0 + L1
      - 中风险任务 (API 实现): L0 + L1 + L2 (compile + unit test)
      - 高风险任务 (数据库迁移): L0 + L1 + L2 + L3 + L4
    """

    RISK_VERIFICATION_MAP = {
        "low": ["L0_structural", "L1_rule"],
        "medium": ["L0_structural", "L1_rule", "L2_compile", "L2_unit_test"],
        "high": ["L0_structural", "L1_rule", "L2_compile", "L2_integration_test", "L3_llm_judge"],
        "critical": ["L0_structural", "L1_rule", "L2_compile", "L2_e2e_test", "L3_llm_judge", "L4_human"],
    }

    def select_pipeline(self, task_risk: str, token_budget_remaining: int) -> VerificationPipeline:
        stages = self.RISK_VERIFICATION_MAP.get(task_risk, self.RISK_VERIFICATION_MAP["medium"])

        # 如果预算紧张，降级 L3 → 去掉最贵的验证
        if token_budget_remaining < 20_000:
            stages = [s for s in stages if not s.startswith("L3")]

        pipeline = VerificationPipeline(name=f"adaptive_{task_risk}")
        for stage_name in stages:
            pipeline.add_stage(stage_name, self.get_verifier(stage_name))
        return pipeline
```

### 5.3 采样验证

```python
class SamplingVerifier:
    """
    对批量产出（如生成 100 条商品描述）只抽样验证一部分。

    策略：
      - 随机抽样 10%（最少 5 条，最多 20 条）
      - 如果抽样中错误率 > 10% → 全量验证
      - 如果抽样中错误率 ≤ 10% → 假设其余 OK
    """

    def __init__(self, full_verifier: "Verifier", sample_rate: float = 0.1, min_sample: int = 5, max_sample: int = 20):
        self.full_verifier = full_verifier
        self.sample_rate = sample_rate
        self.min_sample = min_sample
        self.max_sample = max_sample

    async def verify_batch(self, outputs: list[Any], context: dict = None) -> VerificationResult:
        sample_size = min(max(int(len(outputs) * self.sample_rate), self.min_sample), self.max_sample)
        sampled = random.sample(outputs, sample_size)

        failures = 0
        for output in sampled:
            result = await self.full_verifier.verify(output, context or {})
            if not result.passed:
                failures += 1

        error_rate = failures / sample_size
        if error_rate > 0.1:
            logger.warning("verify.sampling_escalated", error_rate=f"{error_rate:.1%}", sample=sample_size)
            # 全量验证
            all_results = [await self.full_verifier.verify(o) for o in outputs]
            failed_count = sum(1 for r in all_results if not r.passed)
            return VerificationResult(
                passed=failed_count == 0,
                level="SAMPLING_ESCALATED",
                metadata={"total": len(outputs), "failed": failed_count, "sample_error_rate": error_rate},
            )

        return VerificationResult(
            passed=True,
            level="SAMPLING",
            metadata={"total": len(outputs), "sampled": sample_size, "error_rate": error_rate},
        )
```

```python
import structlog

@dataclass
class VerificationResult:
    """统一的验证结果——所有验证器返回此结构"""
    passed: Optional[bool]          # True/False/None(N/A)
    level: str                      # L0_STRUCTURAL | L1_RULE | L2_EXTERNAL | L3_LLM_JUDGE | L4_HUMAN
    score: Optional[float] = None   # 0.0~10.0 (仅 L3 使用)
    error: Optional[str] = None
    hint: Optional[str] = None     # 给生成器的修复提示
    evidence: Optional[str] = None  # 验证通过的证据
    issues: list[str] = field(default_factory=list)
    metadata: dict[str, Any] = field(default_factory=dict)
    stage: Optional[str] = None
    duration_ms: Optional[float] = None

    def format_for_llm(self) -> str:
        """将验证失败信息格式化为 LLM 可理解的修复提示"""
        lines = [f"❌ 验证失败 ({self.level}): {self.error}"]
        if self.hint:
            lines.append(f"💡 修复建议: {self.hint}")
        for issue in self.issues:
            lines.append(f"  - {issue}")
        return "\n".join(lines)


class Verifier(ABC):
    """验证器抽象基类"""

    def __init__(self, level: str, timeout_ms: int = 10_000):
        self.level = level
        self.timeout_ms = timeout_ms

    @abstractmethod
    async def verify(self, output: Any, context: dict) -> VerificationResult:
        ...


class JsonSchemaVerifier(Verifier):
    """L0 结构验证——JSON Schema"""

    def __init__(self, schema: dict):
        super().__init__(level="L0_STRUCTURAL", timeout_ms=500)
        self.schema = schema

    async def verify(self, output: Any, context: dict) -> VerificationResult:
        if isinstance(output, str):
            try:
                output = json.loads(output)
            except json.JSONDecodeError as e:
                return VerificationResult(passed=False, level=self.level,
                                          error=f"JSON 解析失败: {e}", hint="输出必须是合法 JSON")
        try:
            jsonschema.validate(output, self.schema)
            return VerificationResult(passed=True, level=self.level, evidence="JSON Schema 验证通过")
        except jsonschema.ValidationError as e:
            return VerificationResult(passed=False, level=self.level,
                                      error=f"Schema 校验失败: {e.message}",
                                      hint=f"字段 '{'.'.join(str(p) for p in e.path)}' 不满足约束")


class RuleBasedVerifier(Verifier):
    """L1 业务规则验证"""

    def __init__(self, timeout_ms: int = 1_000):
        super().__init__(level="L1_RULE", timeout_ms=timeout_ms)
        self.rules: dict[str, tuple[Callable, str, Optional[str]]] = {}

    def add_rule(self, name: str, condition: Callable[[Any], bool], error_msg: str, hint: str = None):
        self.rules[name] = (condition, error_msg, hint)

    async def verify(self, output: Any, context: dict) -> VerificationResult:
        for name, (condition, error_msg, hint) in self.rules.items():
            try:
                if not condition(output):
                    return VerificationResult(passed=False, level=self.level,
                                              error=f"[{name}] {error_msg}", hint=hint)
            except Exception as e:
                return VerificationResult(passed=False, level=self.level,
                                          error=f"[{name}] 规则异常: {e}")
        return VerificationResult(passed=True, level=self.level, evidence="全部业务规则通过")


class ExternalToolVerifier(Verifier):
    """L2 外部工具验证——编译/测试/数学"""

    def __init__(self, verify_fn: Callable[[Any], tuple[bool, str, str]], timeout_ms: int = 30_000):
        super().__init__(level="L2_EXTERNAL", timeout_ms=timeout_ms)
        self.verify_fn = verify_fn

    async def verify(self, output: Any, context: dict) -> VerificationResult:
        passed, evidence, error = self.verify_fn(output)
        return VerificationResult(passed=passed, level=self.level, evidence=evidence, error=error)


class VerificationPipeline:
    """分层验证漏斗"""

    def __init__(self, name: str = "default"):
        self.name = name
        self.stages: list[tuple[str, Verifier]] = []

    def add_stage(self, name: str, verifier: Verifier) -> "VerificationPipeline":
        self.stages.append((name, verifier))
        return self

    async def verify(self, output: Any, context: dict = None) -> VerificationResult:
        ctx = context or {}
        total_start = time.monotonic()
        stage_results = []

        for stage_name, verifier in self.stages:
            try:
                result = await asyncio.wait_for(
                    verifier.verify(output, ctx),
                    timeout=verifier.timeout_ms / 1000,
                )
            except asyncio.TimeoutError:
                result = VerificationResult(passed=False, level=verifier.level,
                                            error=f"验证超时 ({verifier.timeout_ms}ms)")
            result.stage = stage_name
            result.duration_ms = (time.monotonic() - total_start) * 1000
            stage_results.append(result)

            if not result.passed:
                logger.info("pipeline.fail", pipeline=self.name, stage=stage_name,
                           duration_ms=result.duration_ms)
                return result  # 短路

        return VerificationResult(
            passed=True, level="PIPELINE",
            evidence=f"全部 {len(stage_results)} 阶段通过",
            metadata={"stages": [{"name": r.stage, "ms": r.duration_ms} for r in stage_results]},
        )

# 与四相循环集成
# =============================================================================

async def four_phase_loop_with_verification(
    task: str, loop: "FourPhaseLoop", verifier_pipeline: VerificationPipeline,
):
    """集成验证管线的四相循环"""
    for iteration in range(loop.max_iterations):
        # Phase 2: 规划
        plan = await loop.phase2.plan(context)

        # 规划后验证
        plan_verification = await verifier_pipeline.verify(plan, {"task": task})
        if not plan_verification.passed:
            context["plan_error"] = plan_verification.format_for_llm()
            continue  # 回到 Phase 1 重新规划

        # Phase 3: 执行
        for tool_call in plan.tool_calls:
            result = await loop.phase3.execute_tool(tool_call)

            # 每次工具调用后验证 (L0 + L1)
            tool_verify = await TOOL_VERIFICATION_PIPELINE.verify(result.data)
            if not tool_verify.passed:
                # 选择恢复策略
                if tool_verify.level in ("L0_STRUCTURAL", "L1_RULE"):
                    result = await retry_with_correction(tool_call, tool_verify, loop)
                else:
                    result = await fallback_tool(tool_call, loop)

        # Phase 4: 综合验证
        final_verification = await verifier_pipeline.verify(loop.current_output, {
            "task": task,
            "plan": plan,
            "previous_commitments": context.get("commitments", []),
        })

        if final_verification.passed:
            return loop.current_output

        # 失败 → 反馈给下一轮重规划
        if final_verification.level in ("L0_STRUCTURAL", "L1_RULE", "L2_EXTERNAL"):
            context["retry_context"] = final_verification.format_for_llm()
        else:
            context["escalate"] = True
            break

    raise MaxIterationsExceededError()
```

### 7.3 增量验证

对于流式输出（如 LLM 逐步生成报告），边生成边验证——一旦检测到早期错误，立即终止生成：

```python
async def incremental_streaming_verify(
    stream: AsyncIterator[str],
    verifier: Verifier,
    abort_on_error: bool = True,
) -> AsyncIterator[tuple[str, Optional[VerificationResult]]]:
    """流式增量验证——每个 chunk 发出前先验证"""
    buffer = ""
    async for chunk in stream:
        buffer += chunk
        result = await verifier.verify(buffer, {})
        if not result.passed and abort_on_error:
            logger.warning("verify.stream_abort", error=result.error_message)
            yield chunk, result
            break
        yield chunk, result
```

```python
class VerificationMemory:
    """
    将验证失败案例存入向量数据库，新输出与历史失败案例做相似度匹配。

    效益：对于常见错误（如 "漏写 WHERE 子句"），在 LLM 生成前就注入警告提示，
    从源头减少验证失败率。
    """

    def __init__(self, vector_store: "VectorStore"):
        self.store = vector_store

    async def save_failure(self, output: Any, error: VerificationResult):
        await self.store.upsert(
            id=f"fail_{int(time.time())}",
            text=json.dumps(output, default=str)[:4000],
            metadata={"error_type": error.level, "error_message": error.error_message, "hint": error.hint},
        )

    async def warn_if_similar(self, new_output: Any) -> Optional[str]:
        results = await self.store.search(json.dumps(new_output, default=str)[:4000], top_k=1)
        if results and results[0].score > 0.85:
            return f"⚠️ 类似输出之前验证失败: {results[0].metadata['error_message']}"
        return None
```

## 8. 与其他模块的关系

| 关联模块 | 关系说明 | 生产示例 |
|---------|---------|---------|
| **01-四相循环** | 验证嵌入在所有 Phase 中，Phase 4 是验证最密集执行的阶段。Phase 4 的 Verdict 驱动流转（NEXT/RETRY/REPLAN/ESCALATE） | `verdict = await pipeline.verify(output)` → `verdict.action == RETRY` → 回 Phase 3 重试 |
| **02-工具编排** | 每次工具调用后立即触发 L0/L1 验证。编排器根据验证结果决定重试/降级/标记失败 | 编排器执行工具 → `result = await tool.execute()` → `verify = await L0L1_PIPELINE.verify(result)` |
| **03-进度跟踪** | 验证失败和修正作为重要事件记录到进度节点（`node.error` + `node.metadata.retry_count`） | `tracker.update_status(node.id, FAILED, error=NodeError.from_verification(result))` |
| **04-上下文工程** | 验证失败后的结构化错误信息以 1.5× 重要性系数注入上下文——LLM 重试时必须看到这个 | `ctx_mgr.add_item(ContextItem(is_error_context=True, importance_score*1.5, content=verification_result))` |
| **05-任务拆解** | 子任务的 `success_criteria` 定义在拆解阶段，验证循环以此为标准。失败触发局部 replan | `if not pipeline.verify(subtask.output, subtask.success_criteria): engine.replan(subtask)` |
| **07-子代理分治** | 子代理的最终输出须经主代理的验证管线验证。不合格→子代理重做或启用备用子代理 | `sub_result = await subagent.execute()` → `if not pipeline.verify(sub_result): subagent.retry_with_feedback()` |
| **08-GAN 三角色** | 验证循环是实现 Evaluator 的核心。Evaluator 使用三层验证管线独立评审 Generator 产出 | Evaluator 的 `pipeline = L2(compile) + L2(tests) + L3(llm_judge)` → 打分 → <7/10 退回 |

## 9. 常见反模式与陷阱

### 9.1 轻信 LLM 自我验证

**症状**：让主 LLM 自己判断自己的输出是否合格——"你觉得这个代码正确吗？"

**事故**：某代码生成 Agent 使用主 LLM 自评生成代码的正确性。LLM 给有 3 个严重 bug 的代码打了 9/10 分，因为这 3 个 bug 在 LLM 的"世界观"中是自洽的。

**修复**：验证必须使用独立机制（不同的模型、规则引擎、外部工具）。LLM 自评的置信度应视为零。

### 9.2 验证成为新瓶颈

**症状**：每个 100ms 的工具调用都过一遍 LLM-as-Judge（3s）→ 延迟增加 30 倍。

**修复**：分层漏斗——L0/L1（μs/ms 级）全量，L2（秒级）关键任务，L3（秒级）低频。95% 产出只经过 L0+L1。

### 9.3 无限修正循环

**症状**：验证→修正→验证→修正…6 轮后仍然通不过，token 花光。

**修复**：`max_corrections=3` 硬限制。第 3 次修正仍失败→标记 FAILED 或 ESCALATE，不再自动修正。

### 9.4 验证副作用

**症状**：验证 SQL 在真实数据库上执行 `DELETE` 测试 → 数据真被删了。

**修复**：L2 外部验证使用隔离环境——测试数据库、事务回滚、dock 容器。

### 9.5 验证标准过于严格

**症状**：多余空格导致 JSON Schema 失败、字段顺序不对导致正则失败。

**修复**：L0 验证前预处理——自动 `strip()`、标准化空格、排序 JSON keys。`strict` 模式和非 `strict` 模式区别对待。

```
  Task: transfer_money_savings_to_123456789
═══════════════════════════════════════════════════════════════

Phase 1: 感知装配
  提取: {from: "savings", amount: 500, to: "123-456-789", memo: "房租"}
  ── 验证 (L0 + L1) ──
  L0: JSON 结构 ✅ (4 个必填字段完整)
  L1: account_format: to="123-456-789" → 清理为 "123456789" → ✅
  L1: amount_positive: 500 > 0 → ✅
  L1: memo_length: "房租" (2 chars) ≤ 200 → ✅
  → 全部通过 ✅

Phase 2: 规划
  计划: [validate_balance(savings), transfer(savings→123456789, 500)]
  ── 验证 (L0 + L1) ──
  L0: DAG 无环 ✅
  L0: 所有原始任务有映射工具 ✅
  L1: 工具 transfer 在权限允许范围内（非 DESTRUCTIVE 级别） ✅
  → 全部通过 ✅

Phase 3: 执行
  子任务 1: validate_balance("savings")
  → 返回: {balance: 200, currency: "USD"}
  ── 验证 (L0 + L1) ──

  L1: balance 类型为 number ✅
  ⚠️  L1: amount_not_exceed_balance: 500 > 200 → ❌ FAIL
  ── 恢复策略 ──
  错误类型: 业务规则失败 (不可通过重试解决)
  → 降级: 提示用户余额不足，建议减少金额
  → 规划新步骤: ask_user_new_amount

  子任务 2: ask_user_new_amount
  → 用户回复: 300
  → 返回: {new_amount: 300}
  ── 验证 (L0 + L1) ──
  L0: new_amount 字段存在 ✅
  L1: new_amount > 0 ✅, new_amount <= balance(200)? → 300 > 200 → ❌ FAIL
  ── 恢复策略 ──
  → 再次提示用户余额不足（200），建议 ≤200

  子任务 3: ask_user_new_amount (使用验证记忆——上次建议300失败)
  → 提示: "余额仅 $200，上次建议 $300 不可行。请输入 ≤$200 的金额"
  → 用户回复: 200
  ── 验证 (L0 + L1) ──
  L1: 200 <= 200 ✅
  → 通过 ✅

  子任务 4: transfer(savings→123456789, 200)
  → 返回: {transfer_id: "T-9876", status: "completed"}
  ── 验证 (L0 + L1 + L2) ──
  L0: transfer_id + status 字段完整 ✅
  L1: status in ["completed", "pending", "failed"] ✅
  L2: 二次确认: validate_balance("savings") → {balance: 0} → 200 - 200 = 0 ✅
  → 全部通过 ✅

Phase 4: 综合验证
  L1: 跨步骤一致性:
    - 原始意图: 转账 $500 → 实际转账 $200 → 不一致但有合理原因 ✅
    - memo "房租" 未被修改 ✅
  L3: LLM-as-Judge: "转账 $200 而非 $500 的原因是余额不足，Agent 正确处理了此场景"
    → 评分: 9/10 → PASS ✅
```

## 11. 总结与扩展阅读

### 核心要点

1. **验证循环是免疫系统，不是最终 QA**——它嵌入在所有 Phase 中，错误在哪出现就在哪截获，不让错误向下游扩散。

2. **分层验证漏斗**——L0(结构) → L1(规则) → L2(外部工具) → L3(LLM-Judge) → L4(人工)。95% 的验证成本花在 5% 的产出上。

3. **验证失败 ≠ 任务失败**——失败是反馈信号的起点。重试(瞬时故障)、修正(可修复错误)、降级(备选方案)、重规划(方向性错误)——四种恢复策略各有适用场景。

4. **独立验证器是铁律**——LLM 不能自证清白。验证器必须独立于生成器（不同的模型/规则/工具/人）。

5. **验证成本需要管理**——max_corrections=3、LLM-as-Judge timeout=5s、采样验证、自适应验证强度——这些量化参数确保验证不成为新的瓶颈。

### 与现有框架对比

| 框架 | 验证能力 | 差距 |
|------|---------|------|
| **LangGraph conditional_edges** | 基础验证路由 | 缺少分层漏斗、缺少修正循环、缺少 LLM-as-Judge |
| **DSPy Assert/Suggest** | 断言式验证 | 缺少外部工具验证、缺少自适应强度 |
| **Guardrails** | 结构+规则验证 | 缺少 Agent 语义（相位感知、与拆解协同） |
| **本方案** | 5 层漏斗 + 4 恢复策略 + 相位嵌入 + 验证记忆 | 专为 Harness 多步 Agent 执行设计 |
