# 机制详解：验证循环 (Verify Loop)

> **对应失效**：④ Tool 错误吞并（任务层面）、⑦ 缺自动化评审（微观层面）
> **核心贡献**：工具编排保证"调用不崩溃"（工程层），验证循环保证"结果正确"（任务层）。每个子任务完成后用真机工具实际验证，而不信任 LLM 的自我判断。
> **所属支柱**：控制流（主要）、输入流（验证结果的输入）

---

## 一、为什么 LLM 不能自我验证？

### 1.1 自我验证的天然缺陷

LLM 在被问到"你做对了吗？"时，有三个系统性偏差：

```
偏差 1: 幻觉一致性 (Hallucination Consistency)
  LLM 在生成错误代码时，它的"世界观"是自洽的。
  当它自评时，它用同一个"世界观"去评判 → 找不到自己的错误。
  
  类比: 让做梦的人判断自己是不是在做梦
  
偏差 2: 自我辩护倾向 (Self-Justification Bias)  
  LLM 倾向于给自己生成的答案正面评价。
  不是因为它在"撒谎"，而是因为训练数据中高质量回答
  通常伴随积极的自我评价。
  
  类比: 让学生给自己的考卷打分
  
偏差 3: 外部状态不可见 (External State Blindness)
  LLM 没有感官。它不知道真实文件系统上文件有没有被修改，
  不知道浏览器里渲染出来是什么样，不知道测试到底能不能跑过。
  
  类比: 让盲人仅凭记忆判断房间的颜色
```

### 1.2 验证循环的金科玉律

> **只有来自 LLM 外部的、可复现的、客观的验证信号才能被信任。**
> 
> LLM 的"我觉得做好了" = 噪音。
> pytest 的"31 passed" = 信号。

## 二、验证循环的工作流

### 2.1 核心流程

```
子任务完成
    ↓
┌─────────────────────────────┐
│  第 1 层: 编译/语法验证       │
│  工具: compile / lint / type check │
│  速度: 快 (秒级)              │
│  覆盖: 语法错误、类型错误      │
└──────────┬──────────────────┘
           ↓ 通过
┌─────────────────────────────┐
│  第 2 层: 单元/功能验证       │
│  工具: pytest / unittest / jest │
│  速度: 中 (秒-分钟级)         │
│  覆盖: 逻辑正确性             │
└──────────┬──────────────────┘
           ↓ 通过
┌─────────────────────────────┐
│  第 3 层: 集成/行为验证       │
│  工具: Playwright / curl / e2e test │
│  速度: 慢 (分钟级)            │
│  覆盖: 端到端行为             │
└──────────┬──────────────────┘
           ↓ 通过 (或不通过)
┌─────────────────────────────┐
│  验证结果 → 反馈给 Agent      │
│  - 通过 → 继续下一个子任务    │
│  - 不通过 → 注入失败信息 → 重试 │
└─────────────────────────────┘
```

### 2.2 验证循环伪代码

```python
def verify_loop(subtask, max_retries=3):
    """
    三层验证 + 失败重试
    """
    
    for attempt in range(max_retries):
        
        # ================================================================
        # L1: 语法/编译层
        # ================================================================
        if subtask.requires_compile_check:
            l1_result = run_compile_check(subtask)
            
            if not l1_result.passed:
                # 编译失败 —— 不需要继续验证
                failure_info = {
                    "level": "L1_COMPILE",
                    "attempt": attempt + 1,
                    "output": l1_result.output,
                    "expected": "编译通过",
                    "actual": l1_result.errors,
                    "hint": generate_l1_hint(l1_result)
                }
                
                if attempt < max_retries - 1:
                    # 告诉 Agent 哪里错了，让它修
                    subtask.retry_with_context(failure_info)
                    continue
                else:
                    # 重试次数耗尽
                    subtask.mark_failed(failure_info)
                    return False
        
        # ================================================================
        # L2: 单元/功能层
        # ================================================================
        if subtask.requires_unit_test:
            l2_result = run_tests(subtask.test_target)
            
            if not l2_result.passed:
                failure_info = {
                    "level": "L2_TESTS",
                    "attempt": attempt + 1,
                    "test_output": l2_result.output,
                    "failed_tests": l2_result.failed_test_names,
                    "expected": f"{l2_result.total} tests passed",
                    "actual": f"{l2_result.failed} failed, {l2_result.passed} passed",
                    "hint": generate_l2_hint(l2_result)
                }
                
                if attempt < max_retries - 1:
                    subtask.retry_with_context(failure_info)
                    continue
                else:
                    subtask.mark_failed(failure_info)
                    return False
        
        # ================================================================
        # L3: 集成/行为层
        # ================================================================
        if subtask.requires_e2e_verification:
            l3_result = run_e2e_verification(subtask)
            
            if not l3_result.passed:
                failure_info = {
                    "level": "L3_E2E",
                    "attempt": attempt + 1,
                    "screenshot_path": l3_result.screenshot,
                    "log_path": l3_result.log_file,
                    "description": l3_result.failure_description,
                    "hint": generate_l3_hint(l3_result)
                }
                
                if attempt < max_retries - 1:
                    subtask.retry_with_context(failure_info)
                    continue
                else:
                    subtask.mark_failed(failure_info)
                    return False
        
        # ================================================================
        # 全部验证通过！
        # ================================================================
        subtask.mark_completed({
            "l1": l1_result if subtask.requires_compile_check else None,
            "l2": l2_result if subtask.requires_unit_test else None,
            "l3": l3_result if subtask.requires_e2e_verification else None,
            "attempts": attempt + 1
        })
        return True
    
    return False
```

### 3.2 验证方式选择指南

```python
def select_verification_method(subtask):
    """
    根据子任务的特征自动选择验证方式
    """
    
    if subtask.phase == "analyze":
        # 分析阶段：不需要自动化验证，但需要用户确认分析结论
        return VerificationMethod.USER_APPROVAL
    
    if subtask.type == "code_modification":
        return [
            VerificationMethod.LINT,           # 风格
            VerificationMethod.TYPE_CHECK,      # 类型
            VerificationMethod.UNIT_TEST,       # 逻辑
        ]
    
    if subtask.type == "api_implementation":
        return [
            VerificationMethod.LINT,
            VerificationMethod.TYPE_CHECK,
            VerificationMethod.UNIT_TEST,
            VerificationMethod.INTEGRATION_TEST,  # 比普通代码修改多了这个
        ]
    
    if subtask.type == "ui_implementation":
        return [
            VerificationMethod.LINT,
            VerificationMethod.UNIT_TEST,
            VerificationMethod.E2E_TEST,         # 用 Playwright 验证 UI
        ]
    
    if subtask.type == "file_generation":
        return [
            VerificationMethod.FILE_EXISTS,       # 文件存在
            VerificationMethod.FILE_SIZE,         # 大小合理
            VerificationMethod.FILE_FORMAT,       # 格式正确
        ]
```

## 四、失败上下文注入

### 4.1 让 Agent "看见"失败

验证失败时，不是简单地告诉 Agent "你失败了"，而是给它足够的诊断信息：

```python
def build_failure_context(subtask, verification):
    """
    从验证失败中提取对 Agent 有用的诊断上下文
    """
    
    context = {
        "message": f"子任务 '{subtask.description}' 验证失败（第 {verification.attempt} 次尝试）",
        "level": verification.level,
    }
    
    if verification.level == "L1_COMPILE":
        context.update({
            "error_type": "编译错误",
            "errors": parse_compile_errors(verification.output),
            "action_hint": (
                "请仔细阅读编译错误信息。通常错误指向的文件和行号是准确的。"
                "如果错误信息不明确，尝试只修改一行后重新编译看错误是否变化。"
            )
        })
    
    elif verification.level == "L2_TESTS":
        context.update({
            "error_type": "测试失败",
            "failed_tests": verification.failed_tests,
            "failure_details": [
                {
                    "test": ft.name,
                    "assertion": ft.assertion,
                    "expected": ft.expected,
                    "actual": ft.actual
                }
                for ft in verification.failed_test_details
            ],
            "action_hint": (
                f"{len(verification.failed_tests)} 个测试失败。"
                "检查每个失败的 assertion——actual 和 expected 的差异就是修改的bug所在。"
            )
        })
    
    elif verification.level == "L3_E2E":
        context.update({
            "error_type": "端到端验证失败",
            "screenshot": verification.screenshot_path,
            "log": verification.log_path[:2000],  # 截断版
            "action_hint": (
                "查看截图对比预期和实际渲染效果。"
                "如果有 Playwright trace，可以回放操作过程定位问题。"
            )
        })
    
    return context
```

### 4.2 智能提示生成

```python
def generate_l1_hint(compile_result):
    """
    根据编译错误类型生成针对性的修复提示
    """
    if "undefined reference" in compile_result.errors:
        return "你可能使用了未导入或未定义的方法/变量。检查拼写和导入语句。"
    
    if "type mismatch" in compile_result.errors:
        return "类型不匹配。检查参数类型是否与方法签名一致。"
    
    if "syntax error" in compile_result.errors:
        return "语法错误。检查括号匹配、分号缺失等常见问题。"
    
    if "cannot find symbol" in compile_result.errors:
        return "找不到符号。可能是类名/方法名拼写错误，或者缺少 import。"
    
    # 默认提示
    return f"编译失败，共 {compile_result.error_count} 个错误。请逐行修复。"


def generate_l2_hint(test_result):
    """
    根据测试失败类型生成针对性的修复提示
    """
    hints = []
    
    for failure in test_result.failed_test_details:
        if "AssertionError" in failure.assertion:
            hints.append(
                f"测试 '{failure.name}' 断言失败：\n"
                f"  期望: {failure.expected}\n"
                f"  实际: {failure.actual}\n"
                f"  差异: 检查第 {failure.line} 行的逻辑"
            )
        elif "AttributeError" in failure.assertion:
            hints.append(
                f"测试 '{failure.name}' 属性错误：\n"
                f"  对象缺少属性或方法。可能是方法名还未更新。"
            )
        elif "ImportError" in failure.assertion:
            hints.append(
                f"测试 '{failure.name}' 导入错误：\n"
                f"  检查文件路径和模块名是否正确。"
            )
    
    return "\n".join(hints)
```

## 五、三层验证的性能优化

### 5.1 快速失败原则

```
L1 (编译) → L2 (测试) → L3 (E2E)
   ↓ 失败      ↓ 失败      ↓ 失败
   立即返回    立即返回    返回失败

不浪费时间在后面的验证上，因为底层已经失败了。
```

### 5.2 增量验证

```python
# 不是每次从头运行所有测试，而是只运行相关的测试

# ❌ 每次运行全量测试 (3000 个用例，3 分钟)
def verify_all():
    return run_tests("tests/")

# ✅ 只运行与修改相关的测试 (15 个用例，3 秒)
def verify_changes(subtask):
    changed_files = subtask.result.changed_files
    affected_tests = find_affected_tests(changed_files)
    return run_tests(affected_tests)

# 定期（每 5 个子任务）运行一次全量测试
def periodic_full_verification(task_list):
    if task_list.completed_count % 5 == 0:
        return run_tests("tests/")
```

### 5.3 并行验证

```python
# 独立的验证层可以并行执行
# 例如：lint + 类型检查 两者互不依赖

async def parallel_verification(subtask):
    tasks = []
    
    if subtask.requires_lint:
        tasks.append(run_lint(subtask))
    if subtask.requires_type_check:
        tasks.append(run_type_check(subtask))
    
    # 并行执行，等待全部完成
    results = await asyncio.gather(*tasks)
    
    return all(r.passed for r in results), results
```

## 六、验证循环的局限性

1. **验证工具的覆盖率**：如果测试覆盖率只有 30%，验证循环只能防 30% 的错误
2. **验证盲区**：某些质量属性难以自动化验证（如代码可读性、架构设计的优雅性）
3. **验证工具的可靠性**：如果验证脚本本身有 bug → 假通过 / 假失败
4. **E2E 的脆弱性**：UI 自动化测试天生脆弱，选择器变化就失败

**这些局限性正是 GAN 三角色架构（人类级别的综合评审）存在的理由。** 验证循环处理确定性的自动化检查，GAN 处理需要判断力的综合评审。

## 七、总结

验证循环是 Harness 的**质量守门人**，也是"信任模型"与"验证模型"的分界线。

核心原则：
1. **绝不信任 LLM 的自我判断** —— 只信任外部工具的客观验证信号
2. **分层验证** —— L1 语法 → L2 逻辑 → L3 行为，逐层把关
3. **失败信息结构化** —— 不是 "你失败了"，而是 "你在哪里、怎么失败的、怎么修"
4. **快速失败** —— 底层失败不浪费时间在上层验证
