# Harness Engineer 能力模型

> **Harness Engineer**：专门设计和维护 Agent 驾驭系统的工程师。
> 他们的工作不是写 prompt，不是调模型，而是构建模型能稳定运行的工程环境。

---

## 一、Harness Engineer 的定义

```
Harness Engineer ≠ Prompt Engineer
Harness Engineer ≠ ML Engineer  
Harness Engineer ≠ Backend Engineer

Harness Engineer = 让 Agent 从"Demo"变成"产品"的人

Prompt Engineer 关注: 怎么让模型理解我的意思（一代工程）
Harness Engineer 关注: 怎么让模型 30 分钟不崩溃 + 产出可信 + 成本可控（三代工程）
```

**Harness Engineer 回答的核心问题**：

1. 这个 Agent 能连续运行 30 分钟而不出问题吗？
2. crash 之后怎么恢复？丢失了什么？
3. Agent 的输出谁在检查？我怎么知道它真的做对了？
4. Agent 有没有可能越权执行危险操作？有没有防护？
5. 这个任务花了多少 API 费用？能预算化吗？
6. Context 快满了怎么办？能不能自动管理？
7. 复杂任务怎么拆解？怎么并行？

### Level 1: 基础理论与概念

**目标**：理解 Agent 为什么需要 Harness，能识别 Naive Agent 的失效模式。

```
知识清单:
  □ Agent = Model + Harness 公式的深刻理解
  □ Naive Agent 的八种失效形态（能逐一解释原因和后果）
  □ 三代工程演进的逻辑（Prompt → Context → Harness）
  □ LLM 的基本原理（token, context window, temperature, prompt cache）
  □ Agent 的基本架构（system prompt → tool calling → response loop）

检验标准:
  - 看到一个 Agent 产品，能指出它有哪些 Harness 机制
  - 看到一个 Agent 失败案例，能诊断是八种失效中的哪一种
  - 能解释为什么 Level 2 (LLM+Code Interpreter) 和 Level 3 (Claude Code) 
    有本质不同，即使它们用同一个底层模型
```

### Level 2: 工具与实践

**目标**：能使用主流 Agent 产品和框架，理解各自的 Harness 实现。

```
知识清单:
  □ Claude Code: 完整 Harness 机制理解
    - 四相循环的观察和利用
    - CLAUDE.md 的配置策略
    - Hook 系统的使用和自定义
    - Permission 配置
    - Progress tracking 的恢复机制
  
  □ LangChain / LangGraph: 框架层的 Harness 构建
    - StateGraph 的状态管理
    - Checkpoint 机制
    - Human-in-the-loop 实现
    - Tool 的 Schema 设计和错误处理
  
  □ Agent SDK / API: 底层 API 使用
    - Anthropic API (messages, tools, prompt cache)
    - OpenAI API (function calling, streaming)
    - Token counting 和管理

  □ Git 工作流
    - Agent 操作的 git 最佳实践
    - Commit 粒度控制
    - Branch 策略

检验标准:
  - 能配置 Claude Code 的 CLAUDE.md 和 settings.json 
  - 能用 LangGraph 实现一个带 checkpoint 的 Agent 流程
  - 能写出一个工具编排层的原型（结构化 ToolResult）
```

### Level 3: 机制深入理解与调优

**目标**：深入理解八大机制，能调优每个机制的参数和策略。

```
知识清单:
  □ 四相循环
    - 四个阶段的 token/时间分配策略
    - 最大迭代次数和收敛策略的调优
    - 不同类型的任务 → 不同的循环配置
  
  □ 工具编排
    - ToolResult Schema 设计
    - 错误分类策略（ErrorType 枚举设计）
    - 恢复策略映射（错误类型 → 恢复动作）
    - 权限闸与工具编排的集成
  
  □ 上下文工程
    - Token 监控与三级管理策略
    - Prompt Cache 优化（前缀稳定、断点设置）
    - 压缩策略：摘要 vs 截断
    - CLAUDE.md 的设计方法论
  
  □ 任务拆解
    - 原子性判断标准
    - 依赖关系建模
    - 并行组标记策略
    - 增量拆解 vs 自上而下拆解
  
  □ 验证循环
    - 三层验证的设计和实现
    - 验证工具的选择和集成
    - 失败上下文注入策略
  
  □ 子代理分治
    - 子代理的职责边界设计
    - 三种调用模式的选择
    - 子代理的故障隔离
  
  □ GAN 三角色
    - 三角色的职责分离
    - 评分标准体系设计
    - 博弈退修流程
  
  □ 进度跟踪
    - 进度文件 Schema 设计
    - 原子写入实现
    - 恢复流程设计
    - Git checkpoint 策略

检验标准:
  - 能设计一个完整的 task_list Schema
  - 能调优 context 管理的阈值参数
  - 能设计一个 Evaluator 的评分标准体系
  - 能诊断一个 Agent 运行日志中的性能瓶颈
```

### Level 4: 系统架构与设计

**目标**：能从零设计一个完整的 Harness 系统。

```
知识清单:
  □ 三支柱架构设计
    - 输入流管道的设计
    - 控制流的分层权限模型
    - 状态流的生命周期管理
  
  □ Harness 系统集成
    - 多 Agent 系统的协调架构
    - 子代理树的深度和宽度策略
    - 事件驱动的 Hook 系统设计
    - 可观测性：日志、指标、追踪
  
  □ 生产级考量
    - 故障模式与恢复策略（FMEA）
    - 安全和权限的纵深防御
    - 成本控制和预算系统
    - 性能优化（并行化、缓存、批处理）
    - 版本管理（Agent 版本、Prompt 版本、Harness 版本）

检验标准:
  - 能画出一个完整 Harness 系统的架构图
  - 能写出一份 Harness 系统的故障模式分析（FMEA）
  - 能为一个特定场景（如代码审查 Agent）设计完整的 Harness 方案
```

## 四、学习路径建议

```
阶段 1: 认知建立 (1-2 周)
  → 阅读本课程的三幕主文档 (破/立/实)
  → 阅读 Naive Agent 的八种失效形态
  → 动手：写一个 Naive Agent，让它崩溃，观察为什么崩溃

阶段 2: 工具实践 (2-4 周)
  → 深度使用 Claude Code，观察它的 Harness 行为
  → 配置 CLAUDE.md + settings.json
  → 试验 Hook 系统
  → 用 LangGraph 构建一个简单的 Agent 流程

阶段 3: 机制深入 (4-8 周)
  → 逐一深读八大机制文档
  → 每读一个机制，在代码中实现一个原型
  → 重点：上下文工程 + 任务拆解 + 验证循环（最基础的三件套）

阶段 4: 系统设计 (8-12 周)
  → 选择一个真实场景，设计完整的 Harness 方案
  → 对比至少 3 个 Agent 产品的 Harness 优劣
  → 关注 Anthropic / OpenAI 的 Agent 工程博客和研究
```

## 五、Harness Engineer 的思维模型

```
1. "失败是必然的" 思维
   不是"如果出错怎么办"，而是"这个组件会在哪里出错，出错时怎么恢复？"
   
2. "验证优于信任" 思维
   模型说"做好了"不算。工具验证说"通过了"才算。
   
3. "成本是设计参数" 思维
   Token 预算和 API 费用是设计时要考虑的变量，不是事后的账单。
   
4. "状态是资产" 思维
   Agent 的状态（进度、中间产物、决策记录）是有价值的资产，需要持久化和保护。
   
5. "收敛是主动行为" 思维
   别等 Agent 自己停下来。设计主动的收敛机制：
   最大迭代次数、无进展检测、重复失败检测、token 预算耗尽。
```
