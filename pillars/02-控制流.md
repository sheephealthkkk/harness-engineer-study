# 三支柱之二：控制流 (Control Flow)

> **核心问题**：Agent 能干什么？行为边界在哪里？什么能做、什么不能做、什么需要审批才能做？
> **代表机制**：四相循环、工具编排、权限闸、验证循环、GAN 三角色

---

## 一、控制流的本质

控制流 = **拉红线**。你不是在写 Agent "可以做什么"，而是在定义 Agent "不可以做什么"和"什么情况下必须停下来等人确认"。

```
输入流 = Agent 的"眼睛"（看见什么）
控制流 = Agent 的"手铐"（能做什么、必须经过什么流程才能做）
状态流 = Agent 的"寿命"（能跑多久）
```

---

## 二、控制流的五层模型

```
Layer 5: 博弈层 (Adversarial)
  GAN 三角色 → 多方制衡 → 无法自我欺骗
  ─────────────────────────────────────
Layer 4: 审批层 (Approval Gating)
  权限闸 + Hook 系统 → 危险操作拦截
  ─────────────────────────────────────
Layer 3: 验证层 (Verification)
  验证循环 → 每步完成后真机验证 → 不通过不能继续
  ─────────────────────────────────────
Layer 2: 编排层 (Orchestration)
  四相循环 + 工具编排 → 结构化执行+结构化返回
  ─────────────────────────────────────
Layer 1: 约束层 (Constraints)
  System Prompt + Token 预算 → 行为边界+成本边界
  ─────────────────────────────────────
```

---

## 三、各层详解

### Layer 1: 约束层

```python
# System Prompt 中的行为约束（软约束）
SOFT_CONSTRAINTS = """
## 行为边界
- 你是协助者，不是决策者。涉及架构决策、技术选型时，给出建议而非直接执行
- 你每一步的修改应该是小范围的、可验证的。一次修改不超过 3 个文件
- 修改前先理解现有代码。不知道的就是不知道，不要猜
- 遇到不确定的情况，停下来询问用户，不要自己假设
"""

# Token 预算（硬约束）
HARD_CONSTRAINTS = {
    "max_iterations": 25,           # 最多 25 轮
    "max_tokens_per_request": 160000,  # 单词请求 token 上限
    "max_session_tokens": 1000000,  # 整个 session token 预算
    "max_session_duration": 3600,   # 最长运行 1 小时
}
```

### Layer 2: 编排层

编排层保证 Agent 的每一步行动都是**结构化的、可控的**：

- **四相循环**：每一步必须经过 GATHER → ACT → VERIFY → ITERATE，不能跳过
- **工具编排**：每个工具调用必须通过结构化接口，永远不吞错误

### Layer 3: 验证层

验证层建立"不验证就不能继续"的硬规则：

```python
# 验证层的关键约束
VERIFICATION_GATES = {
    # 编译门：代码修改后必须编译通过
    "compile_gate": {
        "trigger": "任何 .py / .ts / .go / .java 文件被修改",
        "action": "自动运行编译器",
        "on_failure": "进入修复循环，最多 3 次",
        "skip_condition": "修改的只是注释或文档"
    },
    
    # 测试门：修改代码后必须运行相关测试
    "test_gate": {
        "trigger": "任何函数/方法逻辑被修改",
        "action": "运行受影响的测试文件",
        "on_failure": "修复失败测试，不能跳过",
        "skip_condition": "只修改了格式化/注释"
    },
    
    # 用户门：关键决策点必须用户确认
    "user_gate": {
        "trigger": "架构变更、新增依赖、API 变更",
        "action": "暂停并请求用户确认",
        "on_failure": "N/A (用户说不行就换方案)"
    }
}
```

### Layer 4: 审批层

```python
class PermissionSystem:
    """
    分层权限系统 — Agent 的每一个操作都必须经过权限检查
    """
    
    # 权限级别定义
    LEVELS = {
        0: {"name": "READ", "policy": "auto", "description": "只读操作"},
        1: {"name": "MODIFY_SAFE", "policy": "auto_or_confirm", "description": "可逆的修改"},
        2: {"name": "MODIFY_RISKY", "policy": "confirm", "description": "需确认的修改"},
        3: {"name": "NETWORK", "policy": "confirm", "description": "网络请求"},
        4: {"name": "DESTRUCTIVE", "policy": "confirm_with_warning", "description": "不可逆操作"},
        5: {"name": "FORBIDDEN", "policy": "deny", "description": "绝对禁止"},
    }
    
    # Hook 系统（27 种 Hook）
    HOOKS = {
        # 工具执行前
        "pre_tool_use": [],       # 任何工具调用前
        "pre_bash": [],           # Shell 命令执行前
        "pre_edit": [],           # 文件编辑前
        "pre_write": [],          # 文件写入前
        "pre_delete": [],         # 文件删除前（默认: 要求确认）
        
        # 工具执行后
        "post_tool_use": [],      # 任何工具调用后
        "post_bash": [],          # Shell 命令执行后
        "post_edit": [],          # 文件编辑后
        
        # Session 生命周期
        "on_session_start": [],   # Session 开始
        "on_session_end": [],     # Session 结束
        "on_error": [],           # 发生未处理错误
        
        # 自定义
        "on_file_change": [],     # 文件变更
        "on_git_commit": [],      # Git commit 前
        "on_token_warning": [],   # Token 达到警告线
    }
```

### Layer 5: 博弈层

博弈层是最上层的控制——用多个独立 Agent 的相互制衡替代单个 Agent 的自我约束：

```
单 Agent 的自我约束：
  "我不应该生成低质量代码" ← 它自己判断什么是"低质量"
  → 问题：自我判断有天然偏差

GAN 三角色的多方制衡：
  Planner: "这是验收标准"
  Generator: "我按标准来生成"
  Evaluator: "我来独立检查你是否真的达标了"
  → 博弈：Evaluator 的独立性杜绝了自我评分
```

---

## 四、控制流的设计原则

1. **默认禁止 (Default Deny)**：不明确允许的操作默认为禁止
2. **最小权限 (Least Privilege)**：只给予完成当前子任务所需的最小权限
3. **分层审批 (Layered Approval)**：不同风险级别对应不同的审批策略
4. **审批审计 (Approval Audit)**：所有审批操作留下可追溯的日志

---

## 五、控制流代表机制

| 机制 | 对控制流的贡献 |
|------|-------------|
| **四相循环** | 控制执行节奏——不能跳过验证阶段 |
| **工具编排** | 控制工具调用——结构化接口+权限前置检查 |
| **权限闸** | 控制操作权限——危险操作必须人工确认 |
| **验证循环** | 控制质量门——不通过验证不能继续 |
| **GAN 三角色** | 控制质量上限——多方博弈，杜绝自我欺骗 |
