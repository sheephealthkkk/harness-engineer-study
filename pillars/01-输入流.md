# 三支柱之一：输入流 (Input Flow)

> **核心问题**：Agent 能看见什么？它的"视野"里有什么信息？这些信息的质量、时效性、完整性如何？
> **代表机制**：上下文工程、任务拆解、子代理分治、进度跟踪

---

## 一、输入流的本质

输入流决定了 Agent 做出决策的**信息基础**。Agent 只能基于它"看到"的信息来推理和行动。如果输入流有盲区，Agent 的决策就有盲区。

```
输入流的质量 = 信息的相关性 × 准确性 × 时效性 × 完整性
```

---

## 二、输入流的三层结构

```
┌──────────────────────────────────────────────────────┐
│  Layer 1: 固定层 (Static Layer)                       │
│  ────────────────────────────────────                │
│  生命周期: 跨所有 session 不变                         │
│  内容:                                               │
│   · System Prompt — Agent 的角色、行为准则、边界       │
│   · CLAUDE.md — 项目规范、编码约定、常用命令、注意事项   │
│   · Tool Definitions — 可用工具的名称、参数、功能       │
│                                                      │
│  设计原则: 一旦确定，session 内绝不修改                 │
│           （修改 = Cache Miss → 成本飙升）             │
├──────────────────────────────────────────────────────┤
│  Layer 2: 会话层 (Session Layer)                      │
│  ────────────────────────────────────                │
│  生命周期: 当前 session 存活                           │
│  内容:                                               │
│   · 用户任务描述 — 用户最初给出的完整任务               │
│   · 对话历史 — 当前 session 的 messages               │
│   · 压缩摘要 — L1 压缩后产生的中间过程摘要              │
│   · 子代理返回结果 — 其他子 Agent 的产出摘要            │
│                                                      │
│  设计原则: 保留决策节点，丢弃过程噪音                   │
├──────────────────────────────────────────────────────┤
│  Layer 3: 动态层 (Dynamic Layer)                      │
│  ────────────────────────────────────                │
│  生命周期: 每次 API 请求可能变化                        │
│  内容:                                               │
│   · 环境信息 — 当前时间、工作目录、Git 分支/状态        │
│   · 进度信息 — 当前子任务、完成进度、上次错误           │
│   · 工具返回 — read_file/grep/glob 的最新结果          │
│   · 验证结果 — 上一个子任务的验证通过/失败信息          │
│                                                      │
│  设计原则: 按需注入，用完即弃                           │
└──────────────────────────────────────────────────────┘
```

## 三、输入流的设计原则

### 3.1 最小充分原则

```
放入 context 的每一条信息都必须满足：够用，但不多余

检查清单:
  ✅ 这条信息与当前子任务直接相关吗？
  ✅ 没有这条信息 Agent 能做出正确决策吗？
  ✅ 这条信息是最新的版本吗？
  ✅ 这条信息的大小在合理范围内吗？
  
  如果是 否 否 否 否 → 不要放进 context
```

### 3.2 Cache 友好原则

```python
# 输入流的"排列顺序"直接影响成本

# ✅ Cache 友好的排列
messages = [
    # 最前面的内容最有可能被缓存
    system_prompt,          # ← 永久不变，100% 缓存
    tool_definitions,       # ← 基本不变，高缓存命中
    user_task,              # ← session 内不变，缓存
    # ... 缓存断点 ...
    # 后面的内容每次都会重新计算
    recent_interactions,    # ← 可能变化
    current_subtask_context, # ← 每轮都变
]

# 每节省 1% 的 Cache 重计算 = 节省 ~0.9% 的 API 费用
```

### 3.3 渐进加载原则

```
不要一次性把所有相关信息都放进 context
→ 先放最相关的
→ Agent 需要更多信息时通过工具调用获取
→ 工具返回的结果自然进入 context

这就像一个研究员：
  - 不是先读完整个图书馆再开始写作
  - 而是带着问题去查找、获取、使用信息
```

## 四、输入流管道的实现

```python
class InputPipeline:
    """
    管理 Agent 每次请求前"看到什么"
    """
    
    def prepare_input(self, task, progress, messages):
        """每次 API 调用前，构建本次请求的输入"""
        
        # 1. 固定层（只在 session 初始化时构建一次）
        if self.is_new_session:
            input_base = self.build_static_layer()
        
        # 2. 会话层（持续维护）
        managed_messages = self.context_manager.manage(messages)
        
        # 3. 动态层（每次请求时按需注入）
        dynamic_context = self.build_dynamic_layer(task, progress)
        
        # 4. 组装
        return input_base + managed_messages + [dynamic_context]
    
    def build_static_layer(self):
        """构建固定层 — 只在 session 启动时调用一次"""
        return [
            {"role": "system", "content": SYSTEM_PROMPT},
            {"role": "user", "content": f"<project_context>{CLAUDE_MD}</project_context>"},
        ]
    
    def build_dynamic_layer(self, task, progress):
        """构建动态层 — 每次请求都可能不同"""
        dynamic_info = {
            "type": "system_status",
            "timestamp": datetime.now().isoformat(),
            "working_directory": os.getcwd(),
            "git": {
                "branch": get_git_branch(),
                "status": get_git_status_summary(),
            },
            "progress": {
                "completed": progress.completed_count,
                "total": progress.total_count,
                "current_subtask": progress.current_subtask.description,
            }
        }
        
        # 如果是重试，注入失败上下文
        if progress.current_subtask.attempts > 0:
            dynamic_info["previous_attempt"] = {
                "attempt_number": progress.current_subtask.attempts,
                "error": progress.current_subtask.last_error,
                "verification_output": progress.current_subtask.last_verification_output,
            }
        
        return {
            "role": "user",
            "content": json.dumps(dynamic_info)
        }
```

## 五、输入流的反模式

| 反模式 | 为什么是反模式 | 正确做法 |
|--------|-------------|---------|
| 在 System Prompt 中注入动态时间 | 每次时间都变 → Cache 永远不命中 | 动态信息放 user message 中 |
| 把整个代码库放进 context | Context 瞬间占满 | 按需用工具读取 |
| 每条工具返回原样保留 | 冗余信息累积 | 截断、摘要、只保留关键输出 |
| 所有信息一次性注入 | 很多信息根本用不上 | 渐进加载，需要时再获取 |
| 在 messages 中间插入内容 | 破坏 Cache 前缀 | 只在尾部追加新内容 |

## 六、输入流代表机制

| 机制 | 对输入流的贡献 |
|------|-------------|
| **上下文工程** | 管理"放什么"+"什么时候清" |
| **任务拆解** | 将输入流的焦点限制在当前子任务 |
| **子代理分治** | 隔离独立子任务的输入流 |
| **进度跟踪** | 提供跨 session 的输入流连续性 |
| **工具编排** | 控制工具返回的数据如何进入输入流 |
