# 三支柱之三：状态流 (State Flow)

> **核心问题**：Agent 能跑多久？如何在长时间运行中保持稳定？面对 Context 膨胀、Token 消耗、进程中断等自然熵增，系统如何对抗？
> **代表机制**：上下文工程、进度跟踪、Token 预算

---

## 一、状态流的本质

状态流 = Agent 的**韧性 (Resilience)**。自然界一切系统都趋向熵增（变乱），Agent 的运行也不例外：

```
Agent 运行中的"熵增"：
  1. messages 列表 → 自然增长（每轮增加工具调用记录）
  2. Token 消耗 → 持续累积
  3. 中间产物 → 越来越多
  4. 模型注意力 → 越来越分散
  5. 系统稳定性 → 越来越脆弱（运行越久，crash 概率越高）
```

**状态流的目标**：对抗熵增，让 Agent 能持续、稳定地长时间运行。

## 二、状态流的生命周期

```
┌─────────────────────────────────────────────────────┐
│                   Session 生命周期                    │
├─────────────────────────────────────────────────────┤
│                                                      │
│  [启动]                                              │
│    │                                                 │
│    ├── 1. 检查是否存在 progress.json                  │
│    │      ├── 存在 → 恢复上下文 + 断点续传             │
│    │      └── 不存在 → 创建新进度 + 新 session         │
│    │                                                 │
│    ├── 2. 初始化 Token 预算                           │
│    │      └── 总预算: 1,000,000 tokens               │
│    │                                                 │
│    ├── 3. 初始化上下文管理器                           │
│    │      └── 监控 tokens: 80K 警告 / 120K 压缩       │
│    │                                                 │
│    ▼                                                 │
│  [运行中]                                            │
│    │                                                 │
│    ├── 每轮迭代后:                                    │
│    │   ├── 保存 progress.json                        │
│    │   ├── 检查 token 预算余量                        │
│    │   └── 检查 context 是否超过阈值                  │
│    │                                                 │
│    ├── 每个子任务完成后:                               │
│    │   ├── 保存 progress.json (含 output_summary)     │
│    │   ├── 可选: git commit (里程碑)                  │
│    │   └── 清理该子任务的细节 context                  │
│    │                                                 │
│    ├── Context 超过压缩阈值时:                         │
│    │   └── L1 压缩 → L2 子代理卸载 → L3 重置          │
│    │                                                 │
│    ▼                                                 │
│  [终止]                                              │
│    │                                                 │
│    ├── 正常终止:                                      │
│    │   ├── 保存最终 progress.json (status=completed)  │
│    │   ├── 生成 session 摘要                          │
│    │   └── 清理临时文件                               │
│    │                                                 │
│    ├── 异常终止 (crash):                              │
│    │   ├── progress.json 保留在 crash 时的状态         │
│    │   ├── 下次启动时自动检测并恢复                    │
│    │   └── 未持久化的最近 1-2 轮操作丢失 (损失 < 2 分钟) │
│    │                                                 │
│    └── Token 预算耗尽:                                │
│        ├── 优雅降级: 保存进度，报告用户                │
│        ├── 提示: "任务完成 X%，预算已用 Y tokens"      │
│        └── 允许用户追加预算继续                        │
│                                                      │
└─────────────────────────────────────────────────────┘
```

## 三、对抗熵增的三大武器

### 3.1 令牌预算 (Token Budget)

```python
class TokenBudgetManager:
    """
    状态流的"油耗表"——Agent 能跑多远，取决于还剩多少 token
    """
    
    def __init__(self):
        self.session_budget = 1_000_000     # 总预算
        self.session_used = 0               # 已使用
        self.request_tokens = 0             # 当前请求
        self.warning_threshold = 0.7         # 70% 开始警告
        self.critical_threshold = 0.9        # 90% 启动收敛
        
        # 成本估算（Claude Sonnet 价格）
        self.COST_PER_1M_INPUT = 3.0       # $3/1M input tokens
        self.COST_PER_1M_OUTPUT = 15.0     # $15/1M output tokens
        self.estimated_cost = 0.0
    
    def before_request(self, messages):
        """每次请求前检查预算"""
        
        remaining = self.session_budget - self.session_used
        usage_ratio = self.session_used / self.session_budget
        
        if usage_ratio > self.critical_threshold:
            # 进入应急模式
            return {
                "status": "CRITICAL",
                "action": "CONVERGE",
                "message": (
                    f"Token 预算已使用 {usage_ratio:.0%}。"
                    "请尽快完成任务并提交结果。"
                ),
                "remaining_tokens": remaining,
            }
        
        if usage_ratio > self.warning_threshold:
            return {
                "status": "WARNING",
                "action": "SIMPLIFY",
                "message": (
                    f"Token 预算已使用 {usage_ratio:.0%}。"
                    "请精简后续操作，跳过非必要的优化。"
                ),
                "remaining_tokens": remaining,
            }
        
        return {"status": "OK", "remaining_tokens": remaining}
    
    def after_request(self, usage):
        """更新使用量"""
        self.session_used += usage.total_tokens
        self.estimated_cost += (
            usage.input_tokens * self.COST_PER_1M_INPUT / 1_000_000 +
            usage.output_tokens * self.COST_PER_1M_OUTPUT / 1_000_000
        )
```

### 3.2 上下文生命周期

```python
class ContextLifecycleManager:
    """
    状态流的"内存管理"——主动回收和压缩 context
    """
    
    # 触发阈值
    SOFT_LIMIT = 120_000    # 压缩
    HARD_LIMIT = 155_000    # 重置
    
    def manage(self, messages, progress):
        current_tokens = count_tokens(messages)
        
        if current_tokens > self.HARD_LIMIT:
            return self.hard_reset(messages, progress)
        
        if current_tokens > self.SOFT_LIMIT:
            return self.compact(messages, progress)
        
        # 即使没到阈值，也检查是否有"死"上下文可以清理
        return self.garbage_collect(messages, progress)
    
    def garbage_collect(self, messages, progress):
        """
        清理"死"上下文：
        - 已完成的子任务的详细工具调用记录
        - 截断的大文件内容（保留摘要即可）
        - 重复的验证结果
        """
        # 标记哪些 messages 属于已完成的子任务
        # 这些可以被压缩为 output_summary
        completed_ids = [st.id for st in progress.subtasks if st.status == "completed"]
        
        # 对于已完成子任务的详细交互，标记为"可压缩"
        # 当下次压缩触发时，优先压缩这些内容
        return messages  # 具体的压缩逻辑在 compact() 中
```

### 3.3 状态持久化

```python
class StatePersistence:
    """
    状态流的"存档点"——在任何时候中断都能从最近的存档恢复
    """
    
    SAVE_TRIGGERS = [
        "on_subtask_complete",      # 子任务完成时
        "on_iteration_end",         # 每轮迭代结束
        "on_signal",                # 收到终止信号
        "on_interval",              # 每 30 秒
    ]
    
    def save(self, progress):
        """原子保存"""
        # 1. 写临时文件
        tmp_path = f"{PROGRESS_FILE}.tmp.{uuid4()}"
        write_json(tmp_path, progress.to_dict())
        
        # 2. 原子 rename
        os.replace(tmp_path, PROGRESS_FILE)
        
        # 3. 可选：同时保存一个备份
        if progress.completed_count % 5 == 0:  # 每 5 个子任务
            backup_path = f"{PROGRESS_FILE}.backup.{progress.completed_count}"
            copy_file(PROGRESS_FILE, backup_path)
    
    def recover(self):
        """从存档恢复"""
        if not os.path.exists(PROGRESS_FILE):
            return None  # 无存档，全新开始
        
        progress = read_json(PROGRESS_FILE)
        
        # 验证存档完整性
        if self.validate(progress):
            return progress
        else:
            # 尝试从备份恢复
            return self.recover_from_backup()
```

## 四、状态流设计原则

1. **持久化优先 (Persist First)**：每次状态变更后立即落盘，不要"等一会儿再写"
2. **原子写入 (Atomic Write)**：先写临时文件，再 rename——崩溃不会损坏数据
3. **优雅降级 (Graceful Degradation)**：Token 预算将尽时，不是 crash，而是降级
4. **状态可审计 (Auditable State)**：任何时候打开 progress.json，都能理解当前状态

## 五、状态流代表机制

| 机制 | 对状态流的贡献 |
|------|-------------|
| **上下文工程** | 管理 context 生命周期（压缩、重置） |
| **进度跟踪** | 状态持久化 + 断点续传 |
| **Token 预算** | 硬上限 + 优雅降级 |
| **四相循环** | 通过最大迭代次数防止无限运行 |
| **子代理分治** | 子代理拥有独立的 token 预算和生命周期 |
